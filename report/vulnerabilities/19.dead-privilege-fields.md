# 19. Privilege and moderation fields that look like authorization but enforce nothing

- **Rank: 4 / 10**
- **Side: Server**
- **Category:** Misleading security surface / unused attack surface
- **Location:** `server/src/models/user.model.ts:48-53`

## The issue

The user schema declares a moderation and privilege system:

```ts
isDeactivated:    { type: Boolean, default: false },
isAdmin:          { type: Boolean, default: false },
isSuspended:      { type: Boolean, default: false },
suspensionStart:  { type: Date, default: null },
suspensionEnd:    { type: Date, default: null },
suspensionReason: { type: String, default: "" },
suspendedBy:      { type: mongoose.Schema.Types.ObjectId, ref: "User" },
```

Nothing implements it. I checked every reference in the codebase:

| Field | Written by | Read by |
| --- | --- | --- |
| `isDeactivated` | `deactivateUser`, `reactivateUser`, `loginUser` | login, refresh, and four read filters. **This one is real** |
| `isSuspended` | **nothing** | login, refresh, and four read filters |
| `isAdmin` | **nothing** | **nothing** |
| `suspensionStart` | **nothing** | **nothing** |
| `suspensionEnd` | **nothing** | **nothing** |
| `suspensionReason` | **nothing** | **nothing** |
| `suspendedBy` | **nothing** | **nothing** |

There is no admin route, no `requireAdmin` middleware, no suspension endpoint, no moderation UI. `grep -rn "isAdmin" server/src/` returns exactly one hit: the schema declaration.

The one near-miss is `getUserChannelProfile.ts:10`, which reads a query parameter named `adminId`:

```ts
const adminId = req.query.adminId as string;
```

The name suggests privilege. It is not. It is used at line 55 as the *viewer's* ID to compute whether that viewer subscribes to the channel. It is the same caller-supplied-identity pattern documented in `07.unauthenticated-write-to-any-users-watch-history.md`, wearing a misleading name. Renaming it to `viewerId` costs nothing and removes a genuine source of confusion about whether this endpoint has an authorization check.

## Why it matters

This is not exploitable today. `isAdmin` grants nothing because nothing reads it. That is why the rank is 4.

The reasons it is still worth acting on:

1. **It is exposed publicly right now.** `GET /api/v1/users/profile/:userId` is unauthenticated and returns the whole document minus password and refresh token (see `08.user-object-overexposure.md`). So `isAdmin`, `isSuspended`, and `suspensionReason` are world-readable. Publishing "here is which account is the admin" is free reconnaissance, and `suspensionReason`, a moderator's free-text note about a user, being public is a problem the moment it is ever populated.

2. **Half-built authorization reads as real authorization.** Someone reviewing this schema, including you in six months, will reasonably assume there is an admin system. The failure mode is writing a feature that trusts `isAdmin` without checking whether anything validates it, and the first such feature ships a privilege-escalation bug, because `isAdmin` sits on a schema whose other fields are freely updatable.

3. **The update paths are close to it.** `newUsernameUpdate.ts` does `User.findByIdAndUpdate(req.user._id, { $set: { username } })` with `username` taken raw from the body (see `12.nosql-operator-injection.md`). It is one careless refactor, `$set: req.body`, from being a self-service admin promotion. Every field on the user document that grants privilege is a field that mass-assignment can reach.

You have already indicated these should be treated as dead fields, so the recommendation below is removal.

## The fix

### Remove the unused fields

```ts
// server/src/models/user.model.ts
const schema = {
  username:      { type: String, required: true, unique: true, trim: true, index: true },
  email:         { type: String, required: true, unique: true, lowercase: true, trim: true },
  fullname:      { type: String, required: true, trim: true, index: true },
  avatar:        { type: String },
  coverImage:    { type: String },
  watchHistory:  [{ type: mongoose.Schema.Types.ObjectId, ref: "Video" }],
  password:      { type: String, required: [true, "PASSWORD IS REQUIRED"] },
  refreshToken:  { type: String, default: "" },
  avatarPublicId:      { type: String },
  CoverImagePublicId:  { type: String },

  isDeactivated: { type: Boolean, default: false },
  isSuspended:   { type: Boolean, default: false },

  // removed: isAdmin, suspensionStart, suspensionEnd, suspensionReason, suspendedBy
};
```

**Keep `isSuspended`.** Five call sites already read it: `loginUser.ts:38`, `refreshAccessToken.ts:42`, and the `$match` filters in `searchUserText`, `homepage`, `getUserChannelProfile`, and `feed`. Removing the boolean would silently disable those guards, and `17.auth-middleware-ignores-account-status.md` adds another reader. It is a working kill switch you can set manually in the database; that is genuinely useful even without a UI.

**Keep `isDeactivated`.** Fully implemented and user-facing.

**Remove the rest.** `isAdmin` grants nothing and advertises a target. The four `suspension*` detail fields are metadata for a workflow that does not exist.

### Clean up the type definitions

`server/src/constants/ModelTypes.ts` declares `UserThisType`. Remove the corresponding properties there, then run `npx tsc --noEmit` in `server/`, and any remaining reference becomes a compile error.

### Backfill existing documents

Removing fields from a Mongoose schema does not remove them from stored documents. Mongoose will simply ignore them on read, but they remain in the database and will still be returned by any aggregation using `$project` with explicit inclusion, or by `.lean()` queries. Clean them up:

```js
// run once in mongosh
db.users.updateMany({}, {
  $unset: {
    isAdmin: "",
    suspensionStart: "",
    suspensionEnd: "",
    suspensionReason: "",
    suspendedBy: "",
  }
});
```

### Rename the misleading parameter

```ts
// server/src/controllers/userControllers/getUserChannelProfile.ts
const viewerId = req.query.viewerId as string;   // was: adminId
```

Update the client caller in `client/src/hooks/data-fetching/useFetchUserChannelProfile.ts`. Better still, drop the query parameter entirely and read `req.user?._id`, see `suggestions/05.optional-auth-middleware.md`, which removes this whole pattern.

### If you build admin features later

Do not reintroduce a boolean on the user document. Use a separate collection:

```ts
// server/src/models/role.model.ts
const roleSchema = new mongoose.Schema({
  user: { type: Schema.Types.ObjectId, ref: "User", required: true, index: true },
  role: { type: String, enum: ["admin", "moderator"], required: true },
  grantedBy: { type: Schema.Types.ObjectId, ref: "User", required: true },
  grantedAt: { type: Date, default: Date.now },
}, { timestamps: true });

roleSchema.index({ user: 1, role: 1 }, { unique: true });
```

Three properties this gets you that a boolean does not: privilege cannot be reached by mass assignment on the user document; granting is auditable (who, when); and adding a third role does not require a schema migration.
