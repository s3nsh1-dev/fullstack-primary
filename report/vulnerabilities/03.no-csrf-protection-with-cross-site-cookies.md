# 03. No CSRF protection, with cookies configured to be sent cross-site

- **Rank: 8 / 10**
- **Side: Both (server sets the policy, client must send the token)**
- **Category:** Cross-Site Request Forgery
- **Location:** `server/src/constants.ts:7-12`, `server/src/app.ts:34-51`

## The issue

Authentication is cookie-based, and in production the cookies are explicitly configured to be sent on cross-site requests:

```ts
// server/src/constants.ts
export const httpOptions: CookieOptions = {
  httpOnly: true,
  secure: env.NODE_ENV === "production",
  sameSite: env.NODE_ENV === "production" ? "none" : "lax",
  path: "/",
};
```

`sameSite: "none"` is *necessary* here — your client and API are on different origins, so `Lax` would break the app. But it is also the setting that makes CSRF possible, and nothing anywhere in the codebase compensates for it. There is no CSRF token, no origin check on state-changing routes, no custom-header requirement.

## Why CORS does not protect you

This is the part that is easy to get wrong, so it is worth being precise.

The CORS config in `app.ts` restricts which origins may **read a response**. It does not restrict which origins may **send a request**. For "simple requests" the browser dispatches the request, attaches the cookies, the server executes it, and only then does the browser refuse to hand the response body back to the attacker's JavaScript. The side effect has already happened.

A request is "simple" (no preflight) when it is `GET`, `HEAD`, or `POST` with a `Content-Type` of `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`. Your server accepts two of those three:

```ts
app.use(express.urlencoded({ extended: true, limit: "16kb" }));   // app.ts:48
```

plus `multipart/form-data` via multer on the upload routes. So an attacker page needs no JavaScript at all — a plain auto-submitting HTML form is enough.

## Exploit

Any `POST` route reachable with `verifyJWT` is exposed. Concretely, from `server/src/routes/`:

| Route | Effect when forged |
| --- | --- |
| `POST /api/v1/tweets` | Post arbitrary content as the victim |
| `POST /api/v1/comments/v/:videoId` | Comment as the victim on any video |
| `POST /api/v1/likes/toggle/v/:videoId` | Like/unlike as the victim |
| `POST /api/v1/subscriptions/c/:channelId` | Subscribe the victim to a channel |
| `POST /api/v1/users/logout` | Force-log-out the victim (nuisance/denial) |
| `POST /api/v1/videos` | Upload a video to the victim's channel (multipart is simple) |

A working proof of concept for the tweet case — the victim only has to load the page while logged in:

```html
<!-- attacker.example/page.html -->
<form id="f" action="https://your-api.example/api/v1/tweets" method="POST"
      enctype="application/x-www-form-urlencoded">
  <input type="hidden" name="content" value="follow @attacker for free crypto">
</form>
<script>document.getElementById('f').submit();</script>
```

The browser attaches `accessToken` because `SameSite=None`. Express parses the urlencoded body into `req.body.content`. `createTweet` (`server/src/controllers/tweetControllers/createTweet.ts:9-17`) reads `req.body.content` and writes it with `owner: req.user._id`. The tweet is published. The attacker never sees the response and does not need to.

`PATCH` and `DELETE` routes (update-account, deactivate, delete video, update playlist) *are* preflighted and therefore protected by CORS today. That is luck, not design — it depends on nobody ever changing a route from `PATCH` to `POST`. Note that `userRouter.route("/delete-user").post(...)` at `server/src/routes/user.routes.ts:57` is exactly such a route, with a comment saying it should become `DELETE` later.

## Why this is 8 and not 10

Rank reflects that the highest-value actions are currently not reachable this way:

- `POST /users/change-password` requires `currentPassword`, which the attacker does not have.
- `POST /users/delete-user` is a no-op (see `06.account-deletion-is-a-noop.md`) so forging it does nothing — today.
- Account takeover via email change goes through `PATCH /users/update-account`, which is preflighted.

So the realistic impact is forged content, forged social graph edges, forced logout, and unwanted uploads under the victim's identity — reputational and integrity damage rather than takeover. Both of the mitigating factors above are accidents that a routine refactor would remove.

## The fix

Use the **double-submit cookie** pattern. It is stateless, it works across origins, and it does not require server-side session storage — which fits your JWT-cookie design.

### Server

```ts
// server/src/middleware/csrf.middleware.ts
import crypto from "crypto";
import type { Request, Response, NextFunction } from "express";
import ApiError from "../utils/ApiError";
import { env } from "../config/env";

const CSRF_COOKIE = "csrfToken";
const CSRF_HEADER = "x-csrf-token";
const SAFE_METHODS = new Set(["GET", "HEAD", "OPTIONS"]);

/** Issue a CSRF token cookie. Readable by JS on purpose — httpOnly must be false. */
export const issueCsrfToken = (res: Response): string => {
  const token = crypto.randomBytes(32).toString("hex");
  res.cookie(CSRF_COOKIE, token, {
    httpOnly: false,             // the client must read this to echo it back
    secure: env.NODE_ENV === "production",
    sameSite: env.NODE_ENV === "production" ? "none" : "lax",
    path: "/",
  });
  return token;
};

export const verifyCsrf = (req: Request, _res: Response, next: NextFunction) => {
  if (SAFE_METHODS.has(req.method)) return next();

  const cookieToken = req.cookies?.[CSRF_COOKIE];
  const headerToken = req.get(CSRF_HEADER);

  if (!cookieToken || !headerToken) {
    throw new ApiError(403, "CSRF TOKEN MISSING");
  }

  const a = Buffer.from(cookieToken);
  const b = Buffer.from(headerToken);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    throw new ApiError(403, "CSRF TOKEN INVALID");
  }
  next();
};
```

Wire it in `app.ts` after `cookieParser()` and before the routers:

```ts
app.use(cookieParser());
app.use(verifyCsrf);
```

Call `issueCsrfToken(res)` alongside the auth cookies in `loginUser`, `refreshAccessToken`, and the new `GET /users/me` bootstrap endpoint.

The security property: an attacker's page can cause the browser to *send* the `csrfToken` cookie, but same-origin policy prevents it from *reading* that cookie's value, so it cannot populate the `x-csrf-token` header. And setting a custom header forces a CORS preflight, which your origin allowlist rejects.

### Client

This is why the fix is "both sides". Every mutating call must echo the token. Doing this in 20+ hand-written `fetch`/`axios` blocks is how you end up with three routes that forgot. Add it once in the shared client instead — see `suggestions/06.single-http-client-with-interceptors.md`:

```ts
// client/src/lib/apiClient.ts
const readCookie = (name: string): string | undefined =>
  document.cookie.split("; ").find((c) => c.startsWith(`${name}=`))?.split("=")[1];

apiClient.interceptors.request.use((config) => {
  const method = (config.method ?? "get").toUpperCase();
  if (!["GET", "HEAD", "OPTIONS"].includes(method)) {
    const token = readCookie("csrfToken");
    if (token) config.headers["x-csrf-token"] = token;
  }
  return config;
});
```

You also need `x-csrf-token` added to the CORS `allowedHeaders` list in `app.ts:45`, which currently only permits `Content-Type` and `Authorization`.

### A cheaper interim mitigation

If you want something in place today, add an Origin check. It is weaker (it trusts a header the browser controls, and it has an awkward blind spot for requests with no `Origin`), but it is ten lines:

```ts
app.use((req, _res, next) => {
  if (SAFE_METHODS.has(req.method)) return next();
  const origin = req.get("origin");
  if (!origin || !allowedOrigins.includes(origin)) {
    throw new ApiError(403, "CROSS-ORIGIN REQUEST REJECTED");
  }
  next();
});
```

Note this rejects requests with no `Origin` header, which is the *opposite* of what `app.ts:40` does today — see `18.cors-allows-requests-with-no-origin.md`. Pick one behaviour and apply it consistently.

## Interaction with other documents

- Requires `suggestions/06.single-http-client-with-interceptors.md` on the client. Applying the CSRF header by hand across the existing 20 axios calls and 20 fetch calls is the failure mode this fix must avoid.
- `18.cors-allows-requests-with-no-origin.md` must be resolved *before* or *with* this, because the two documents both decide what happens to an `Origin`-less request. The agreed resolution: reject `Origin`-less **mutating** requests, allow `Origin`-less **safe** requests.
- Does **not** conflict with `16.tokens-returned-in-response-body.md`. That document removes tokens from the JSON body and keeps them cookie-only, which *increases* reliance on cookies and therefore makes this CSRF fix more important, not less.
- `suggestions/03.security-middleware-baseline.md` lists this middleware in the recommended `app.ts` ordering.
