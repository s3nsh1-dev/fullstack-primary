# 09. Every user's email address is readable without authentication

- **Rank: 7 / 10**
- **Side: Server**
- **Category:** PII exposure
- **Location:** five controllers, listed below

## The issue

Five separate unauthenticated endpoints project the `email` field into their responses.

### 1. Search: the worst one

```ts
// server/src/controllers/searchUserText.controller.ts:24-28
User.find({
  $or: [{ username: regex }, { fullname: regex }],
  isDeactivated: false,
  isSuspended: false,
}).select("username fullname avatar email createdAt"),
```

Route: `GET /api/v1/search/q/:searchText`, no `verifyJWT` (`searchUserText.route.ts:6`).

This one is qualitatively worse than the others because it is a **bulk** endpoint with **no result limit** (see `13.unbounded-pagination-and-unpaginated-search.md`). The regex is built from the path parameter, so:

```bash
curl "https://your-api.example/api/v1/search/q/a"
```

returns every user whose username or full name contains the letter "a", each with their email address. Twenty-six requests, `a` through `z`, dump essentially your entire user table. Loop over two-letter combinations and you have all of it, deduplicated, with names attached.

### 2. Homepage

```ts
// server/src/controllers/homepage.controller.ts:21-33
$project: { _id: 1, username: 1, email: 1, fullname: 1, avatar: 1, ... }
```

Route: `GET /api/v1/homepage/:username`, no auth (`homepage.route.ts:6`).

### 3. Channel profile

```ts
// server/src/controllers/userControllers/getUserChannelProfile.ts:79-89
$project: { fullname: 1, username: 1, email: 1, avatar: 1, coverImage: 1, ... }
```

Route: `GET /api/v1/users/channel/:username`, no auth (`user.routes.ts:51`).

### 4. Single tweet

```ts
// server/src/controllers/tweetControllers/fetchTweet.ts:17-20
const tweet = await Tweet.findById(tweetId).populate({
  path: "owner",
  select: "username fullname avatar email coverImage",
});
```

Route: `GET /api/v1/tweets/:tweetId`, no auth (`tweet.route.ts:19`).

### 5. Profile by ID

`GET /api/v1/users/profile/:userId`, covered in detail in `08.user-object-overexposure.md`, which leaks `email` along with `watchHistory` and the moderation fields.

## Why it matters

An email address is the primary identifier for account recovery, the primary target for phishing, and, critically, the join key that links your users to breach data from other services.

Concretely:

- **Credential stuffing.** Take the harvested email list, check it against public breach corpora, and try any recovered password against `POST /users/login`. With no rate limiting (`05.no-rate-limiting-on-any-endpoint.md`) and no password policy (`14.weak-registration-validation.md`), a non-trivial fraction will work.
- **Targeted phishing.** The attacker now has `{email, fullname, username, avatar}` for each user. That is enough to send a convincing "your PlayTube account has been suspended, click here" message. The `avatar` URL even lets them render the victim's own photo in the email.
- **Deanonymisation.** Users choose pseudonymous usernames deliberately. Publishing the email next to the pseudonym destroys that separation. Someone who picked a handle specifically to keep their real identity out of it has been outed by an endpoint they never interacted with.
- **Scraping is cheap and undetectable.** No auth means no account to ban, and with no rate limit there is nothing in the logs to distinguish the scrape from normal traffic.

None of these endpoints has a legitimate need for `email`. I checked the consumers:

- `client/src/components/search/UserSearchCard.tsx` and `SearchResultUser.tsx` render username, fullname, avatar.
- `client/src/components/homepage/HomeUserDetails.tsx` renders the profile header.
- `client/src/components/Tweets/ContentProfileHeader.tsx` renders the tweet author.

None display the email. It is being fetched and shipped over the wire for no reason at all, which is the good news, because removing it breaks nothing.

## The fix

Define the projection once and apply it in all five places:

```ts
// server/src/constants/projections.ts
export const PUBLIC_USER_FIELDS = "_id username fullname avatar coverImage createdAt";

/** Aggregation-pipeline form of the same shape. */
export const PUBLIC_USER_PROJECTION = {
  _id: 1, username: 1, fullname: 1, avatar: 1, coverImage: 1, createdAt: 1,
} as const;
```

Then:

```ts
// searchUserText.controller.ts
User.find({ ... }).select(PUBLIC_USER_FIELDS).limit(20),

// homepage.controller.ts
{ $project: { ...PUBLIC_USER_PROJECTION, subscribers: 1, videos: 1, tweets: 1, playlists: 1 } }

// getUserChannelProfile.ts
{ $project: { ...PUBLIC_USER_PROJECTION, mySubCount: 1, meSubbingCount: 1, isSubbed: 1 } }

// fetchTweet.ts
.populate({ path: "owner", select: PUBLIC_USER_FIELDS })
```

The one endpoint that legitimately returns the caller's own email is `GET /users/current-user`, which is authenticated and returns `req.user`. Use `PRIVATE_USER_FIELDS` there (defined in document 08).

### Verify nothing else leaks it

```bash
cd server
grep -rn "email" src/controllers/ | grep -E "select|project"
```

Re-run this after the fix. It should return only the authenticated self-lookup paths.

### Also check the client's types

`client/src/constants/dataTypes.ts` and `responseTypes.ts` likely declare `email` on the public user shapes. Removing it there turns any remaining consumer into a compile error, which is how you confirm nothing depended on it.

## A note on `normalizeEmail()`

Unrelated to exposure, but in the same area and worth fixing while you are here: `server/src/routes/contact.route.ts:18` applies express-validator's `.normalizeEmail()` to the contact form address. That transform strips dots and `+tags` from Gmail addresses, so `john.doe+playtube@gmail.com` becomes `johndoe@gmail.com`. It is then used as the `reply_to` on the outbound email. For a contact form this silently rewrites the address you reply to. `.normalizeEmail()` is meant for deduplicating signups, not for preserving a contact address. Drop it here.

## Interaction with other documents

- `08.user-object-overexposure.md` defines `PUBLIC_USER_FIELDS` / `PRIVATE_USER_FIELDS`. **These two documents share one fix**. Implement the projections module once and both close together.
- `13.unbounded-pagination-and-unpaginated-search.md` adds the `.limit(20)` shown above. Without it, removing `email` still leaves an endpoint that returns your entire user table in one response.
- `05.no-rate-limiting-on-any-endpoint.md`. Rate limiting makes bulk scraping slow; removing the field makes it worthless. Do both; the field removal is the one that actually matters.
- `07.unauthenticated-write-to-any-users-watch-history.md` relies on the same endpoints to harvest user IDs. Note that `_id` **stays** in `PUBLIC_USER_FIELDS`, since the client needs it for routing and it is not secret. Fixing document 07 properly (auth on the route) is what closes that, not hiding IDs.
