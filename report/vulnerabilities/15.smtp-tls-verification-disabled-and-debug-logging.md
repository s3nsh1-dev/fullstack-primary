# 15. SMTP certificate verification disabled, with full protocol debug logging

- **Rank: 6 / 10**
- **Side: Server**
- **Category:** Improper certificate validation / credential exposure in logs
- **Location:** `server/src/services/mail.service.ts:8-28`

## The issue

```ts
this.transporter = nodemailer.createTransport({
  port: env.GMAIL_SMTP_PORT,
  host: env.GMAIL_SMTP_HOST,
  secure: env.GMAIL_SMTP_SECURE,
  requireTLS: !env.GMAIL_SMTP_SECURE,
  auth: {
    user: env.GMAIL_AUTH_USER_PROVIDER,
    pass: env.GMAIL_PASSWORD,
  },
  ...
  tls: {
    rejectUnauthorized: false,          // (1)
    checkServerIdentity: () => undefined,  // (2)
  },
  logger: true,                          // (3)
  debug: true,                           // (3)
} as any);
```

Four separate problems in one object literal.

**(1) `rejectUnauthorized: false`** disables certificate chain validation. The client accepts self-signed certificates, expired certificates, and certificates from any issuer.

**(2) `checkServerIdentity: () => undefined`** is the more consequential one. Returning `undefined` from this callback signals "identity verified". Node's default implementation checks that the certificate's subject/SAN actually matches the hostname you dialled. Overriding it means the client accepts a *valid, correctly signed* certificate issued for **any** domain. Together, (1) and (2) remove every guarantee TLS provides. The connection is encrypted but unauthenticated, which is precisely the condition a man-in-the-middle needs.

**(3) `logger: true, debug: true`** makes Nodemailer log the full SMTP conversation, which includes the `AUTH LOGIN` exchange. The credential is base64-encoded in the protocol, not encrypted, and base64 is an encoding rather than a cipher. So your Gmail App Password is printed to stdout on every connection, captured by whatever collects your process output.

**(4) `as any`** on the config object suppresses the TypeScript error that would have flagged `checkServerIdentity`'s signature mismatch. It is why none of this was caught at compile time.

## Why it matters

An attacker positioned on the network path can transparently intercept the SMTP session: a hostile Wi-Fi network, a compromised upstream router, a DNS hijack, or a malicious sidecar in a shared hosting environment. They present any certificate they like, the client accepts it, and the first thing the client sends is `AUTH LOGIN` with your Gmail App Password.

A Gmail App Password is not scoped to sending. It grants **full IMAP/SMTP access to the mailbox**. An attacker who captures it can read every email in the account, send mail as you, and, because email is the recovery channel for essentially every other service, pivot into password resets on your other accounts. This is one of the highest-value credentials in the whole system, and it is being transmitted over a connection with authentication deliberately switched off.

Problem (3) is a separate leak that does not require a network position: it puts the same credential in your logs. `logger: true` writes to the console, which on Render/Railway/Fly goes to the platform's log dashboard and any attached aggregator. This is the same class of failure as `02.plaintext-passwords-written-to-logs.md`, in a different component.

## Mitigating context

Rank 6 rather than 8 because of one thing: `mail.service.ts` **is not currently used**. `contact.controller.ts:5` imports from `mailHttp.service` instead:

```ts
import { ContactFormData, mailService } from "../services/mailHttp.service";
```

The HTTP service (`mailHttp.service.ts`) calls the Resend API over `fetch` with normal TLS validation, and does not enable debug logging. It is the safe path, and it is the one in use.

So this is dormant code. It is still ranked at 6 because:

- The file is present, exported, and importable. Changing one import line reactivates it.
- `server/.env` still contains `GMAIL_PASSWORD`, so the credential exists and is loaded into `env` at boot regardless of which service is used.
- `client/fullstack-primary-extraFiles/render-email-issue.md` documents the SMTP-to-HTTP migration, which means the SMTP path was live at some point. If it ran in production, the App Password should be treated as already exposed.

## The fix

### If you are keeping the SMTP path

```ts
this.transporter = nodemailer.createTransport({
  host: env.GMAIL_SMTP_HOST,
  port: env.GMAIL_SMTP_PORT,
  secure: env.GMAIL_SMTP_PORT === 465,   // implicit TLS on 465, STARTTLS on 587
  requireTLS: env.GMAIL_SMTP_PORT !== 465,
  auth: { user: env.GMAIL_AUTH_USER_PROVIDER, pass: env.GMAIL_PASSWORD },
  connectionTimeout: 30_000,
  greetingTimeout: 30_000,
  socketTimeout: 30_000,
  family: 4,
  // no `tls` override at all — Node's defaults are correct
  logger: false,
  debug: false,
});
```

Deleting the `tls` block entirely is the fix. Node's TLS defaults verify the chain and the hostname, which is what you want against `smtp.gmail.com`. And with the block gone, the `as any` cast can go too, restoring type checking on this object.

The `family: 4` line should stay. The comment explains it, and IPv6 hangs on some hosts are a real problem.

### If you are not keeping it, delete the file

This is my recommendation. You have already migrated to the HTTP provider, the SMTP implementation is unused, and dead code with disabled certificate validation is a liability that will eventually be re-enabled by someone who does not know why it was abandoned.

```bash
cd server
rm src/services/mail.service.ts
grep -rn "mail.service" src/          # confirm nothing imports it
```

Then remove the now-unused variables from `dotenvHelper.ts` and `.env`: `GMAIL_SMTP_HOST`, `GMAIL_SMTP_PORT`, `GMAIL_SMTP_SECURE`, `GMAIL_PASSWORD`, `GMAIL_AUTH_USER_PROVIDER`. And **revoke the Gmail App Password** in your Google Account security settings. An unused credential that still works is a credential that can still be stolen. Revoking takes one click and costs nothing since nothing uses it.

`nodemailer` and `@types/nodemailer` can then come out of `package.json`.

### Either way: check the surviving service

`mailHttp.service.ts` is in better shape but has two issues worth noting:

- **Line 42** sends the API key in an `Authorization` header, correctly. But **line 49-53** logs the provider's error `body` verbatim on failure. Provider error responses can echo request details. Redact or truncate.
- **Line 66-71** catches everything and rethrows `ApiError(500, "Failed to send email")`, including the `ApiError(400, "Email provider not configured")` thrown at line 31. So a configuration error reports as a server fault. Rethrow `ApiError` instances unchanged, as `refreshAccessToken.ts:71-73` correctly does.

The identical bug exists one layer up in `contact.controller.ts:31-38`, where the `catch` swallows the `ApiError(400, "CONTACT FORM VALIDATION FAILED")` thrown at line 17 and converts it to `ApiError(500, "CAN NOT CONNECT TO MAIL SERVER")`. So **every validation failure on the contact form is reported to the user as a mail-server outage.** That is a live user-facing bug on the path that is actually in use:

```ts
} catch (error) {
  if (error instanceof ApiError) throw error;   // add this line
  logService.error("Error submitting contact form", { ... });
  throw new ApiError(500, "CAN NOT CONNECT TO MAIL SERVER");
}
```
