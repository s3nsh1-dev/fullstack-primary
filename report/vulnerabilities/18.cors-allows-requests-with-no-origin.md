# 18. CORS allows credentialed requests with no Origin header

- **Rank: 4 / 10**
- **Side: Server**
- **Category:** Permissive CORS configuration
- **Location:** `server/src/app.ts:26-47`

## The issue

```ts
const allowedOrigins = (env.CORS_ORIGIN ? env.CORS_ORIGIN.split(",") : [])
  .map((cors) => cors.trim())
  .filter(Boolean);
if (allowedOrigins.length < 1) {
  throw new ApiError(400, "CORS_ORIGIN is not defined");
}

app.use(cors({
  origin: (origin, callback) => {
    if (!origin) return callback(null, true);          // <-- here
    return callback(null, allowedOrigins.includes(origin));
  },
  credentials: true,
  methods: ["GET", "POST", "PUT", "DELETE", "PATCH"],
  allowedHeaders: ["Content-Type", "Authorization"],
}));
```

The allowlist itself is correct: exact string matching against a configured list, no wildcard, no `startsWith`, no regex. That is the right shape and better than most hand-rolled CORS configs.

The problem is line 40: a request with no `Origin` header is unconditionally allowed, with `credentials: true`.

## Why it matters, and why the rank is 4

`if (!origin) return callback(null, true)` is a very common idiom, and it is usually described as harmless because browsers always send `Origin` on cross-origin requests. That is mostly true, and it is why this is ranked 4 rather than higher. Non-browser clients (curl, Postman, server-to-server) send no `Origin` and also carry no ambient cookies, so allowing them changes nothing about a browser-based attack.

The reasons it is still worth fixing:

1. **It contradicts the CSRF mitigation you need.** The standard cheap defence against the CSRF problem in `03.no-csrf-protection-with-cross-site-cookies.md` is an origin check on mutating requests. That defence is exactly inverted by this line. If you implement an `Origin`-based CSRF guard while `app.ts` also has "no origin means allow", the two policies disagree and the weaker one wins.

2. **Browsers do omit `Origin` in some cases.** Same-origin `GET`/`HEAD` requests omit it. More relevantly, some navigation and redirect flows produce requests where `Origin` is absent or `null`. An `<iframe sandbox>` without `allow-same-origin` sends `Origin: null`, and certain redirect chains strip it. Note that `Origin: null` is a *present* header with the value `"null"`, so it hits the allowlist branch and is correctly rejected. Genuinely absent `Origin` is the case being waved through.

3. **`credentials: true` raises the stakes.** With credentials enabled, "allow" means "allow, and reflect the origin, and permit cookies". The combination is what makes a permissive branch here worth scrutinising rather than shrugging at.

## Secondary issue: the misconfiguration is not caught

`dotenvHelper.ts:42` defaults `CORS_ORIGIN` to `"*"`. The guard on line 29 checks `allowedOrigins.length < 1`, and `"*".split(",")` yields `["*"]`, which has length 1. So the guard passes, and the app boots with an allowlist containing the literal string `"*"`, which matches no real origin. Every browser request from your frontend then fails CORS with no error on the server side.

This is an outage, not a breach, but it is a silent one: the server logs nothing, the health check passes, and the failure appears only in the user's browser console. See `01.hardcoded-fallback-jwt-secrets.md` for the general form of this problem.

There is also a `throw` at module scope (line 30), outside any request handler. `ApiError` extends `Error`, so this crashes the process at import time with an unhandled exception rather than a readable startup message. That is arguably the correct outcome, failing fast, but it should be a plain descriptive `Error`, not an HTTP-shaped one.

## The fix

```ts
// server/src/config/cors.ts
import cors from "cors";
import { env } from "./env";

const allowedOrigins = env.CORS_ORIGIN.split(",")
  .map((o) => o.trim())
  .filter(Boolean);

if (allowedOrigins.length === 0 || allowedOrigins.includes("*")) {
  throw new Error(
    "FATAL: CORS_ORIGIN must be a comma-separated list of explicit origins. " +
    `Wildcards are not permitted with credentials. Received: "${env.CORS_ORIGIN}"`
  );
}

export const corsOptions: cors.CorsOptions = {
  origin: (origin, callback) => {
    // Requests with no Origin are non-browser clients (curl, health checks,
    // server-to-server). They carry no ambient cookies, so CORS is not the
    // control that matters for them — but they must not be treated as
    // same-origin either. Allow them here, and let the CSRF middleware
    // reject Origin-less *mutating* requests.
    if (!origin) return callback(null, true);
    if (allowedOrigins.includes(origin)) return callback(null, true);
    return callback(null, false);
  },
  credentials: true,
  methods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
  allowedHeaders: ["Content-Type", "Authorization", "X-CSRF-Token"],
  maxAge: 86400,
};
```

Changes:

- **`"*"` is rejected at boot** with a message that says what to do. This is the fix for the silent-misconfiguration half.
- **`OPTIONS` added to `methods`.** The `cors` package handles preflight itself so this is not strictly required, but the omission is confusing to read.
- **`X-CSRF-Token` added to `allowedHeaders`.** Required by `03.no-csrf-protection-with-cross-site-cookies.md`. Without it, the browser's preflight rejects the header and every mutating request fails. Easy to forget and produces a confusing failure.
- **`maxAge: 86400`** caches preflight results for a day, removing an extra round trip before every `PATCH`/`DELETE`.
- **The `!origin` branch is kept, deliberately, with a comment explaining why**, and the actual protection moves to the CSRF middleware which rejects `Origin`-less mutating requests.

That last point is the important one. This document and document 03 both have an opinion about `Origin`-less requests, and they must not disagree. The agreed division:

| | CORS layer | CSRF layer |
| --- | --- | --- |
| `GET`/`HEAD`/`OPTIONS`, no `Origin` | allow | allow |
| `POST`/`PATCH`/`DELETE`, no `Origin` | allow | **reject** |
| Any method, `Origin` not in allowlist | reject | reject |

Putting the rejection in the CSRF layer rather than the CORS layer keeps `GET /api/v1/health` reachable from an uptime monitor while still blocking forged writes.

### Verify after deploying

```bash
# should succeed
curl -i -H "Origin: https://your-frontend.example" https://your-api.example/api/v1/health

# should NOT include Access-Control-Allow-Origin
curl -i -H "Origin: https://evil.example" https://your-api.example/api/v1/health

# preflight should list your headers
curl -i -X OPTIONS \
  -H "Origin: https://your-frontend.example" \
  -H "Access-Control-Request-Method: PATCH" \
  -H "Access-Control-Request-Headers: x-csrf-token" \
  https://your-api.example/api/v1/users/update-account
```

## Interaction with other documents

- **`03.no-csrf-protection-with-cross-site-cookies.md` is the controlling document.** The `allowedHeaders` entry and the `Origin`-less policy split above are both requirements from it. Read the two together; implementing this one alone leaves the CSRF hole open, and implementing that one without adding `X-CSRF-Token` here breaks every write.
- `01.hardcoded-fallback-jwt-secrets.md`. The `"*"` default that this document's boot guard catches originates there. `suggestions/01.fail-fast-env-config.md` removes the default entirely, which makes the guard here redundant but harmless. Keep both; defence in depth on a config value costs nothing.
- `suggestions/03.security-middleware-baseline.md` specifies where `cors` sits relative to `helmet`, the rate limiter, and the CSRF middleware. Order matters. CORS must precede the CSRF check so preflights are answered before the token requirement applies.
