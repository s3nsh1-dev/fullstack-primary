# 14. No password policy and unsafe input handling on registration

- **Rank: 6 / 10**
- **Side: Both (server enforces nothing, client enforces nothing)**
- **Category:** Weak credential policy / unhandled input types
- **Location:** `server/src/controllers/userControllers/registerUser.ts:8-17`, `server/src/controllers/userControllers/changeCurrentPassword.ts:8-14`, `client/src/components/RegisterForm.tsx`

## The issue

### No password policy anywhere

Registration:

```ts
const { fullname, email, username, password } = req.body;
if ([fullname, email, username, password].some((field) => field.trim() === "")) {
  throw new ApiError(400, "INCOMPLETE INPUT FIELDS BY USER");
}
```

Password change:

```ts
if (!currentPassword || !newPassword || currentPassword.length < 1 || newPassword.length < 1)
  throw new ApiError(400, " CURRENT PASSWORD AND NEW PASSWORD ARE REQUIRED");
```

The only requirement, in both places, is **non-empty**. `"a"` is a valid password. The `user.model.ts` schema declares `password: { type: String, required: [true, "PASSWORD IN REQUIRED"] }` with no `minlength`.

The client does not compensate — `RegisterForm.tsx` renders `<FormInput type="password" ... required />` with no `minLength`, no pattern, and no validation in `handleSubmit`.

### `.trim()` on possibly-undefined values

`registerUser` calls `field.trim()` on each of the four fields before checking they exist. Omit `fullname` from the request and `undefined.trim()` throws a `TypeError`, which `asyncHandler` forwards to the error middleware, which classifies it as a generic error and returns **500 INTERNAL SERVER ERROR** for what is plainly a client mistake.

Send `{"password": 12345}` and `.trim()` is not a function on a number — same 500.

This is also the trigger for the orphaned-upload path described in `04.unauthenticated-file-upload-to-public-directory.md`: multer has already written the files to disk when this throws, and nothing cleans them up.

### The duplicate check is wrong

```ts
const exitedUser = await User.findOne({ $or: [{ username, email }] });
```

`$or` takes an array of conditions. This passes an array containing **one** object with two keys, which means "username matches AND email matches" — not "either matches". So a registration reusing an existing username with a different email passes this check.

It is then caught by the unique index on `username`, surfacing as a Mongo `E11000` handled by `handleMongooseDuplicateKeyError` (`error.middleware.ts:56-66`), which returns 409 with the message `username 'taken_name' already exists`. The end state is correct, but by accident, and via an error path that echoes the submitted value back.

There is a real consequence: because the check fails, the code proceeds to **upload both images to Cloudinary** before hitting the index violation. Every duplicate-username attempt costs you a Cloudinary upload and leaves the asset orphaned there — no cleanup runs on that path.

### No email verification

`email` is stored as submitted. Nothing confirms the address belongs to the registrant. Anyone can register with anyone's email. This matters more later than now: it means you cannot safely build a password-reset flow, because the addresses in your database are unverified claims.

### Fullname is unvalidated at registration but strict on update

`registerUser` accepts any `fullname`. But `updateAccountDetails.ts:66` validates it against `/^[A-Za-z\s]+$/`. So a name accepted at signup can be rejected when the user later edits their profile — including names with apostrophes, hyphens, or any non-ASCII letters. That regex is also too strict to be correct: it rejects `O'Brien`, `Jean-Luc`, `Müller`, and every name not written in the Latin alphabet.

## Why it matters

The password policy is the load-bearing item. Combined with:

- no rate limiting on login (`05.no-rate-limiting-on-any-endpoint.md`),
- a username/email oracle (same document, plus `09.email-addresses-exposed-on-public-endpoints.md`),

...an account with a two-character password is not a hypothetical weakness, it is an open door. bcrypt at cost 10 protects the hash if your database leaks; it does nothing against online guessing of a password that is in the top 100 list.

The 500s are lower impact but they are unauthenticated, trivially triggered, and they pollute `error.log` with stack traces while masking real failures.

## The fix

### Server: a real policy, applied in both places

```ts
// server/src/utils/passwordPolicy.ts
const MIN = 10;
const MAX = 128;

// A small embedded list; for production use the `zxcvbn` package instead.
const COMMON = new Set([
  "password", "12345678", "qwertyui", "letmein", "iloveyou",
  "admin123", "welcome1", "password1", "123456789", "qwerty123",
]);

export const assertStrongPassword = (password: unknown): string => {
  if (typeof password !== "string") throw new ApiError(400, "PASSWORD MUST BE A STRING");
  if (password.length < MIN) throw new ApiError(400, `PASSWORD MUST BE AT LEAST ${MIN} CHARACTERS`);
  if (password.length > MAX) throw new ApiError(400, `PASSWORD MUST BE AT MOST ${MAX} CHARACTERS`);
  if (COMMON.has(password.toLowerCase())) throw new ApiError(400, "PASSWORD IS TOO COMMON");
  return password;
};
```

A note on the design: **length is the requirement, not character classes.** Mandating "one uppercase, one digit, one symbol" reliably produces `Password1!` and nothing better. NIST SP 800-63B dropped composition rules for this reason and recommends a length floor plus a breached-password check. The `MAX` of 128 exists because bcrypt silently truncates input beyond 72 bytes — without an explicit cap, two different long passwords can hash identically.

Apply it in `registerUser` **and** in `changeCurrentPassword`. Missing the second is the common mistake, and it makes the first pointless.

### Server: fix the input handling

```ts
// server/src/controllers/userControllers/registerUser.ts
const str = (v: unknown) => (typeof v === "string" ? v.trim() : "");

const fullname = str(req.body.fullname);
const email    = str(req.body.email).toLowerCase();
const username = str(req.body.username).toLowerCase();
const password = assertStrongPassword(req.body.password);

if (!fullname || !email || !username) {
  throw new ApiError(400, "FULLNAME, EMAIL AND USERNAME ARE REQUIRED");
}
if (!/^[a-z0-9_]{3,20}$/.test(username)) {
  throw new ApiError(400, "USERNAME MUST BE 3-20 CHARACTERS: a-z, 0-9, UNDERSCORE");
}
if (!/^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/.test(email)) {
  throw new ApiError(400, "INVALID EMAIL ADDRESS");
}

// correct $or: either field colliding is a duplicate
const existing = await User.findOne({ $or: [{ username }, { email }] });
if (existing) throw new ApiError(409, "USERNAME OR EMAIL IS ALREADY REGISTERED");
```

Note the duplicate check now runs **before** the Cloudinary uploads — currently it runs first too, but because the `$or` is wrong it does not catch anything, so the uploads happen. Fixing the `$or` alone recovers that.

The 409 message deliberately does not say *which* field collided. Saying "email already registered" is an account-existence oracle. Whether you care depends on your threat model; `usernameAvailability` already gives away username existence by design, so the email is the one worth protecting.

The username rules here must match `newUsernameUpdate` — see `12.nosql-operator-injection.md`, which defines the same regex and the reserved-word list. **Put them in one shared module** rather than duplicating the literal.

### Relax the fullname regex

```ts
// updateAccountDetails.ts — replace /^[A-Za-z\s]+$/
fullname: {
  regex: /^[\p{L}\p{M}'\-. ]{1,80}$/u,
  cleaner: cleanFullname,
},
```

`\p{L}` matches letters in any script, `\p{M}` matches combining marks, and the `u` flag is required for both. This accepts `O'Brien`, `Jean-Luc`, `Müller`, `李雷`. Apply the same rule at registration so the two agree.

Also reconsider `cleanFullname` (`updateAccountDetails.ts:43-52`), which title-cases every word. It rewrites `van der Berg` to `Van Der Berg` and `McDonald` to `Mcdonald`. Store what the user typed.

### Client: validate before submitting

Server-side enforcement is what secures the system; client-side validation is what makes it usable. Without it the user submits, waits, and gets a generic failure — and `RegisterForm.tsx` has no `onError` handler at all, so the mutation failure is silent.

Two bugs in that component to fix at the same time:

```tsx
const handleSubmit = async (e: React.FormEvent) => {
  e.preventDefault();
  registerMutate.mutate(formData, {
    onSuccess: (data) => { login(data); },
  });
  setFormData(resetForm);        // <-- runs immediately, not on success
};
```

- `setFormData(resetForm)` is outside the callback, so the form is cleared even when registration **fails** — the user loses everything they typed and sees no error.
- There is no `onError`, so `useUserRegister`'s `throw new Error("USER REGISTRATION FAILED")` surfaces nowhere.

There is a third, more serious bug in the same three lines, covered separately in `suggestions/04.unify-auth-session-model.md`: `onSuccess` calls `login(data)` with the raw response envelope, and `registerUser` **does not set auth cookies**. So after registering the client believes it is logged in when it is not.

```tsx
const [error, setError] = useState<string | null>(null);

const handleSubmit = (e: React.FormEvent) => {
  e.preventDefault();
  setError(null);

  if (formData.password.length < 10) {
    setError("Password must be at least 10 characters");
    return;
  }
  if (!/^[a-z0-9_]{3,20}$/.test(formData.username.toLowerCase())) {
    setError("Username must be 3-20 characters: a-z, 0-9, underscore");
    return;
  }

  registerMutate.mutate(formData, {
    onSuccess: () => { setFormData(resetForm); /* then log in — see suggestions/04 */ },
    onError: (err: Error) => setError(err.message),
  });
};
```
