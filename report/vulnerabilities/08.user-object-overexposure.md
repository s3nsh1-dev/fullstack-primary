# 08. Full user document exposed to anonymous callers, including watch history

- **Rank: 7 / 10**
- **Side: Server**
- **Category:** Excessive data exposure / broken object-level authorization
- **Location:** `server/src/controllers/userControllers/fetchUserById.ts:13`, `server/src/routes/user.routes.ts:38`

## The issue

```ts
// server/src/routes/user.routes.ts:38  — note: above the "//secured routes" comment
userRouter.route("/profile/:userId").get(fetchUserById);
```

```ts
// server/src/controllers/userControllers/fetchUserById.ts
const user = await User.findById(userId).select("-password -refreshToken");
```

The endpoint is unauthenticated, and the projection is a **denylist**: it removes two fields and returns everything else. Every field added to `userSchema` in the future is exposed by default.

Against the current schema (`server/src/models/user.model.ts:8-54`), an anonymous `GET /api/v1/users/profile/<id>` returns:

| Field | Why it should not be public |
| --- | --- |
| `email` | Direct PII. Enables targeted phishing and credential stuffing. |
| `watchHistory` | Array of up to 50 video ObjectIds, a behavioural profile of what this person watched, in order. |
| `isAdmin` | Tells an attacker exactly which accounts are worth targeting. |
| `isSuspended`, `suspensionReason`, `suspensionStart`, `suspensionEnd`, `suspendedBy` | Moderation state. `suspensionReason` is free text written by a moderator about a user and is now world-readable. |
| `isDeactivated` | Reveals accounts the owner deliberately hid. |
| `avatarPublicId`, `CoverImagePublicId` | Internal Cloudinary identifiers. |
| `createdAt`, `updatedAt` | Minor, but `updatedAt` leaks activity timing. |

## Why it matters

`watchHistory` is the serious one. It is a per-person list of consumed content, exposed without any authentication, keyed by an ID that is handed out freely by other public endpoints (search results, the feed, homepage lookups; see `07.unauthenticated-write-to-any-users-watch-history.md` for the harvesting chain).

That is enough to enumerate every user via search and then pull a viewing profile for each one. Viewing history is treated as sensitive across every comparable platform, and for good reason: it reveals interests, and by extension things people do not choose to disclose. Combined with the `email` field in the same response, each record is directly attributable to a real person.

`isSuspended` and `suspensionReason` compound this. Publishing "this account was suspended, and here is the moderator's note explaining why" is a defamation surface as well as a privacy one.

`isAdmin` deserves a note: nothing in this codebase ever *reads* it (see `19.dead-privilege-fields.md`), so it grants nothing today. But it advertises which accounts *would* be privileged the moment an admin feature ships, and it is exposed publicly right now.

## Related: the same over-exposure through other paths

`fetchUserById` is the worst case but not the only one. The same denylist projection appears in:

- `server/src/middleware/auth.middleware.ts:36-38`. `User.findById(...).select("-password -refreshToken")` becomes `req.user`, which is then returned wholesale by `getCurrentUser` (`getCurrentUser.ts:11`) and `checkUserAuthDetails` (`healthCheck.controller.ts:19`). Those are authenticated and return the caller's own record, so the exposure is to the user themself, much less severe, but it still means `suspensionReason` and `isAdmin` are shipped to the browser.
- `server/src/controllers/userControllers/refreshAccessToken.ts:33`. `.select("-password")` only. This one leaves **`refreshToken`** in the returned object, and that value is sent to the client in the JSON body at line 66. It is a bcrypt hash of the refresh token rather than the token itself, so it is not directly replayable, but shipping a credential hash to the client is gratuitous, and it is the highest-value offline-cracking target in the schema.
- `server/src/controllers/userControllers/updateUserAvatar.ts:19-25` and `updateUserCoverImage.ts:33`. Same denylist, returned to the caller.

## The fix

### Replace every denylist projection with an allowlist

Define the shapes once and use them everywhere. Two shapes cover the whole app:

```ts
// server/src/constants/projections.ts

/** Safe to show to anyone, including anonymous visitors. */
export const PUBLIC_USER_FIELDS =
  "_id username fullname avatar coverImage createdAt";

/** Additionally safe to show to the account owner. */
export const PRIVATE_USER_FIELDS =
  `${PUBLIC_USER_FIELDS} email updatedAt`;
```

Then:

```ts
// server/src/controllers/userControllers/fetchUserById.ts
export const fetchUserById = asyncHandler(async (req, res) => {
  const { userId } = req.params;
  if (!isValidObjectId(userId)) throw new ApiError(400, "INVALID USER ID");

  const isSelf = req.user?._id && String(req.user._id) === userId;

  const user = await User.findOne({
    _id: userId,
    isDeactivated: { $ne: true },
    isSuspended: { $ne: true },
    isDeleted: { $ne: true },
  }).select(isSelf ? PRIVATE_USER_FIELDS : PUBLIC_USER_FIELDS);

  if (!user) throw new ApiError(404, "USER NOT FOUND");

  return res.status(200).json(new ApiResponse(200, { user }, "USER FETCHED SUCCESSFULLY"));
});
```

Three changes beyond the projection:

1. **Deactivated, suspended, and deleted accounts are now filtered out.** Today `fetchUserById` happily returns them, which contradicts `searchUserText.controller.ts` and `homepage.controller.ts`, both of which correctly exclude them. That inconsistency means "deactivate my account" does not actually hide you. This endpoint still serves you.
2. **`isSelf` is computed from `req.user`**, which requires `optionalAuth` on the route (`suggestions/05.optional-auth-middleware.md`). Without it, `req.user` is always undefined and every caller gets the public shape, which is a safe default, so this degrades correctly if you apply it before the middleware exists.
3. **`watchHistory` is gone from the response entirely.** It has one legitimate consumer, `GET /users/history`, which is already authenticated and reads `req.user._id`.

### Also fix the refresh endpoint

```ts
// server/src/controllers/userControllers/refreshAccessToken.ts:33
user = await User.findById(decodedRefreshToken._id).select(PRIVATE_USER_FIELDS);
```

This drops `refreshToken` from the object before it is returned at line 66. Note the handler *also* needs `refreshToken` to run `compareRefreshToken` at line 50, so fetch it explicitly and separately, or select it and strip it before responding:

```ts
const user = await User.findById(id).select(`${PRIVATE_USER_FIELDS} +refreshToken isSuspended isDeactivated`);
// ... use user.refreshToken for the comparison ...
const safeUser = user.toObject();
delete safeUser.refreshToken;
return res.status(200).json(new ApiResponse(200, { user: safeUser }, "..."));
```

### Consider `select: false` at the schema level

The most durable version of this fix moves the decision into the model, so no controller can leak these by forgetting:

```ts
// server/src/models/user.model.ts
password:     { type: String, required: [true, "PASSWORD IN REQUIRED"], select: false },
refreshToken: { type: String, default: "", select: false },
email:        { type: String, required: true, unique: true, lowercase: true, trim: true, select: false },
watchHistory: [{ type: mongoose.Schema.Types.ObjectId, ref: "Video", select: false }],
```

Fields marked `select: false` are excluded unless explicitly requested with `.select("+email")`. This inverts the default from "exposed unless removed" to "hidden unless requested", which is the property you want.

Be aware this is a breaking change with real reach: `loginUser` needs `+password`, `auth.middleware` needs nothing extra, `refreshAccessToken` needs `+refreshToken`, `changeCurrentPassword` needs `+password`, and `updateAccountDetails` writes `email`. Grep for every `User.find` before switching. Given that scope, applying the allowlist projections first and the schema-level change second is the lower-risk order.
