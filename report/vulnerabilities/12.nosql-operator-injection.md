# 12. NoSQL operator injection through unvalidated body values

- **Rank: 5 / 10** — revised down from 6 after retesting; see "Corrected 2026-08-10" below
- **Side: Server**
- **Category:** Injection
- **Location:** `loginUser.ts:20-28`, `newUsernameUpdate.ts:7-15`, `getAllVideos.ts:32-45`, `usernameAvailability.ts:7-10`

## Corrected 2026-08-10 — the query-string vector does not exist on this stack

The original version of this document opened by claiming that "Express parses `?a[$ne]=x` into the JavaScript object `{ a: { $ne: "x" } }`". **That is false for this project.** This server runs Express 5.1.0, and Express 5 changed the default `query parser` from `extended` (qs) to `simple` (Node's `querystring`). Verified against the installed dependency:

```
app.get('query parser')        →  'simple'
GET /t?inp[$ne]=zzz            →  req.query === { 'inp[$ne]': 'zzz' }   (a flat string key)
```

The bracket text becomes part of the **key name**, and the value stays a `string`. No nested object is produced, so no operator reaches the filter. **Case 1 below (`usernameAvailability`) is therefore not exploitable as written**, and every other `?param[$op]=` claim about this codebase should be read the same way.

What *is* real, and was retested end-to-end:

```
POST  content-type: application/json
{"email":{"$gt":""},"password":"x"}          →  req.body.email === { $gt: '' }     ✅ injects

POST  content-type: application/x-www-form-urlencoded
username[$ne]=zzz&password=x                 →  req.body.username === { $ne: 'zzz' } ✅ injects
```

Both work because `app.ts:48-49` registers `express.urlencoded({ extended: true })` — which *does* use `qs` — and `express.json()`, which passes arbitrary JSON structures through untouched. So the injection surface is **request bodies only**, not query strings.

The urlencoded vector deserves particular attention: `application/x-www-form-urlencoded` is a CORS "simple" content type, so an operator-injected login attempt can be fired from an attacker's page with no preflight. See `03.no-csrf-protection-with-cross-site-cookies.md`.

Rank moves 6 → 5: one of the four cases is void, and the remaining exploitable case is body-only.

## The issue

Express parses a JSON body into whatever structure the client sent, and `express.urlencoded({ extended: true })` parses `a[$ne]=x` in a **body** into `{ a: { $ne: "x" } }`. Mongoose passes those structures into query filters as-is. Any body value that reaches a filter without a type check can therefore become a **query operator** instead of a value.

Four places are listed below. Case 1 is retained for completeness but is **not exploitable** on Express 5; cases 2–4 are confirmed.

### 1. `usernameAvailability` — NOT EXPLOITABLE as originally described

```ts
// server/src/controllers/userControllers/usernameAvailability.ts
const { inp } = req.query as { inp: string };
if (!inp) throw new ApiError(404, "USERNAME NOT RECEIVED");

const exists = await User.exists({ username: inp });
```

The original claim was that `GET /api/v1/users/check-username?inp[$ne]=zzz` becomes `{ username: { $ne: "zzz" } }`. It does not — see the correction above. The filter receives the literal string `"zzz"` under a key named `inp[$ne]`, so `inp` is `undefined` and the handler 404s.

The `as { inp: string }` cast is still a lie — TypeScript erases at runtime, and `req.query` values are `string | string[]` even under the simple parser. The residual, much smaller bug:

```
GET /api/v1/users/check-username?inp=a&inp=b     →  req.query.inp === ["a", "b"]
```

An array reaching `User.exists({ username: [...] })` produces a Mongoose `CastError` on a `String` path, which the error middleware turns into a 400. The route is behind `verifyJWT` (`user.routes.ts:54`), so this is an authenticated nuisance, not an oracle. Narrow it to a string anyway — the one-line fix below is unchanged and still correct.

### 2. `loginUser` — the one to care about

```ts
// server/src/controllers/userControllers/loginUser.ts:20-28
const { username, email, password } = req.body;

if (!username && !email) throw new ApiError(400, "USERNAME OR EMAIL IS REQUIRED");

const matchedUser = await User.findOne({ $or: [{ username }, { email }] });
```

`POST` a JSON body of `{"email": {"$gt": ""}, "password": "x"}` and the filter selects the first user in natural order. The bcrypt check at line 33 still runs, so **this is not an authentication bypass** — the attacker must still supply the right password.

What it does give:

- **Targeted account selection without knowing the identifier.** `{"username": {"$regex": "^admin"}}` selects the first admin-ish account, and the response distinguishes "user not found" (404) from "wrong password" (401). That is an oracle over the username space, driven from the login endpoint, which is not rate limited (`05.no-rate-limiting-on-any-endpoint.md`).
- **A crash if `password` is not a string.** `bcrypt.compare(password, hash)` with an object throws, producing a 500. Cheap unauthenticated error-generation.

Two smaller bugs in the same lines, worth fixing together:

- `if (!username && !email)` permits a request with **no password at all**. `matchedUser.isPasswordCorrect(undefined)` → `bcrypt.compare(undefined, hash)` → throws → 500. There is no `if (!password)` guard anywhere in the handler.
- The `$or` means a request supplying only `username` still builds `{ $or: [{ username: "x" }, { email: undefined }] }`. Mongoose strips `undefined` from filters by default, so this happens to work — but it works by accident, and `{ email: undefined }` would match *everything* if `strictQuery` behaviour ever changed.

### 3. `newUsernameUpdate` — no validation of any kind

```ts
// server/src/controllers/userControllers/newUsernameUpdate.ts
const { username } = req.body;
if (!req.user || !req.user._id) throw new ApiError(400, "UNAUTHENTICATED REQUEST");

const user = await User.findByIdAndUpdate(req.user._id, { $set: { username } }, { new: true });
```

`username` goes from the request body into `$set` with zero checks. Mongoose casts to `String` on write, so an object becomes `"[object Object]"` rather than injecting — but that is the *only* thing stopping this, and it means:

- No length limit. No character restrictions. A username may contain `/`, spaces, `..`, control characters, or 10 000 characters.
- Usernames are used as **URL path segments** — `GET /api/v1/users/channel/:username`, `GET /api/v1/homepage/:username`, and client-side `<Route path="/:username">` in `App.tsx:94`. A username containing `/` or matching a reserved client route (`settings`, `history`, `tweets`, `playlists`) breaks routing or shadows a real page.
- No duplicate pre-check. The unique index catches it, producing a 409 "DUPLICATE ENTRY" from the generic Mongo error handler rather than a useful message.
- `usernameAvailability` exists and is called by the client (`useUsernameAvailability.ts`), but the update endpoint does not re-check — so the check-then-set race is wide open.

### 4. `getAllVideos` / `getAllVideosWithoutRestriction` — `$regex` and sort-field injection

```ts
// server/src/controllers/videoControllers/getAllVideos.ts:32-45
if (query) {
  matchStage.$or = [
    { title:       { $regex: query, $options: "i" } },
    { description: { $regex: query, $options: "i" } },
  ];
}

const sortStage: Record<string, 1 | -1> = {};
const sortField = sortBy || "createdAt";
sortStage[sortField] = sortType === "asc" ? 1 : -1;
```

Two problems:

- **`query` is not regex-escaped.** A crafted pattern such as `(a+)+$` against a long string causes catastrophic backtracking — ReDoS — inside the database server, blocking it for other clients. Note that `searchUserText.controller.ts:19` *does* escape correctly; these two controllers do not.
- **`sortBy` is an arbitrary caller-controlled key** used as a document field name. Mongo rejects `$`-prefixed sort keys, so this is not a full injection, but it does let a caller sort by any field including unindexed ones — forcing a full in-memory sort, which Mongo aborts at 100 MB. Unbounded work from an unauthenticated request.

## The fix

The root cause is the same in all four: **values from `req` are used without being narrowed to a primitive type.** Fix the pattern, not the four symptoms.

### Immediate, local fixes

```ts
// usernameAvailability.ts
const inp = typeof req.query.inp === "string" ? req.query.inp.trim() : "";
if (!inp) throw new ApiError(400, "USERNAME NOT RECEIVED");
const exists = await User.exists({ username: inp });
```

```ts
// loginUser.ts
const username = typeof req.body.username === "string" ? req.body.username.trim() : "";
const email    = typeof req.body.email === "string" ? req.body.email.trim().toLowerCase() : "";
const password = typeof req.body.password === "string" ? req.body.password : "";

if ((!username && !email) || !password) {
  throw new ApiError(400, "USERNAME OR EMAIL AND PASSWORD ARE REQUIRED");
}

const or = [];
if (username) or.push({ username });
if (email) or.push({ email });
const matchedUser = await User.findOne({ $or: or });
```

```ts
// newUsernameUpdate.ts
const USERNAME_RE = /^[a-z0-9_]{3,20}$/;
const RESERVED = new Set([
  "admin", "api", "settings", "setting", "history", "tweets", "videos",
  "playlists", "search", "support", "messages", "liked-content",
  "my-videos", "subscribers", "test",
]);

const username = typeof req.body.username === "string"
  ? req.body.username.trim().toLowerCase()
  : "";

if (!USERNAME_RE.test(username)) {
  throw new ApiError(400, "USERNAME MUST BE 3-20 CHARACTERS: a-z, 0-9, UNDERSCORE");
}
if (RESERVED.has(username)) {
  throw new ApiError(409, "THAT USERNAME IS RESERVED");
}
```

The reserved list must stay in sync with the client routes in `App.tsx`. That coupling is a smell — the durable fix is to namespace channel pages under `/c/:username` so no username can ever shadow an app route. Worth doing while the user base is small.

```ts
// getAllVideos.ts
const escapeRegex = (s: string) => s.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");

const rawQuery = typeof req.query.query === "string" ? req.query.query.trim().slice(0, 100) : "";
if (rawQuery) {
  const re = new RegExp(escapeRegex(rawQuery), "i");
  matchStage.$or = [{ title: re }, { description: re }];
}

const SORTABLE = new Set(["createdAt", "views", "duration", "title"]);
const requested = typeof req.query.sortBy === "string" ? req.query.sortBy : "createdAt";
const sortField = SORTABLE.has(requested) ? requested : "createdAt";
```

An allowlist for sort fields, not a sanitiser. The set of sortable columns is small and known — enumerate it.

### The systematic fix

Every one of these is "a value arrived from the network and was used without being checked". A schema validation layer at the route boundary eliminates the class, and gives the controllers correctly typed inputs for free. That design is `suggestions/02.central-validation-layer.md`.

`express-validator` is already a dependency (`server/package.json`) and is used on exactly one route — the contact form. Either extend it everywhere or replace it with `zod`, which gives you inferred TypeScript types from the same schema. My recommendation is `zod`; the reasoning is in that document.

### What about `express-mongo-sanitize`?

It strips `$`-prefixed keys from `req.body`/`req.query` globally, which would blunt case 2 (the only confirmed injection). It is worth adding as defence in depth (`suggestions/03.security-middleware-baseline.md`) but it is **not** the fix:

- It does nothing for case 3 (the value is a legal string, just an invalid username) or case 4 (regex and sort-field abuse use no `$` at all).
- **Sanitising `req.query` is unnecessary on this stack** — Express 5's `simple` query parser cannot produce a nested object in the first place (see the correction at the top). Body sanitisation is the part that would earn its keep.
- The maintained package for Express 5 is `express-mongo-sanitize`'s successor; the original mutates `req.query`, which is a getter-only property in Express 5 and will throw. Check compatibility before installing.

Validate inputs. Sanitising is the backstop.
