# 20. Operations report success when authorization silently failed

- **Rank: 4 / 10**
- **Side: Both (server misreports, client trusts it)**
- **Category:** Broken access control feedback / unchecked write results
- **Location:** `playlistController/deletePlaylist.ts:17-21`, `tweetControllers/updateTweet.ts:17-35`, `comment.controller.ts:129-137`, and the general `if (!result)` pattern

## The issue

Several handlers scope a write by ownership — correctly — and then fail to check whether the write actually matched anything. Mongoose write results are objects, and objects are truthy, so the guards never fire.

### `deletePlaylist` — the clearest case

```ts
const deletedPlaylist = await Playlist.deleteOne({
  _id: playlistId,
  owner: req.user._id,
});
if (!deletedPlaylist) throw new ApiError(400, "PLAYLIST NOT DELETED");

return res.status(200).json(
  new ApiResponse(200, { result: deletedPlaylist }, "PLAYLIST DELETED SUCCESSFULLY")
);
```

The filter is right: a non-owner cannot delete someone else's playlist. But `deleteOne` resolves to `{ acknowledged: true, deletedCount: 0 }` when nothing matched, and that object is truthy. So attempting to delete a playlist you do not own returns:

```
HTTP 200  {"success": true, "message": "PLAYLIST DELETED SUCCESSFULLY", "data": {"result": {"acknowledged": true, "deletedCount": 0}}}
```

The security boundary held. The report is wrong.

Contrast with the sibling handlers, which get this right by using `findOneAndUpdate` and checking for `null`:

```ts
// updatePlaylist.ts:41
if (!playlist) throw new ApiError(403, "USER NOT AUTHORIZED OR PLAYLIST NOT FOUND");
// addVideoToPlaylist.ts:24, removeVideoFromPlaylist.ts:26 — same pattern
```

So three of the four playlist mutations report correctly and one does not.

### `updateTweet` — reports success without writing

```ts
const updatedTweet = await Tweet.aggregate([
  { $match: { _id: toObjectId(tweetId), owner: toObjectId(req.user._id as string) } },
  { $set: { content } },
  { $merge: { into: "tweets", on: "_id", whenMatched: "merge", whenNotMatched: "discard" } },
]);

if (!updatedTweet) throw new ApiError(404, "TWEET NOT FOUND");

return res.status(200).json(
  new ApiResponse(200, { tweet: updatedTweet[0] }, "TWEET UPDATED SUCCESSFULLY")
);
```

An aggregation ending in `$merge` returns an **empty array** — the documents go to the output collection, not to the cursor. So `updatedTweet` is always `[]`:

- `!updatedTweet` is always `false`, so the 404 never fires.
- `updatedTweet[0]` is always `undefined`, so the response always contains `{"tweet": undefined}` → serialised as `{}`.

Editing someone else's tweet returns 200 "TWEET UPDATED SUCCESSFULLY". Editing your own returns 200 with no tweet in the body, so the client cannot update its cache from the response and must refetch.

Using an aggregation pipeline with `$merge` for a single-document update is also the wrong tool — it is heavier than an update and it discards the result. `findOneAndUpdate` does the job.

### `deleteComment` — orphaned likes

```ts
if (nestedComments.length > 0) {
  for (let com of nestedComments) {
    const comID = com._id;
    await Like.findOneAndDelete({ comment: comID });    // deletes ONE like
    await com.deleteOne({ _id: comID });
  }
}

const searchLike = await Like.findOneAndDelete({ comment: comment._id });   // ONE like
```

`findOneAndDelete` removes a single document. A comment with 40 likes loses one; 39 `Like` documents survive pointing at a comment that no longer exists. These then surface in `getEveryLikedContent` (`getEveryLikedContent.ts:21-40`), which populates `comment` and gets `null`, so the user's liked-content page renders entries for deleted comments.

`deleteVideo.ts:35` and `deleteTweet.ts:24` use `deleteMany` correctly for the same job — so this is an inconsistency, not a misunderstanding.

### The general pattern

`if (!result) throw ...` appears throughout the codebase applied to values that cannot be falsy:

```ts
const videos = await Video.find({ owner: userId });
if (!videos) throw new ApiError(404, "VIDEOS NOT FOUND");        // find() returns []

const comment = await Comment.create({ ... });
if (!comment) throw new ApiError(400, "COMMENT NOT REGISTERED"); // create() throws on failure

const updatedVideo = await video.save({ validateModifiedOnly: true });
if (!updatedVideo) throw new ApiError(400, "VIDEO UPDATE FAILED"); // save() returns the doc
```

`find()` returns `[]`, which is truthy. `create()` and `save()` reject rather than resolving falsy. None of these guards can fire. They read like error handling and provide none — which is worse than no check, because it stops anyone from adding a real one.

## Why it matters

Rank 4 because **no actual authorization boundary is crossed**. In every case above the ownership filter is correct and unauthorized data is not modified. This is a reporting failure, not an access-control bypass.

It still matters:

1. **The client acts on the false success.** `useDeletePlaylist` resolves successfully, so `DeletePlaylistModal.tsx` closes and the UI optimistically removes the row. The playlist reappears on the next refetch. The user sees a delete that "didn't stick" with no explanation.

2. **It masks genuine failures.** If `deletePlaylist` ever stops working — a schema change, a wrong field name, a connection issue — it will keep returning 200 "DELETED SUCCESSFULLY". You would find out from user reports, not from monitoring.

3. **It is a probing oracle in reverse.** An attacker enumerating playlist IDs gets 200 for every ID, whether or not it exists and whether or not they own it. That is accidentally good for privacy. But it means you cannot distinguish "attacker probing 10 000 IDs" from normal traffic in your logs, because nothing errors.

4. **`updateTweet` is a live product bug.** The response contains no tweet, so the client cannot update from it.

## The fix

```ts
// deletePlaylist.ts
const result = await Playlist.deleteOne({ _id: playlistId, owner: req.user._id });
if (result.deletedCount === 0) {
  throw new ApiError(404, "PLAYLIST NOT FOUND OR YOU DO NOT OWN IT");
}
return res.status(200).json(new ApiResponse(200, { deleted: true }, "PLAYLIST DELETED SUCCESSFULLY"));
```

404 rather than 403, for the same reason as `11.unpublished-videos-readable-by-id.md`: 403 confirms the resource exists. A combined message avoids distinguishing the two cases.

```ts
// updateTweet.ts — replace the whole aggregation
const updatedTweet = await Tweet.findOneAndUpdate(
  { _id: tweetId, owner: req.user._id },
  { $set: { content } },
  { new: true, runValidators: true }
).populate("owner", PUBLIC_USER_FIELDS);

if (!updatedTweet) throw new ApiError(404, "TWEET NOT FOUND OR YOU DO NOT OWN IT");

return res.status(200).json(
  new ApiResponse(200, { tweet: updatedTweet }, "TWEET UPDATED SUCCESSFULLY")
);
```

Simpler, atomic, correctly authorized, and it actually returns the updated document so the client can use it.

```ts
// comment.controller.ts — deleteComment
const nestedIds = nestedComments.map((c) => c._id);
if (nestedIds.length > 0) {
  await Like.deleteMany({ comment: { $in: nestedIds } });
  await Comment.deleteMany({ _id: { $in: nestedIds } });
}
await Like.deleteMany({ comment: comment._id });
await comment.deleteOne();
```

`deleteMany` with `$in`, matching what `deleteVideo` and `deleteTweet` already do. This also replaces an N-query loop with two queries.

Note the nesting only goes one level deep — a reply to a reply to a comment is not cleaned up. The data model allows arbitrary depth (`comment.model.ts` has a self-referencing `comment` field) but every delete path assumes exactly two levels. Either enforce the two-level limit when creating (`addCommentToComment` should reject a parent that itself has a parent) or make the deletion recursive. Enforcing the limit is simpler and matches the UI.

### Delete the guards that cannot fire

Rather than fixing them individually, remove them. `asyncHandler` already forwards rejections to the error middleware, so a genuine `create()` or `save()` failure is handled correctly today — the `if (!x) throw` lines add nothing.

```bash
cd server
grep -rn "if (!.*) throw new ApiError" src/controllers/ | wc -l
```

Work through them and keep only the ones checking a value that can genuinely be `null`: `findById`, `findOne`, `findOneAndUpdate`, `findByIdAndUpdate`, `findOneAndDelete`. Those return `null` on no-match and the guards are correct and necessary.
