# 10. Changing a password does not revoke existing sessions

- **Rank: 6 / 10**
- **Side: Server**
- **Category:** Session management / insufficient credential invalidation
- **Location:** `server/src/controllers/userControllers/changeCurrentPassword.ts:29-34`

## The issue

```ts
user.password = newPassword;
await user.save({ validateModifiedOnly: true });

return res.status(200).json(new ApiResponse(200, true, "PASSWORD CHANGED SUCCESSFULLY"));
```

The password hash is updated. Nothing else is. Specifically:

- `user.refreshToken` — the bcrypt hash of the currently valid refresh token — is left in place.
- No new cookies are issued to the user who just changed their password.
- There is no token-version or session-generation counter for `verifyJWT` to check.

## Why it matters

"Change my password" is what a person does when they believe someone else has access to their account. It is the primary self-service remediation for a compromise. If it does not end the attacker's session, it fails at the one job it exists to do.

Concretely, after a compromise:

1. Attacker logs in with a stolen password. They now hold an access token (15 min) and a refresh token (7 days), both in cookies.
2. Victim notices and changes their password.
3. Victim's own tokens keep working — fine, that is intended.
4. **The attacker's tokens also keep working.** Their access token stays valid for up to 15 more minutes, and their refresh token stays valid for the full 7 days.
5. On expiry, the attacker's client calls `POST /users/refresh-token`. `compareRefreshToken` compares their token against `user.refreshToken`, which was never cleared, so it matches. They receive a **fresh** access token and a **fresh** refresh token, and the 7-day window restarts.

Step 5 is the important one: this is not a 7-day exposure, it is indefinite. As long as the attacker refreshes once a week, the victim can never evict them by changing their password. The only thing that would work is `POST /users/logout` — which the attacker would have to be tricked into triggering.

The same gap applies to the other credential-adjacent operations:

- `updateAccountDetails` (`updateAccountDetails.ts`) changes the **email address** with no re-authentication and no session invalidation. If a password-reset flow is ever added, this becomes a direct account-takeover path: attacker with a stolen session changes the email to their own, then triggers a reset.
- `deactivateUser` clears the caller's cookies but does not clear `refreshToken` in the database, so a *different* client still holding the old refresh token can call `/refresh-token`. That path does check `isDeactivated` and rejects (`refreshAccessToken.ts:46`), so it is currently covered — by a check in a different file. Worth knowing it is load-bearing.

## Why 6 and not higher

The attack requires the account to already be compromised. This vulnerability does not *cause* a breach; it prevents recovery from one. That is a meaningful distinction — but "the victim cannot lock the attacker out" is a serious enough failure that it sits above the mid-line.

## The fix

There are two mechanisms. Implement both — they cover different token types.

### Mechanism 1 — Clear the stored refresh token (kills refresh tokens)

Immediate, one line, no schema change:

```ts
// server/src/controllers/userControllers/changeCurrentPassword.ts
user.password = newPassword;
user.refreshToken = "";           // invalidates every outstanding refresh token
await user.save({ validateModifiedOnly: true });
```

`compareRefreshToken` (`server/src/utils/refreshTokenSecurity.ts:14`) returns `false` for an empty stored value, so every existing refresh token — including the victim's own — is now dead.

Then re-issue for the caller so they are not logged out by their own password change:

```ts
const { newAccessToken, newRefreshToken } =
  await generateAccessAndRefreshTokens(String(user._id));

return res
  .status(200)
  .cookie("accessToken", newAccessToken, accessTokenCookieOptions)
  .cookie("refreshToken", newRefreshToken, refreshTokenCookieOptions)
  .json(new ApiResponse(200, { rotated: true }, "PASSWORD CHANGED SUCCESSFULLY"));
```

### Mechanism 2 — Token version (kills access tokens)

Mechanism 1 leaves a gap: the attacker's *access* token is still valid for up to 15 minutes, because `verifyJWT` only checks the signature and expiry. To close that you need something in the token that the server can invalidate.

```ts
// server/src/models/user.model.ts — add to schema
tokenVersion: { type: Number, default: 0 },
```

```ts
// include it in the access token payload
async function jwtAccessToken(this: UserThisType) {
  const payload = {
    _id: String(this._id),
    username: this.username,
    tokenVersion: this.tokenVersion ?? 0,
  };
  return jwt.sign(payload, env.ACCESS_TOKEN_SECRET, { expiresIn: env.ACCESS_TOKEN_EXPIRY });
}
```

```ts
// server/src/middleware/auth.middleware.ts — after loading the user
if ((decoded.tokenVersion ?? 0) !== (user.tokenVersion ?? 0)) {
  throw new ApiError(401, "SESSION EXPIRED, PLEASE LOG IN AGAIN");
}
```

Then bump it on any credential change:

```ts
user.password = newPassword;
user.refreshToken = "";
user.tokenVersion = (user.tokenVersion ?? 0) + 1;
await user.save({ validateModifiedOnly: true });
// re-issue cookies for the caller, as above — their new token carries the new version
```

`verifyJWT` already loads the user document on every request (`auth.middleware.ts:36`), so this check costs nothing extra — no additional query, no cache, no session store.

Bump `tokenVersion` on:
- password change
- email change (`updateAccountDetails`)
- account deactivation and deletion
- an explicit "log out of all devices" action, if you add one

### Notice the payload shrank

The example above drops `email` and `fullname` from the access token. That is deliberate and worth doing:

- A JWT is signed, not encrypted. Anyone who obtains the cookie can base64-decode the payload and read it. Putting `email` in there means every token is a PII carrier — including in any log, proxy trace, or error report that captures a cookie header.
- The values go stale. A user who changes their email still carries the old one in their token for 15 minutes.
- Nothing reads them. `auth.middleware.ts` uses only `_id`; everything downstream uses the freshly loaded `req.user`.

This requires updating `UserAccessTokenPayloadType` in `server/src/constants.ts:24-31` and the type guard in `server/src/utils/checkPayloadType.ts`, which currently *requires* `email`, `username`, and `fullname` to be present and would reject the slimmer token.
