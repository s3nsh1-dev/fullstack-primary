# 13. Unbounded result limits and a search endpoint with no pagination at all

- **Rank: 6 / 10**
- **Side: Server**
- **Category:** Resource exhaustion / denial of service
- **Location:** `searchUserText.controller.ts` (no limit), `feed.controller.ts:8-13`, `getEveryLikedContent.ts:9-10`, `getUserPlaylists.ts:10-11`, `comment.controller.ts:207,321,430`, `getWatchHistory.ts:11-12`, `getSubscribedChannels.ts` (no pagination), `getLikedVideos.ts` (no pagination)

## The issue

Pagination is implemented inconsistently across the API, and in most places the caller controls the page size with no upper bound.

### Category A. `limit` accepted from the caller with no cap

```ts
// feed.controller.ts:9
const limit = Number(req.query.limit) || 30;

// getEveryLikedContent.ts:10
const limit = Number(req.query.limit) || 10;

// getUserPlaylists.ts:11
const limit = Number(req.query.limit) || 10;

// getWatchHistory.ts:12
const limit = Number(req.query.limit) || 10;

// comment.controller.ts:207 — and again at 321 and 430
const { page = 1, limit = 10, userId } = req.query;
...
Comment.aggregatePaginate(Comment.aggregate(pipeline), { page: Number(page), limit: Number(limit) });
```

`?limit=1000000` is honoured by every one of these.

The two controllers that *do* validate, `getAllVideos.ts:15-24` and `getUserTweets.ts:16-25`, only check `limit >= 1` and `!Number.isNaN(limit)`. A million passes both.

### Category B. No pagination whatsoever

```ts
// searchUserText.controller.ts — four queries, zero limits
User.find({ $or: [{ username: regex }, { fullname: regex }], ... }).select(...),
Video.aggregate([ { $match: { isPublished: true, $or: [...] } }, { $lookup: ... } ]),
Tweet.aggregate([ { $match: { content: regex } }, { $lookup: ... }, { $lookup: ... } ]),
Playlist.aggregate([ { $match: { $or: [{ name: regex }, { description: regex }] } } ]),
```

```ts
// getSubscribedChannels.ts:15 — every subscription, populated
const channels = await Subscription.find({ subscriber: subscriberId }).populate("channel", ...);

// getLikedVideos.ts:13 — every like, with two $lookups each
const likedVideos = await Like.aggregate([ ... ]);
```

`GET /api/v1/search/q/a` runs four collection scans in parallel with an unanchored case-insensitive regex, joins users into three of them, and serialises the complete result set into one JSON response. There is no `$limit` anywhere in the file.

### Category C. Negative and fractional values

`getEveryLikedContent`, `getUserPlaylists`, `getWatchHistory`, and the comment endpoints compute `skip = (page - 1) * limit` with no lower bound on `page`. `?page=-5&limit=10` yields `skip = -60`. MongoDB rejects a negative `$skip` with an error, so this surfaces as an unhandled 500 rather than a security problem, but it is an unauthenticated crash vector, and `Number("1.5")` passing the `page < 1` check produces a fractional `$skip` that also errors.

## Why it matters

Three distinct failure modes, all reachable without an account:

**Memory exhaustion on the Node process.** `?limit=1000000` on `/feeds` materialises up to a million documents, each with a joined owner object, into a JavaScript array, then `JSON.stringify`s the whole thing into a response buffer. Node's default heap is around 1.5-4 GB depending on the runtime; a few concurrent requests exceed it and the process is OOM-killed. On Render or Railway that is a restart and dropped connections for everyone.

**Database-side aborts.** `getAllVideos` and `getUserTweets` use `$sort` before `$facet` on `createdAt`, which is not indexed (`video.model.ts` declares no indexes at all). MongoDB aborts an in-memory sort exceeding 100 MB, so a large collection produces query failures rather than slow responses.

**Cheap amplification.** `GET /search/q/a` is a single unauthenticated GET that costs four collection scans plus three `$lookup` joins and can return your entire dataset. The request is a few hundred bytes; the work is unbounded. With no rate limiting (`05.no-rate-limiting-on-any-endpoint.md`) a single client saturates the database.

There is also a **data-exposure** dimension: the same search endpoint returns every matching user's email address (`09.email-addresses-exposed-on-public-endpoints.md`). No limit means 26 requests dump the user table. Capping results is part of that fix, not just a performance concern.

## The fix

### One shared helper, used everywhere

The current situation is that eight controllers each re-implement pagination with different defaults, different validation, and different response field names (`havePrevPage`, `hasPrevPage`, `hasPreviousPage` all appear). Consolidate:

```ts
// server/src/utils/pagination.ts
import type { Request } from "express";

const DEFAULT_LIMIT = 20;
const MAX_LIMIT = 100;

export type PageParams = { page: number; limit: number; skip: number };

export const getPageParams = (req: Request, defaultLimit = DEFAULT_LIMIT): PageParams => {
  const rawPage = Number(req.query.page);
  const rawLimit = Number(req.query.limit);

  const page = Number.isFinite(rawPage) ? Math.max(1, Math.floor(rawPage)) : 1;
  const limit = Number.isFinite(rawLimit)
    ? Math.min(MAX_LIMIT, Math.max(1, Math.floor(rawLimit)))
    : defaultLimit;

  return { page, limit, skip: (page - 1) * limit };
};

export const buildPageMeta = (total: number, { page, limit }: PageParams) => {
  const totalPages = Math.max(1, Math.ceil(total / limit));
  return {
    total,
    totalPages,
    currentPage: page,
    limit,
    hasNextPage: page < totalPages,
    hasPrevPage: page > 1,
  };
};
```

`Math.floor` handles fractional input, `Math.max(1, ...)` handles negatives and zero, `Math.min(MAX_LIMIT, ...)` caps the ceiling, and `Number.isFinite` rejects `NaN` and `Infinity`. Note the deliberate choice to **clamp rather than reject**. `?limit=5000` returns 100 results instead of a 400. That is friendlier for clients and removes an error path; reject only if you need callers to notice.

Applied:

```ts
// feed.controller.ts
const { page, limit, skip } = getPageParams(req, 30);

// getUserPlaylists.ts
const { page, limit, skip } = getPageParams(req, 10);
// ... aggregate ...
return res.status(200).json(new ApiResponse(200, {
  playlists: playlists[0].data,
  ...buildPageMeta(playlists[0].total[0]?.total ?? 0, { page, limit, skip }),
}, "USER PLAYLISTS FETCHED SUCCESSFULLY"));
```

### Search needs a hard cap per collection

Search is not a paginated list in this UI. It is a "top results" panel. Cap each collection rather than paginating:

```ts
// searchUserText.controller.ts
const SEARCH_LIMIT = 20;

const searchText = String(req.params.searchText).trim().slice(0, 100);
if (searchText.length < 2) {
  throw new ApiError(400, "SEARCH TEXT MUST BE AT LEAST 2 CHARACTERS");
}

const escaped = searchText.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
const regex = new RegExp(escaped, "i");

const [users, videos, tweets, playlists] = await Promise.all([
  User.find({ ... }).select(PUBLIC_USER_FIELDS).limit(SEARCH_LIMIT),
  Video.aggregate([ { $match: { ... } }, { $limit: SEARCH_LIMIT }, { $lookup: ... } ]),
  Tweet.aggregate([ { $match: { content: regex } }, { $limit: SEARCH_LIMIT }, ... ]),
  Playlist.aggregate([ { $match: { ... } }, { $limit: SEARCH_LIMIT } ]),
]);
```

Two details:

- **Raise the minimum query length from 1 to 2.** The current `length < 1` check permits `GET /search/q/a`, which matches nearly everything. Two characters is still permissive but meaningfully narrows the worst case.
- **Put `$limit` immediately after `$match`, before the `$lookup` stages.** Ordering matters: joining 10 000 documents and then keeping 20 does the work anyway. Limiting first means the joins run on 20 documents.

### Add the missing pagination

`getSubscribedChannels` and `getLikedVideos` need it added, not capped, since they currently return everything. Both are `verifyJWT`-adjacent and scoped to one user, so the blast radius is smaller, but a power user with 5 000 likes will time out their own page.

### The real fix for search: a text index

Unanchored `$regex` cannot use an index, so every query is a collection scan regardless of limits. For a proper solution, add MongoDB text indexes:

```ts
// video.model.ts
videoSchema.index({ title: "text", description: "text" });
// user.model.ts
userSchema.index({ username: "text", fullname: "text" });
```

and query with `$text: { $search: term }`. That is index-backed and gives relevance scoring for free. The trade-off is that text search matches whole words, so it loses substring/prefix behaviour, and a search for "prog" stops matching "programming". Decide which behaviour you want before switching; a hybrid (text index for the common case, regex fallback for short prefixes) is also viable. Index definitions are collected in `suggestions/07.database-indexes-and-unique-constraints.md`.
