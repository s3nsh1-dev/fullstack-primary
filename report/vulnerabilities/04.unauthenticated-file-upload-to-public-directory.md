# 04. Unauthenticated file upload with no size or type limits, into a publicly served directory

- **Rank: 8 / 10**
- **Side: Server**
- **Category:** Unrestricted file upload / resource exhaustion / stored content on API origin
- **Location:** `server/src/middleware/multer.middleware.ts:3-11`, `server/src/app.ts:50`, `server/src/routes/user.routes.ts:30-36`, `server/src/controllers/videoControllers/publishAVideo.ts:14-22`

## The issue

Four separate weaknesses compound here. Individually each is minor. Together they let an anonymous person write arbitrary files of arbitrary size onto your server's disk and then fetch them back over HTTP.

### 1. Multer has no limits and no file filter

```ts
const storage = multer.diskStorage({
  destination: (req, file, cb) => cb(null, "./public/temp"),
  filename: function (req, file, cb) {
    const uniqueName = Date.now() + "-" + file.originalname;
    cb(null, uniqueName);
  },
});

export const multerUpload = multer({ storage });
```

No `limits: { fileSize }`. No `fileFilter`. Multer's defaults are unlimited. Any content type, any size, until the disk fills.

### 2. Multer runs *before* authentication on the register route

```ts
// server/src/routes/user.routes.ts:30
userRouter.route("/register").post(
  multerUpload.fields([
    { name: "avatar", maxCount: 1 },
    { name: "coverImage", maxCount: 1 },
  ]),
  registerUser
);
```

Registration is public by necessity. But multer is *middleware*. It streams the upload to disk to completion before `registerUser` ever runs. So the write happens for anonymous callers, unconditionally, before any validation.

### 3. Failed requests orphan the file permanently

The cleanup path is `uploadOnCloudinary()`, which unlinks the local file (`server/src/utils/cloudinary.ts:28-36`). Nothing else deletes anything. So any request that throws *before* reaching that call leaves the file on disk forever.

`registerUser` throws early in exactly this way:

```ts
// server/src/controllers/userControllers/registerUser.ts:9
if ([fullname, email, username, password].some((field) => field.trim() === ""))
  throw new ApiError(400, "INCOMPLETE INPUT FIELDS BY USER");
```

Send a multipart request with a file but omit `fullname`, and `field.trim()` is called on `undefined`, producing a `TypeError`, a 500, and an orphaned file. There is no `finally` block, no cleanup middleware, no scheduled sweep of `public/temp`.

`publishAVideo` has the same shape: it throws `"TITLE AND DESCRIPTION ARE REQUIRED"` and `"MEDIA ATTACHMENTS MISSING"` after multer has already written the files.

### 4. That directory is served publicly

```ts
app.use(express.static("public"));   // server/src/app.ts:50
```

`express.static("public")` resolves relative to `process.cwd()`. Your start script is `"start": "node dist/index.js"`, run from `server/`, so this serves `server/public/**` at the site root. Uploads land in `server/public/temp/`. Therefore an uploaded file is retrievable at:

```
GET https://your-api.example/temp/1786046431635-payload.html
```

The filename is `Date.now() + "-" + originalname`, and both halves are attacker-controlled or attacker-predictable, so the attacker knows the URL to within a few milliseconds of guessing, and can simply brute-force the millisecond.

## Exploit

**Disk exhaustion (unauthenticated).** `POST /api/v1/users/register` with a 5 GB multipart part named `avatar` and no other fields. The file is written in full, the handler 500s, the file is never removed. Repeat. On a small VPS or a Render instance with a 10-20 GB disk this is a handful of requests. When the disk fills, Mongo's local operations, the log writer, and further uploads all fail.

**Serving hostile content from your API origin.** Upload a file named `payload.html` containing script, then fetch `https://your-api.example/temp/<ts>-payload.html`. The browser renders it (Express `static` sets `Content-Type` from the extension), executing script *in the origin of your API*. Because your auth cookies are scoped to that origin with `path: "/"`, script running there can act with the victim's session. `httpOnly` prevents reading the cookie value, but not making credentialed same-origin requests.

The same applies to `.svg` (renders inline, supports `<script>`), and the origin can also be used to host phishing pages that borrow your domain's credibility.

**Cloudinary bill.** For requests that *do* succeed, there is still no type or size check, so an authenticated user can push arbitrarily large files through to Cloudinary via `POST /api/v1/videos`. Your transformation and storage quota is the limit.

## What is *not* wrong here

Worth stating so you do not spend effort on it: **path traversal via `originalname` does not work.** I tested it against your installed multer 2.1.1:

```
uploaded with filename "../../../pwn.txt"
→ file.originalname === "pwn.txt"
→ written to public/temp/1786046431635-pwn.txt
→ nothing written outside public/temp
```

Busboy strips path components before multer sees the name. So `path.join(destination, filename)` in `multer/storage/disk.js` cannot be walked upward. The recommendation below still replaces `originalname` with a random name, but for content-type and collision reasons, not traversal.

## The fix

### Immediate (do this now, small and self-contained)

```ts
// server/src/middleware/multer.middleware.ts
import multer from "multer";
import crypto from "crypto";
import path from "path";

const IMAGE_MIME = new Set(["image/jpeg", "image/png", "image/webp", "image/avif"]);
const VIDEO_MIME = new Set(["video/mp4", "video/quicktime", "video/webm"]);

const storage = multer.diskStorage({
  destination: (_req, _file, cb) => cb(null, "./private/uploads"),
  filename: (_req, file, cb) => {
    // never reuse the client-supplied name: it controls the served Content-Type
    const ext = path.extname(file.originalname).toLowerCase().slice(0, 10);
    cb(null, `${crypto.randomUUID()}${ext}`);
  },
});

export const imageUpload = multer({
  storage,
  limits: { fileSize: 5 * 1024 * 1024, files: 2 },
  fileFilter: (_req, file, cb) =>
    IMAGE_MIME.has(file.mimetype)
      ? cb(null, true)
      : cb(new Error("ONLY JPEG, PNG, WEBP OR AVIF IMAGES ARE ALLOWED")),
});

export const videoUpload = multer({
  storage,
  limits: { fileSize: 200 * 1024 * 1024, files: 2 },
  fileFilter: (_req, file, cb) => {
    const ok = file.fieldname === "thumbnail" ? IMAGE_MIME : VIDEO_MIME;
    return ok.has(file.mimetype)
      ? cb(null, true)
      : cb(new Error(`INVALID FILE TYPE FOR ${file.fieldname}`));
  },
});
```

Then, in `app.ts`, **delete this line**:

```ts
app.use(express.static("public"));   // remove
```

Nothing in this application needs it. The client is a separate Vite build served from its own origin; the API serves JSON. Removing it eliminates the public-serving half of the problem outright. Move the staging directory to `./private/uploads` (as above) so that even if a static handler is reintroduced later it does not expose staged files.

Add guaranteed cleanup so failures cannot orphan files:

```ts
// server/src/middleware/cleanupUploads.middleware.ts
import type { Request, Response, NextFunction } from "express";
import { promises as fs } from "fs";
import { logService } from "../services/logger.service";

export const cleanupUploads = (req: Request, res: Response, next: NextFunction) => {
  res.on("finish", () => {
    const files = [
      ...(req.file ? [req.file] : []),
      ...Object.values((req.files as Record<string, Express.Multer.File[]>) ?? {}).flat(),
    ];
    for (const f of files) {
      fs.unlink(f.path).catch((err) => {
        if (err.code !== "ENOENT") logService.warn("upload cleanup failed", { path: f.path });
      });
    }
  });
  next();
};
```

Register it once, globally, after the body parsers. `res.on("finish")` fires on success *and* on error responses, so the orphan case is covered. `ENOENT` is expected and ignored, because `uploadOnCloudinary` may have already removed the file.

Finally, sweep what is already there:

```bash
ls -la server/public/temp/     # expect only .gitkeep
```

### Target (the real answer)

Stop staging uploads on your server at all. Have the client upload directly to Cloudinary using a short-lived signature the server issues. The file never touches your disk, your bandwidth, or your event loop. This removes this entire vulnerability class rather than bounding it. That design is `suggestions/10.direct-to-cloudinary-uploads.md`.

## Interaction with other documents

- `suggestions/10.direct-to-cloudinary-uploads.md` is the target-state design. **The two are sequential, not contradictory**: apply the immediate fix now, then the direct-upload design replaces `multer.middleware.ts` and `cleanupUploads` entirely. Do not implement the interim `fileFilter` and then also keep it after moving to signed uploads. The validation moves to the signature parameters (`allowed_formats`, `max_bytes`).
- `05.no-rate-limiting-on-any-endpoint.md` bounds *how fast* an attacker can do this; this document bounds *what each request can do*. Both are needed. A 5 MB limit still fills a disk if it can be called 1000×/second.
- `14.weak-registration-validation.md` covers the `field.trim()` `TypeError` that triggers the orphan path. Fixing validation reduces, but does not eliminate, the orphan window.
- `suggestions/03.security-middleware-baseline.md` specifies where `cleanupUploads` sits in the middleware order.
