# 07. Unauthenticated write to any user's watch history

- **Rank: 7 / 10**
- **Side: Both (server accepts it, client is what taught the API this shape)**
- **Category:** Broken access control (IDOR) / missing authentication
- **Location:** `server/src/routes/user.routes.ts:53`, `server/src/controllers/userControllers/addToWatchHistory.ts:8-30`, `client/src/hooks/data-fetching/useUpdateWatchHistory.ts:14-21`

## The issue

The route has no authentication middleware:

```ts
// server/src/routes/user.routes.ts
userRouter.route("/history").get(verifyJWT, getWatchHistory);        // protected
userRouter.route("/history/:videoId").post(addToWatchHistory);        // NOT protected
```

And the controller takes the target user's identity from the query string:

```ts
const addToWatchHistory = asyncHandler(async (req, res) => {
  const { userId } = req.query;          // <-- caller-supplied
  const { videoId } = req.params;

  if (!isValidObjectId(videoId)) throw new ApiError(400, "Invalid video ID");
  if (!isValidObjectId(userId))
    return res.status(200).json(new ApiResponse(200, { result: false }, "USER NOT LOGGED IN"));

  await User.findByIdAndUpdate(userId, { $pull: { watchHistory: toObjectId(videoId) } });
  await User.findByIdAndUpdate(userId, {
    $push: { watchHistory: { $each: [toObjectId(videoId)], $position: 0, $slice: 50 } },
  });
  ...
});
```

`req.user` is never consulted. The only check on `userId` is that it is a syntactically valid ObjectId. Anyone who knows a user ID can write to that user's watch history.

## Exploit

```bash
# no cookie, no token, no account required
curl -X POST "https://your-api.example/api/v1/users/history/<any-video-id>?userId=<victim-user-id>"
```

Getting a victim's user ID is trivial and unauthenticated:

- `GET /api/v1/search/q/a` returns every matching user with `_id` (`searchUserText.controller.ts:28`)
- `GET /api/v1/homepage/:username` returns `_id` (`homepage.controller.ts:23`)
- `GET /api/v1/feeds` returns owner objects on every item

So the full chain is: hit `/search/q/a` to harvest IDs, then loop.

The write itself is bounded, since `$slice: 50` caps the array, but that cap is what makes the attack *effective* rather than merely noisy. Fifty writes completely replaces a victim's history with attacker-chosen videos. Their `/history` page then shows content they never watched.

## Why it matters

Watch history is not a trivial field. Three distinct harms:

1. **Fabricated evidence about a person's behaviour.** The victim's own history page becomes a record of things they did not do. If the platform ever surfaces history to anyone else, or uses it for recommendations, that fabrication propagates. Someone could plant a history of content that is embarrassing, or in some jurisdictions incriminating, on an account they do not control.

2. **Destruction of the user's real data.** Fifty pushes evict every genuine entry. There is no undo and no audit trail.

3. **It is a write primitive on the `User` collection reachable with no credentials.** Today it is constrained to `$push`/`$pull` on `watchHistory` with a validated ObjectId. That is a narrow escape, and it holds only as long as nobody widens this handler. The structural problem is an unauthenticated route that mutates an arbitrary user document, and that is what needs fixing, not just this field.

Note the reverse direction is correctly protected: `GET /users/history` uses `verifyJWT` and reads `req.user._id`. So the *read* is safe and the *write* is not, which is an unusual and telling asymmetry. It suggests the write endpoint was built for the client's convenience rather than designed.

## Root cause: the `?userId=` pattern

This is not an isolated slip. Passing the acting user's identity as a query parameter is a pattern used throughout the API:

| Endpoint | File | Uses `?userId=` |
| --- | --- | --- |
| `POST /users/history/:videoId` | `addToWatchHistory.ts:9` | writes to it |
| `GET /videos/:videoId` | `getVideoById.ts:11` | like status |
| `GET /comments/v/:video_ID` | `comment.controller.ts:207` | like status |
| `GET /comments/t/:tweet_ID` | `comment.controller.ts:321` | like status |
| `GET /comments/c/:comment_ID` | `comment.controller.ts:430` | like status |
| `GET /tweets/:tweetId` | `fetchTweet.ts:13` | like status |
| `GET /homepage/:username` | `homepage.controller.ts:12` | subscribe status |
| `GET /search/q/:text` | `searchUserText.controller.ts:13` | like status |
| `GET /users/channel/:username` | `getUserChannelProfile.ts:10` | as `adminId` |

The read endpoints leak far less (you learn whether some user liked some video), but they share the same flaw: **the server is trusting the client's claim about who it is.** Fixing only `addToWatchHistory` leaves the pattern in place for the next endpoint someone adds.

## The fix

### Step 1. Protect this route and take the identity from the token

```ts
// server/src/routes/user.routes.ts
userRouter.route("/history/:videoId").post(requireAuth, addToWatchHistory);
```

```ts
// server/src/controllers/userControllers/addToWatchHistory.ts
const addToWatchHistory = asyncHandler(async (req, res) => {
  const userId = req.user!._id;                     // from the verified token
  const { videoId } = req.params;

  if (!isValidObjectId(videoId)) throw new ApiError(400, "INVALID VIDEO ID");

  // confirm the video exists and is visible before recording it
  const video = await Video.findOne({ _id: videoId, isPublished: true }).select("_id");
  if (!video) throw new ApiError(404, "VIDEO NOT FOUND");

  // single atomic update instead of two round trips
  await User.updateOne({ _id: userId }, { $pull: { watchHistory: video._id } });
  await User.updateOne(
    { _id: userId },
    { $push: { watchHistory: { $each: [video._id], $position: 0, $slice: 50 } } }
  );

  return res.status(200).json(new ApiResponse(200, { recorded: true }, "WATCH HISTORY UPDATED"));
});
```

The `$pull`-then-`$push` sequence has to stay as two operations, because MongoDB rejects `$pull` and `$push` on the same field in one update, but both must be scoped to the authenticated user, and the video existence check closes a second small hole: today you can insert *any* valid ObjectId into a history array, including IDs of videos that do not exist.

### Step 2. Client: stop sending `userId`

```ts
// client/src/hooks/data-fetching/useUpdateWatchHistory.ts
const useUpdateWatchHistory = () =>
  useMutation({
    mutationKey: ["update-watch-history"],
    mutationFn: async ({ videoId }: { videoId: string }) =>
      apiClient.post(`/users/history/${videoId}`).then((r) => r.data),
  });
```

The `userId` parameter is removed from the hook's signature, so every caller that passes it becomes a TypeScript error, which is how you find them all.

Handle the anonymous case on the client: only call this hook when `useAuth().user` exists. The server no longer has a "USER NOT LOGGED IN" success path (it returns 401), so the client must not call it for logged-out viewers.

### Step 3. Kill the pattern everywhere else

Introduce `optionalAuth`, a middleware that populates `req.user` when a valid token is present and moves on silently when it is not. Then every read endpoint in the table above drops its `?userId=` parameter and reads `req.user?._id`.

That middleware is specified in `suggestions/05.optional-auth-middleware.md`. It also replaces the ad-hoc inline version currently in `server/src/routes/view.route.ts:10-16`, which is broken in its own way: it only checks `req.headers.authorization`, but this app authenticates with **cookies**, so for a normal logged-in browser user it never runs `verifyJWT` and `req.user` is always undefined.

## Interaction with other documents

- `suggestions/05.optional-auth-middleware.md` is the systematic fix. **Implement that first**, then this document's Step 1 and Step 2 are two small edits within it. Doing this document alone leaves eight other endpoints on the same broken pattern.
- `08.user-object-overexposure.md` and `09.email-addresses-exposed-on-public-endpoints.md` supply the user IDs that make this exploitable at scale. Closing those raises the cost of the attack but does not fix it. IDs also leak through the feed, which is public by design.
- `suggestions/06.single-http-client-with-interceptors.md`. Step 2's rewrite assumes the shared `apiClient`. If you do this before that refactor, keep the raw `fetch` and just drop the query parameter.
- Does **not** conflict with `03.no-csrf-protection-with-cross-site-cookies.md`. Adding `requireAuth` here makes the route cookie-dependent and therefore CSRF-relevant; the CSRF token requirement from document 03 applies to it once protected.
