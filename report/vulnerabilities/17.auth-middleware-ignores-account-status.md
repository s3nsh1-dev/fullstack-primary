# 17. Authentication middleware ignores suspension and deactivation

- **Rank: 5 / 10**
- **Side: Server**
- **Category:** Broken access control
- **Location:** `server/src/middleware/auth.middleware.ts:19-50`

## The issue

`verifyJWT` verifies the signature, loads the user, and admits the request:

```ts
const decodedToken = jwt.verify(token, env.ACCESS_TOKEN_SECRET);

let user = null;
if (isAccessPayloadCorrect(decodedToken) && typeof decodedToken === "object" && "_id" in decodedToken) {
  user = await User.findById(decodedToken._id).select("-password -refreshToken");
} else {
  throw new ApiError(400, "INVALID TOKEN");
}

if (!user) throw new ApiError(401, "INVALID ACCESS TOKEN");
req.user = user;
next();
```

It never checks `isSuspended` or `isDeactivated`, even though the document is already loaded and both fields are right there.

The checks exist elsewhere:

- `loginUser.ts:38-45`. Blocks suspended users, and *reactivates* deactivated ones.
- `refreshAccessToken.ts:42-48`. Blocks both.
- `searchUserText.controller.ts`, `homepage.controller.ts`, `getUserChannelProfile.ts`, `feed.controller.ts` filter both out of read results.

So the rule is enforced on the two token-issuing paths and on public reads, but not on the path every authenticated request actually takes.

## Why it matters

A suspended or deactivated user keeps full write access for the remaining lifetime of their access token, up to 15 minutes.

Fifteen minutes is not nothing when the action is deliberate. A user who deactivates their account and then keeps their tab open can continue posting tweets, commenting, liking, subscribing, and uploading videos for the rest of that window. If suspension is ever wired up to a moderation action, the moderator suspends an account and the account keeps operating while they watch.

The deactivation case has a visible product bug attached to it. `deactivateUser` sets `isDeactivated: true` and clears the caller's cookies. But the public read endpoints filter deactivated users out of search, feed, and homepage, so a deactivated user who still has a valid token in another tab can create a tweet that:

- is written successfully (no status check on the write path),
- is invisible in the feed (the owner `$lookup` filters them out),
- and stays orphaned in the database.

The account is simultaneously active enough to write and inactive enough to be invisible.

There is a second, quieter problem in the same function:

```ts
} catch (error: any) {
  throw new ApiError(401, error?.message || "INVALID ACCESS TOKEN");
}
```

The `try/catch` wraps the database call as well as the JWT verification. So a Mongo connection failure inside `User.findById` is reported to the client as **401 Unauthorized** rather than 503. Users get logged out during a database blip, and the real error never reaches `error.log` because it was converted before the error middleware saw it. It also means `error.message`, potentially a driver-internal message, is passed straight through to the client.

## The fix

```ts
// server/src/middleware/auth.middleware.ts
import jwt from "jsonwebtoken";

const requireAuth = asyncHandler(async (req, _res, next) => {
  const token =
    req.cookies?.accessToken ||
    req.header("Authorization")?.replace("Bearer ", "");

  if (!token) throw new ApiError(401, "UNAUTHENTICATED REQUEST");

  let decoded: jwt.JwtPayload;
  try {
    decoded = jwt.verify(token, env.ACCESS_TOKEN_SECRET) as jwt.JwtPayload;
  } catch {
    // only JWT failures become 401 — nothing else is inside this try
    throw new ApiError(401, "INVALID OR EXPIRED ACCESS TOKEN");
  }

  if (typeof decoded !== "object" || typeof decoded._id !== "string") {
    throw new ApiError(401, "MALFORMED TOKEN PAYLOAD");
  }

  // outside the try: a DB failure here must surface as 5xx, not 401
  const user = await User.findById(decoded._id).select(
    "_id username fullname email avatar coverImage isDeactivated isSuspended tokenVersion"
  );

  if (!user) throw new ApiError(401, "INVALID ACCESS TOKEN");

  if (user.isSuspended) {
    throw new ApiError(403, "ACCOUNT IS SUSPENDED");
  }
  if (user.isDeactivated) {
    throw new ApiError(403, "ACCOUNT IS DEACTIVATED");
  }
  if ((decoded.tokenVersion ?? 0) !== (user.tokenVersion ?? 0)) {
    throw new ApiError(401, "SESSION EXPIRED, PLEASE LOG IN AGAIN");
  }

  req.user = user;
  next();
});
```

Four changes:

1. **Status checks added.** 403, not 401, because the caller *is* authenticated and simply not permitted. The client should distinguish these: a 401 means "try refreshing your token", a 403 means "do not retry, show a message".
2. **The `try` block wraps only `jwt.verify`.** Database errors now propagate to the error middleware and produce a correct 5xx with a logged stack trace.
3. **Explicit field selection** instead of `-password -refreshToken`. Same allowlist principle as `08.user-object-overexposure.md`. `req.user` is returned wholesale by `getCurrentUser` and `checkUserAuthDetails`, so whatever is selected here is shipped to the browser. Note this list drops `watchHistory`, `isAdmin`, and the `suspension*` fields.
4. **`tokenVersion` check** from `10.password-change-does-not-revoke-sessions.md`. Included here because it is the same conditional block and the same document load. Implementing them separately means touching this function twice.

Rename `verifyJWT` to `requireAuth` while you are here. It describes the intent rather than the mechanism, and it pairs naturally with the `optionalAuth` middleware introduced in `suggestions/05.optional-auth-middleware.md`. That is a mechanical rename across 12 route files.

### One decision to make: what does deactivation mean?

`loginUser.ts:42-45` silently *undoes* deactivation:

```ts
if (matchedUser.isDeactivated) {
  matchedUser.isDeactivated = false;
  await matchedUser.save({ validateBeforeSave: false });
}
```

Logging in reactivates the account automatically. But `refreshAccessToken.ts:46` **rejects** deactivated users outright. So the two token-issuing paths disagree: login says "welcome back", refresh says "denied".

There is also an explicit `POST /users/reactivate-user` endpoint (`reactivateUser.ts`) which requires `verifyJWT`, meaning it requires a valid token, which a deactivated user cannot obtain via refresh. So the dedicated reactivation endpoint is unreachable by exactly the users it is for.

Pick one model:

- **Deactivation is reversible by logging in.** Keep the `loginUser` behaviour, remove the check from `refreshAccessToken`, and delete `reactivateUser` as redundant. Simplest, and matches what most products do.
- **Deactivation requires explicit reactivation.** Remove the auto-reactivation from `loginUser`, and make `reactivateUser` a public endpoint that takes credentials directly rather than requiring an existing token.

I recommend the first. But whichever you choose, the current state, three components each implementing a different rule, must not survive.

## Interaction with other documents

- `10.password-change-does-not-revoke-sessions.md` adds the `tokenVersion` field and the payload change. **Same function, same edit**. Implement both at once.
- `19.dead-privilege-fields.md` recommends deleting `isAdmin` and the `suspension*` detail fields while **keeping** `isSuspended` as a plain boolean. The check above uses only the boolean, so the two documents are consistent. Do not remove `isSuspended` itself.
- `suggestions/05.optional-auth-middleware.md` defines `optionalAuth`, which shares this function's token-parsing logic. Factor the common part out rather than copying it.
- `08.user-object-overexposure.md` defines the field allowlist used in the `.select()` above.
- `suggestions/16.consistent-response-envelope.md`. The client needs to handle 403 differently from 401. Currently `useRefreshUser` treats any failure as logged-out, which for a suspended account produces a confusing silent logout instead of an explanation.
