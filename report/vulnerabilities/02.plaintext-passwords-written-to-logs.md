# 02. Plaintext passwords written to application logs

- **Rank: 9 / 10**
- **Side: Server**
- **Category:** Sensitive data exposure / insufficient logging hygiene
- **Location:** `server/src/middleware/requestLogger.middleware.ts:18-22`, `server/src/services/logger.service.ts:85-93`

## The issue

The request logger records the full request body for every mutating method:

```ts
if (["POST", "PUT", "PATCH"].includes(req.method)) {
  logData.body = req.body;
}
logService.http("Incoming request", logData);
```

There is no allowlist, no denylist, and no redaction. `req.body` is passed to Winston, which serialises it as JSON into `logs/http.log` (the file transport is registered when `NODE_ENV === "production"`).

This is not theoretical. It has already happened in this repository. `server/logs/http.log` currently contains:

```
"password":"justinbeiber"
```

That is a real credential sitting in a file on disk in cleartext.

## What is captured

Every route that takes a secret in a POST/PATCH body is affected:

| Route | Secret leaked into `http.log` |
| --- | --- |
| `POST /api/v1/users/login` | `password` |
| `POST /api/v1/users/register` | `password`, `email`, `fullname` |
| `POST /api/v1/users/change-password` | `currentPassword` **and** `newPassword` |
| `PATCH /api/v1/users/update-account` | new `email` |
| `POST /api/v1/contact` | submitter's name, email, full message body |

The change-password case is the worst of the set: it captures the old and the new password in the same log line, so a log reader gets a working credential regardless of when they read it.

## Why it matters

Passwords in `user.model.ts` are correctly bcrypt-hashed before storage (`passwordMiddlewareEncryption`, cost 10). That protection is completely undone by this log. An attacker who gets read access to the log file skips the hashes entirely and reads the credentials directly.

Log files are consistently the softest target in a deployment because they are treated as non-sensitive:

- They are shipped to third-party aggregators (Datadog, Logtail, Better Stack, Papertrail) where a much larger set of people have read access than have database access.
- On Render/Railway/Fly they are visible in the web dashboard to anyone with any role on the project.
- They are included in support bundles, pasted into issue trackers, and attached to bug reports.
- They survive database rotation, secret rotation, and password resets. A password logged today is still readable in an archived log after the user has changed it, and people reuse passwords across sites, so the value extends well past your app.

There is a second, quieter problem: this makes the logs themselves a compliance liability. Retaining plaintext credentials is a reportable data-protection failure in most jurisdictions, independent of whether anyone actually reads them.

## The fix

Three parts. All three are needed; the first alone is not sufficient.

### Part 1. Redact at the logging boundary

Never trust the caller to hand you safe data. Filter inside the logger, so any future route is covered automatically.

```ts
// server/src/utils/redact.ts
const SENSITIVE_KEYS = new Set([
  "password",
  "currentpassword",
  "newpassword",
  "confirmpassword",
  "token",
  "accesstoken",
  "refreshtoken",
  "authorization",
  "cookie",
  "apikey",
  "secret",
]);

export const redact = (value: unknown, depth = 0): unknown => {
  if (depth > 6 || value === null || typeof value !== "object") return value;
  if (Array.isArray(value)) return value.map((v) => redact(v, depth + 1));

  return Object.fromEntries(
    Object.entries(value as Record<string, unknown>).map(([key, val]) =>
      SENSITIVE_KEYS.has(key.toLowerCase())
        ? [key, "[REDACTED]"]
        : [key, redact(val, depth + 1)]
    )
  );
};
```

### Part 2. Stop logging request bodies at all

Redaction is a safety net, not a strategy. A request body is high-volume, high-risk, and low-diagnostic-value. Log the shape, not the content:

```ts
// server/src/middleware/requestLogger.middleware.ts
export function requestLogger(req: Request, res: Response, next: NextFunction): void {
  const startTime = Date.now();
  const requestId = randomUUID();
  res.setHeader("x-request-id", requestId);

  const originalEnd = res.end.bind(res);
  res.end = function (...args: Parameters<typeof originalEnd>): Response {
    logService.http("request", {
      requestId,
      method: req.method,
      route: req.route?.path ?? req.path,
      status: res.statusCode,
      durationMs: Date.now() - startTime,
      userId: req.user?._id ? String(req.user._id) : undefined,
      // deliberately absent: body, query values, headers
    });
    return (originalEnd as (...a: Parameters<typeof originalEnd>) => Response)(...args);
  } as typeof res.end;

  next();
}
```

Note this also collapses two log lines per request into one, which halves log volume, and adds a request ID you can correlate against errors.

The same body-logging problem exists in the error handler at `server/src/middleware/error.middleware.ts:229-237`, which logs `body`, `query`, and `params` for any 5xx. Apply `redact()` there, or drop `body` entirely.

### Part 3. Purge the existing logs

The current files are contaminated. Fixing the code does not fix them.

```bash
cd server
# inspect what is in there before deleting, if you want a record of scope
grep -c 'password' logs/http.log

rm -f logs/*.log
```

`logs/` is already covered by `server/.gitignore:57`, and `git ls-files` confirms nothing under `server/logs/` is tracked, so this never reached your Git history. Good. But if these logs were ever shipped to a hosting dashboard or a log aggregator, delete them there too, and treat every password submitted during that window as compromised.
