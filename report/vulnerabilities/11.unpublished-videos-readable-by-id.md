# 11. Unpublished (private) videos are readable by anyone with the ID

- **Rank: 6 / 10**
- **Side: Server**
- **Category:** Broken object-level authorization
- **Location:** `server/src/controllers/videoControllers/getVideoById.ts:14-31`, `server/src/routes/video.route.ts:46`

## The issue

The app has a publish/unpublish feature. `toggleVideoPublishStatus` (`server/src/controllers/videoControllers/toggleVideoPublishStatus.ts`) flips `isPublished`, correctly checks ownership, and is exposed in the UI through `client/src/components/Videos/EditVideoOptions.tsx`. Unpublishing is presented to the user as making a video private.

`getVideoById` does not honour it:

```ts
const fetchedVideo = await Video.findById(videoId).populate(
  "owner",
  "_id fullname avatar username coverImage"
);
```

No `isPublished` filter. No owner check. The route is unauthenticated:

```ts
videoRouter.route("/:videoId")
  .delete(verifyJWT, deleteVideo)
  .patch(verifyJWT, multerUpload.single("thumbnail"), updateVideo)
  .get(getVideoById);          // <-- public
```

So `GET /api/v1/videos/<id>` returns an unpublished video to anyone, including `videoFile`, the Cloudinary URL of the actual media.

## Why it matters

Every other read path in the codebase filters correctly, which is what makes this one a genuine bug rather than a design choice:

| Endpoint | Filters `isPublished`? |
| --- | --- |
| `getAllVideos` (`getAllVideos.ts:31`) | yes, `matchStage.isPublished = true` |
| `getFeed` (`feed.controller.ts:16`) | yes, `{ $match: { isPublished: true } }` |
| `searchingText` (`searchUserText.controller.ts:32`) | yes |
| `getPlaylistById` (`getPlaylistById.ts:42`) | yes |
| `getAllVideosWithoutRestriction` | no, but it is `verifyJWT` + scoped to `req.user._id`, which is correct and intentional |
| **`getVideoById`** | **no, and it is public** |

The user's mental model is "unpublished means nobody can see it". The actual behaviour is "unpublished means it does not appear in listings, but the URL still works". That gap is exactly the shape of an access-control bug that gets exploited: the owner believes the content is withdrawn and acts accordingly.

Realistic paths to the ID:

- The video was published, got a link shared, and was then unpublished. Every existing link still works. This is the common case and requires no attack at all.
- ObjectIds embed a 4-byte timestamp and a monotonic counter, so IDs created in the same window are highly correlated. Given one video ID, adjacent ones are guessable at a rate far better than random.
- The ID leaks through `GET /users/profile/:userId` in the `watchHistory` array (see `08.user-object-overexposure.md`).

Worth noting: because the response includes `videoFile`, the raw Cloudinary delivery URL, the media itself is then fetchable directly, outside your API, with no further checks. Your API is the only access control on that URL, and it is not applying any.

## The fix

```ts
// server/src/controllers/videoControllers/getVideoById.ts
const getVideoById = asyncHandler(async (req, res) => {
  const { videoId } = req.params;
  if (!isValidObjectId(videoId)) throw new ApiError(400, "INVALID VIDEO_ID");

  const viewerId = req.user?._id;          // requires optionalAuth on the route

  const video = await Video.findById(videoId).populate(
    "owner",
    PUBLIC_USER_FIELDS
  );
  if (!video) throw new ApiError(404, "VIDEO NOT FOUND");

  const isOwnerViewing = viewerId && isOwner(video.owner._id, viewerId);
  if (!video.isPublished && !isOwnerViewing) {
    // 404, not 403 — do not confirm the video exists to someone who cannot see it
    throw new ApiError(404, "VIDEO NOT FOUND");
  }

  const [likesCount, likedByViewer] = await Promise.all([
    Like.countDocuments({ video: video._id }),
    viewerId ? Like.exists({ video: video._id, likedBy: viewerId }) : null,
  ]);

  return res.status(200).json(
    new ApiResponse(
      200,
      { video, isLikedByUser: Boolean(likedByViewer), likesCount },
      "VIDEO FETCHED SUCCESSFULLY"
    )
  );
});
```

Four things changed:

1. **`isPublished` is enforced, with an owner exception.** The owner must still be able to preview their own unpublished video, because the client's edit page depends on it.
2. **The failure is 404, not 403.** Returning 403 tells the caller "this video exists but you may not see it", which is itself a disclosure. 404 is indistinguishable from a nonexistent ID.
3. **`isLikedByUser` comes from `req.user`, not `req.query.userId`.** The current code trusts a caller-supplied `userId` (`getVideoById.ts:11`), the same pattern documented in `07.unauthenticated-write-to-any-users-watch-history.md`. Here it only leaks whether some user liked some video, but it is the same flaw and should go with the rest.
4. **The two `Like` queries run in parallel** rather than sequentially. Minor, but the current code awaits `Like.exists` and then `Like.countDocuments` back to back for no reason.

### Also fix the sibling endpoints

Two other public endpoints touch videos without a publish check:

- **`addToWatchHistory`.** After the fix in document 07, add `isPublished: true` to the video lookup so unpublished videos cannot be inserted into a history.
- **`incrementView`** (`view.controller.ts:20`) calls `Video.findById(videoId)` with no publish check, so views can be added to an unpublished video. Add the filter.
- **`getUserPlaylists`** (`getUserPlaylists.ts:23-43`). The `$lookup` into videos has **no** `{ $match: { isPublished: true } }` sub-pipeline, unlike `getPlaylistById` which does. So the playlist *list* view leaks unpublished videos that `getPlaylistById` correctly hides. That inconsistency is a bug in its own right.

## Interaction with other documents

- `suggestions/05.optional-auth-middleware.md` supplies `req.user` on this public route. Without it, `viewerId` is always undefined and owners lose the ability to preview their own unpublished videos, so **apply that middleware first**, or the fix regresses the edit page.
- `suggestions/08.service-layer-extraction.md` proposes a single `findVisibleVideo(videoId, viewer)` function used by every read path. That is the durable fix: the visibility rule lives in one place instead of being re-derived in six controllers, which is how the inconsistencies in the table above arose.
- `09.email-addresses-exposed-on-public-endpoints.md` defines `PUBLIC_USER_FIELDS`, used in the `populate` above. Note the current code populates `coverImage` on a video's owner, which the video page does not render. The shared projection is fine either way.
- `20.silent-authorization-failures.md` is the same family: authorization decisions that either do not happen or do not surface.
