# 08. Extract a service layer; collapse the duplicated controllers

- **Rank: 7 / 10**
- **Side: Server**
- **Effort: Large.** Best done incrementally, module by module

## Current picture

Controllers do everything: HTTP parsing, validation, authorization, database queries, aggregation pipelines, and response formatting. There are 60+ controller files and no layer beneath them.

The visible consequence is duplication, and the duplication is where the inconsistencies live.

### Near-identical files

`getAllVideos.ts` and `getAllVideosWithoutRestriction.ts` are 97 and 99 lines and differ in **two places**: one reads `userId` from `req.query`, the other from `req.user._id`; one adds `isPublished: true` to the match stage, the other does not. Everything else is copied: the pagination guard, the `$facet`, the projection, the response shape.

The three like-toggles (`toggleVideoLike.ts`, `toggleCommentLike.ts`, `toggleTweetLike.ts`) are the same 49 lines with one field name changed. Same for the three `is*Liked` files and the three `getLiked*` files.

The three comment-fetch handlers in `comment.controller.ts` (lines 205, 317, 427) are ~110 lines each of the same aggregation with a different `$match` key.

### Duplication breeds divergence

This is the real cost. Copies drift, and the drift is exactly where the bugs are:

- `getPlaylistById.ts:42` filters `{ $match: { isPublished: true } }` inside the video `$lookup`. `getUserPlaylists.ts:23-43` does not. So the playlist list leaks unpublished videos that the playlist detail view correctly hides.
- `getTweetComments` at `comment.controller.ts:409` checks the like with `Like.exists({ video: toObjectId(tweet_ID) })`, the **`video`** field, for a tweet ID. Copied from `getVideoComments` and not adapted. `isLiked` is always `false` there.
- `getCommentsComment` at line 520 uses `toObjectId(String(req.user?._id))` on a route with no auth middleware, so `req.user` is always `undefined` and this becomes `new ObjectId("undefined")`, which **throws**, a 500 whenever a client passes a valid `userId` query parameter.
- `deleteComment` uses `Like.findOneAndDelete` (one document) where `deleteVideo` and `deleteTweet` use `Like.deleteMany`. See `vulnerabilities/20`.
- Pagination response fields differ across controllers: `havePrevPage`, `hasPrevPage`, `hasPreviousPage`.

Every one of those is a copy that was not updated. That is the argument for the layer.

## Proposed picture

Three layers with clear responsibilities:

```
route     → HTTP shape: path, middleware chain, schema
controller→ translate HTTP ↔ domain; no business logic, no queries
service   → business rules, authorization, database access
```

### Example: the video read path

```ts
// server/src/services/video.service.ts
import { Video } from "../models/video.model";
import ApiError from "../utils/ApiError";
import { isOwner } from "../utils/checkIsOwner";
import { PUBLIC_USER_FIELDS } from "../constants/projections";
import type { Types } from "mongoose";

type Viewer = { _id: Types.ObjectId } | undefined;

/**
 * The single definition of "can this viewer see this video".
 * Every read path goes through here so the rule cannot drift.
 */
export const findVisibleVideo = async (videoId: string, viewer: Viewer) => {
  const video = await Video.findById(videoId).populate("owner", PUBLIC_USER_FIELDS);
  if (!video) throw new ApiError(404, "VIDEO NOT FOUND");

  const viewerOwnsIt = viewer && isOwner(video.owner._id, viewer._id);
  if (!video.isPublished && !viewerOwnsIt) {
    throw new ApiError(404, "VIDEO NOT FOUND");   // 404, not 403 — do not confirm existence
  }
  return video;
};

/** Visibility filter for list queries. One place, used by every listing. */
export const visibilityFilter = (ownerId: Types.ObjectId, viewer: Viewer) =>
  viewer && String(viewer._id) === String(ownerId)
    ? { owner: ownerId }                          // own channel: include drafts
    : { owner: ownerId, isPublished: true };      // anyone else: published only

export const listVideosByOwner = async (
  ownerId: Types.ObjectId,
  viewer: Viewer,
  { skip, limit, sortField, sortDir, search }: ListOptions
) => {
  const match: Record<string, unknown> = visibilityFilter(ownerId, viewer);
  if (search) {
    const re = new RegExp(escapeRegex(search), "i");
    match.$or = [{ title: re }, { description: re }];
  }
  const [result] = await Video.aggregate([
    { $match: match },
    { $sort: { [sortField]: sortDir } },
    { $facet: { data: [{ $skip: skip }, { $limit: limit }, { $project: VIDEO_CARD_PROJECTION }],
                totalCount: [{ $count: "count" }] } },
  ]);
  return { videos: result.data, total: result.totalCount[0]?.count ?? 0 };
};
```

Both video-list controllers collapse to one:

```ts
// server/src/controllers/videoControllers/getAllVideos.ts
export const getAllVideos = asyncHandler(async (req, res) => {
  const { ownerId } = req.validatedQuery as VideoListQuery;
  const page = getPageParams(req);

  const { videos, total } = await listVideosByOwner(
    toObjectId(ownerId), req.user, { ...page, ...sortFrom(req) }
  );

  return res.status(200).json(
    new ApiResponse(200, { videos, ...buildPageMeta(total, page) }, "VIDEOS FETCHED SUCCESSFULLY")
  );
});
```

`getAllVideosWithoutRestriction.ts` is **deleted**. Its behaviour, "show me my own drafts too", is now what `visibilityFilter` does automatically when the viewer is the owner. That is not just less code: it is the fix for the `getUserPlaylists` leak above, because the same filter now applies wherever videos are listed.

### Example: the polymorphic like toggle

```ts
// server/src/services/like.service.ts
type LikeTarget = "video" | "comment" | "tweet";

const MODEL: Record<LikeTarget, Model<any>> = { video: Video, comment: Comment, tweet: Tweet };

export const toggleLike = async (target: LikeTarget, targetId: string, userId: Types.ObjectId) => {
  const exists = await MODEL[target].exists({ _id: targetId });
  if (!exists) throw new ApiError(404, `${target.toUpperCase()} NOT FOUND`);

  try {
    await Like.create({ [target]: targetId, likedBy: userId });
    return { liked: true };
  } catch (error: any) {
    if (error?.code !== 11000) throw error;      // relies on the unique index
    await Like.deleteOne({ [target]: targetId, likedBy: userId });
    return { liked: false };
  }
};

export const countLikes = (target: LikeTarget, targetId: string) =>
  Like.countDocuments({ [target]: targetId });

export const hasLiked = async (target: LikeTarget, targetId: string, userId?: Types.ObjectId) =>
  userId ? Boolean(await Like.exists({ [target]: targetId, likedBy: userId })) : false;
```

Six controller files become three thin handlers over one service. And `toggleLike` adds a check none of the three currently has: **the target must exist.** Today you can like a nonexistent video ID and a `Like` document is created pointing at nothing.

## What not to do

**Do not create an abstract `BaseService` with generic CRUD.** It looks like the same idea and it is not. Generic CRUD pushes the interesting part, the authorization rule and the visibility filter, back into the controller, which is where the duplication started. The value here is that `findVisibleVideo` encodes a *specific business rule* in one place. A generic `findById<T>` encodes nothing.

**Do not do this all at once.** The migration order below is by value, not by module count.

## Migration order

1. **`video.service.ts`.** Highest duplication, and it carries the `isPublished` fix (`vulnerabilities/11`) and the `getUserPlaylists` leak.
2. **`like.service.ts`.** Six files to three, and it needs the unique indexes from `07.database-indexes-and-unique-constraints.md`.
3. **`comment.service.ts`.** One aggregation builder for the three fetch handlers; fixes the `tweet_ID`-as-`video` bug and the `ObjectId("undefined")` crash.
4. **`user.service.ts`.** Projections and the visibility rules for deactivated/suspended accounts.

Each step ships independently. Nothing else needs to change while a module is being migrated.
