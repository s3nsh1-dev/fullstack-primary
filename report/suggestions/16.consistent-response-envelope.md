# 16. One response envelope, honestly used

- **Rank: 6 / 10**
- **Side: Both**
- **Effort: Small-medium.** Mostly mechanical

## Current picture

`ApiResponse` is a good idea applied inconsistently.

```ts
// server/src/utils/ApiResponse.ts
class ApiResponse {
  constructor(statusCode: number, data: any, message: string = "SUCCESS") {
    this.statusCode = statusCode;
    this.data = data;
    this.message = message;
    this.success = statusCode < 400;
  }
}
```

**The envelope's `statusCode` disagrees with the HTTP status.**

```ts
// registerUser.ts:65 — HTTP 201, body says 200
return res.status(201).json(new ApiResponse(200, createdUser, "USER REGISTERED SUCCESSFULLY"));

// changeCurrentPassword.ts:25 — HTTP 400 with success:false, sent via the *success* path
return res.status(400).json(new ApiResponse(400, false, "INCORRECT PASSWORD"));
```

The second is the more damaging: a failed password change returns through `res.json` rather than `throw new ApiError`, so `axios` treats a 400 as... a 400, and rejects, but the client's `useChangeUserPassword` catch block turns it into `` `PASSWORD CHANGING REQUEST FAILED: ${error}` `` and the actual message is lost. Meanwhile every other failure in the app arrives via the error middleware with a different body shape.

**Two different error shapes.** Success responses have `{statusCode, data, message, success}`. The error middleware emits `{success, message, errors, data, stack?}`, with no `statusCode`. So a client cannot read `response.data.statusCode` reliably.

**`data` is sometimes a raw driver result.**

```ts
// deletePlaylist.ts
new ApiResponse(200, { result: deletedPlaylist }, "PLAYLIST DELETED SUCCESSFULLY")
// → data: { result: { acknowledged: true, deletedCount: 0 } }

// toggleSubscription.ts, toggleVideoLike.ts, deleteVideo.ts — same pattern
```

The client receives MongoDB internals. `deletedCount: 0` is the only signal that the delete did not happen, and no client checks it (`vulnerabilities/20`).

**Inconsistent nesting.** `{user}`, `{video}`, `{tweet}`, `{playlist}`, `{data: channel[0]}`, `{result}`, `{stats}`, or the bare value. `getUserChannelProfile.ts:101` returns `{ data: channel[0] }` inside `ApiResponse.data`, so the client reads `response.data.data.data`.

**Booleans as `data`.** `changeCurrentPassword` returns `data: true`. `isVideoLiked` returns `data: false`. Not wrong, but it means the client cannot use one unwrapping helper.

The client absorbs all of this: `client/src/constants/responseTypes.ts` declares a bespoke type per endpoint, and each hook unwraps differently.

## Proposed picture

### One shape, two variants

```ts
// server/src/utils/ApiResponse.ts
export type SuccessBody<T> = {
  success: true;
  message: string;
  data: T;
  requestId?: string;
};

export type ErrorBody = {
  success: false;
  message: string;
  errors: unknown | null;
  data: null;
  requestId?: string;
  stack?: string;              // development only
};

export class ApiResponse<T> {
  readonly success = true as const;
  constructor(readonly data: T, readonly message: string = "SUCCESS") {}
}
```

`statusCode` is **removed from the body**. It duplicates information the HTTP layer already carries, it is a second source of truth that can disagree, and no correct client reads it in preference to `response.status`. That is the one breaking change here, and it removes a whole class of inconsistency.

Sending becomes:

```ts
// server/src/utils/respond.ts
export const ok = <T>(res: Response, data: T, message = "SUCCESS", status = 200) =>
  res.status(status).json({ success: true, message, data, requestId: res.req.requestId });
```

```ts
return ok(res, { user: createdUser }, "USER REGISTERED SUCCESSFULLY", 201);
```

The HTTP status is now passed once, in one place, and cannot disagree with itself.

### Errors always go through `throw`

```ts
// changeCurrentPassword.ts — before
if (!isPasswordValid) {
  return res.status(400).json(new ApiResponse(400, false, "INCORRECT PASSWORD"));
}
// after
if (!isPasswordValid) throw new ApiError(401, "CURRENT PASSWORD IS INCORRECT");
```

401 rather than 400: the supplied credential was wrong, which is an authentication failure, not a malformed request. Either is defensible; the important part is that it goes through the same path as every other error so the body shape is uniform.

Grep for the pattern:

```bash
cd server && grep -rn "res.status(4\|res.status(5" src/controllers/
```

Every hit is a place bypassing the error middleware.

### Meaningful payloads, not driver results

```ts
// deletePlaylist.ts
const result = await Playlist.deleteOne({ _id: playlistId, owner: req.user._id });
if (result.deletedCount === 0) throw new ApiError(404, "PLAYLIST NOT FOUND OR YOU DO NOT OWN IT");
return ok(res, { id: playlistId }, "PLAYLIST DELETED SUCCESSFULLY");

// toggleVideoLike.ts
return ok(res, { liked: true, likeCount }, "LIKE ADDED");
```

`{liked, likeCount}` is what the UI needs. `{acknowledged, deletedCount}` is what the driver returned. Only one of those belongs in an API.

### Consistent nesting rule

Adopt one rule and apply it: **a single resource is nested under its name; a collection uses the pagination contract.**

```ts
ok(res, { user });                              // single
ok(res, { video });                             // single
ok(res, paginated(items, total, params));       // collection → { items, pagination }
ok(res, { liked: true, likeCount: 42 });        // an action result
```

Fix `getUserChannelProfile.ts:101` (`{data: channel[0]}` → `{channel: channel[0]}`) and `getWatchHistory` (`{data: result.videos, ...}` → the paginated shape).

### Client

```ts
// client/src/lib/apiClient.ts
export type ApiEnvelope<T> = {
  success: boolean;
  message: string;
  data: T;
  requestId?: string;
};

export const unwrap = async <T>(p: Promise<{ data: ApiEnvelope<T> }>): Promise<T> =>
  (await p).data.data;
```

One helper replaces the per-hook unwrapping. `client/src/constants/responseTypes.ts` shrinks from a type per endpoint to a type per *resource*, wrapped generically:

```ts
// before
export type UserLoginResponseType = { statusCode: number; data: {...}; message: string; success: boolean };
export type VideoResponseType = { statusCode: number; data: {...}; message: string; success: boolean };
// ... one per endpoint

// after
type SessionResponse = { user: PublicUser };
type VideoResponse = { video: Video; isLikedByUser: boolean; likesCount: number };
// the envelope is applied by ApiEnvelope<T> at the call site
```

### Error handling on the client

```ts
export class ApiError extends Error {
  constructor(message: string, readonly status: number, readonly details?: unknown,
              readonly requestId?: string) { super(message); }
}
```

Thrown by the response interceptor (`06.single-http-client-with-interceptors.md`). Every component can then render `error.message`, the server's actual message, instead of the current mix of hardcoded strings and stringified axios errors.

`requestId` is the practical payoff: a user reporting a failure can quote an ID that appears verbatim in your logs (`11.structured-logging-with-redaction.md`).

## Also worth fixing in the error middleware

**Two dead branches.**

```ts
// error.middleware.ts:205
else if (error.array || (error.errors && Array.isArray(error.errors)))
```

`error.array` is the express-validator check. If you adopt zod (`02.central-validation-layer.md`) this branch never fires. Note also that `ApiError.errors` is typed `string | null` but the check tests `Array.isArray(error.errors)`, and those cannot both be right.

**The `errors` field can leak internals.** `ApiError.errors` is `any` and is echoed to the client. `handleMongooseDuplicateKeyError` builds `` `${field} '${value}' already exists` ``, echoing a submitted email back to whoever probed for it. Harmless for a username, less so for an email.

**Stack traces are gated on `NODE_ENV === "development"`**, which is correct. Verify `NODE_ENV` is actually set to `production` in your deployment. With the fallback in `dotenvHelper.ts` defaulting to `"development"` (`vulnerabilities/01`), an unset variable means stack traces are served to the public.

## Migration

Breaking for the client, so do it per-endpoint:

1. Add `ok()`, `ApiEnvelope<T>`, and the client `unwrap`.
2. Convert one resource at a time (users, then videos, then …), server and client hooks together.
3. Remove `statusCode` from the envelope last, once nothing reads it.

```bash
cd client && grep -rn "\.statusCode" src/ | wc -l   # → 0 before step 3
```
