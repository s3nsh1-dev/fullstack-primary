# 09. One pagination contract, server and client

- **Rank: 7 / 10**
- **Side: Both**
- **Effort: Small-medium.** One helper, ~12 controllers, matching client types

## Current picture

Ten controllers implement pagination, and no two agree.

**Different defaults.** `getAllVideos` 5, `feed` 30, `getEveryLikedContent` 10, `getUserPlaylists` 10, `getWatchHistory` 10, `comment.controller` 10, `getUserTweets` and `getUserChannelSubscribersCount` have no default at all and 400 if the parameters are missing.

**Different validation.** Some validate, some clamp, some ignore:

```ts
// getAllVideos.ts:15-24 — rejects, but does not cap
if (!page || !limit || page < 1 || limit < 1 || Number.isNaN(page) || Number.isNaN(limit))
  throw new ApiError(400, "INVALID PAGINATION PARAMETER");

// getEveryLikedContent.ts:9-10 — no validation whatsoever
const page = Number(req.query.page) || 1;
const limit = Number(req.query.limit) || 10;

// comment.controller.ts:207 — destructured with defaults, then Number()'d, unchecked
const { page = 1, limit = 10, userId } = req.query;
```

**Different response field names.** This is the one that hurts the client:

| Controller | "has previous page" field |
| --- | --- |
| `getAllVideos.ts:76` | `havePrevPage` |
| `getUserTweets.ts:92` | `havePrevPage` |
| `getUserPlaylists.ts:55` | `havePrevPage` |
| `getUserChannelSubscribersCount.ts:52` | `hasPrevPage` |
| `getEveryLikedContent.ts:19` | `hasPreviousPage` |
| `getWatchHistory.ts` | `hasPreviousPage` |

Three spellings of one concept. And the "total" field is `totalVideos`, `totalSubscribers`, `totalDocs`, `totalHistory`, or `length` depending on which endpoint you ask.

**Different envelope nesting.** `comment.controller` returns `mongoose-aggregate-paginate-v2`'s own shape (`{docs, totalDocs, page, totalPages, hasNextPage, ...}`) nested under `comments`, while everything else returns a hand-built flat object.

The client pays for all of it. `client/src/constants/responseTypes.ts` carries a separate type per endpoint, and each list component re-implements "is there a next page" against whichever spelling that endpoint uses. `useIntersectionObserver`-driven infinite scroll has to be wired per endpoint.

## Proposed picture

### Server

```ts
// server/src/utils/pagination.ts
import type { Request } from "express";

export const MAX_LIMIT = 100;

export type PageParams = { page: number; limit: number; skip: number };

export const getPageParams = (req: Request, defaultLimit = 20): PageParams => {
  const rawPage = Number(req.query.page);
  const rawLimit = Number(req.query.limit);

  const page = Number.isFinite(rawPage) ? Math.max(1, Math.floor(rawPage)) : 1;
  const limit = Number.isFinite(rawLimit)
    ? Math.min(MAX_LIMIT, Math.max(1, Math.floor(rawLimit)))
    : defaultLimit;

  return { page, limit, skip: (page - 1) * limit };
};

export type PageMeta = {
  total: number;
  totalPages: number;
  currentPage: number;
  limit: number;
  hasNextPage: boolean;
  hasPrevPage: boolean;
};

export const buildPageMeta = (total: number, { page, limit }: PageParams): PageMeta => {
  const totalPages = Math.max(1, Math.ceil(total / limit));
  return {
    total,
    totalPages,
    currentPage: page,
    limit,
    hasNextPage: page < totalPages,
    hasPrevPage: page > 1,
  };
};

/** Every paginated endpoint returns exactly this. */
export type Paginated<T> = { items: T[]; pagination: PageMeta };

export const paginated = <T>(items: T[], total: number, params: PageParams): Paginated<T> => ({
  items,
  pagination: buildPageMeta(total, params),
});
```

**Clamp, do not reject.** `?limit=5000` returns 100 rather than a 400. Rejecting means every client must know the cap; clamping means the server enforces it and nobody has to. It also removes an error path from twelve controllers.

**`items`, not a per-resource key.** Currently the array is called `videos`, `tweets`, `playlists`, `subscribers`, `liked`, `comments`, or `data` depending on the endpoint. A single name lets the client write one generic list hook. If you find `items` too anonymous in the response, the alternative is to keep the resource name and standardise only `pagination`, which still gets you most of the benefit. Pick one and apply it everywhere.

Applied:

```ts
// getUserPlaylists.ts
const params = getPageParams(req, 10);
const [result] = await Playlist.aggregate([ /* ... $facet ... */ ]);

return res.status(200).json(
  new ApiResponse(
    200,
    paginated(result.data, result.total[0]?.total ?? 0, params),
    "USER PLAYLISTS FETCHED SUCCESSFULLY"
  )
);
```

### If you adopt the validation layer

`02.central-validation-layer.md` proposes a zod `pagination` schema. **That supersedes `getPageParams`**. Do not run both:

```ts
export const pagination = z.object({
  page:  z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
});
```

```ts
const { page, limit } = req.validatedQuery as z.infer<typeof pagination>;
const skip = (page - 1) * limit;
```

`buildPageMeta` and `paginated` stay either way, since they are the response half, which zod does not cover.

### Client

```ts
// client/src/constants/responseTypes.ts
export type PageMeta = {
  total: number;
  totalPages: number;
  currentPage: number;
  limit: number;
  hasNextPage: boolean;
  hasPrevPage: boolean;
};

export type Paginated<T> = { items: T[]; pagination: PageMeta };
```

One generic infinite-scroll hook replaces the per-endpoint versions:

```ts
// client/src/hooks/usePaginatedQuery.ts
export const usePaginatedQuery = <T>(
  key: readonly unknown[],
  path: string,
  limit = 20
) =>
  useInfiniteQuery({
    queryKey: [...key, limit],
    initialPageParam: 1,
    queryFn: ({ pageParam }) =>
      unwrap<Paginated<T>>(
        apiClient.get(path, { params: { page: pageParam, limit } })
      ),
    getNextPageParam: (last) =>
      last.pagination.hasNextPage ? last.pagination.currentPage + 1 : undefined,
  });
```

```ts
// a call site
const { data, fetchNextPage, hasNextPage } = usePaginatedQuery<Playlist>(
  playlistKeys.byUser(userId), `/playlists/user/${userId}`, 10
);
const playlists = data?.pages.flatMap((p) => p.items) ?? [];
```

`getNextPageParam` is written once instead of per endpoint. That matters because it is currently derived from a differently-named field in each hook, and one of those spellings is wrong somewhere by definition.

### The aggregate-paginate outlier

`comment.controller.ts` uses `mongoose-aggregate-paginate-v2`, which returns its own shape. Two options:

- **Keep the plugin, reshape the output.** `paginated(result.docs, result.totalDocs, params)`. Minimal change.
- **Drop the plugin, use `$facet`** like every other controller. The plugin adds a dependency for something `$facet` already does, and it means `Comment` is the only model needing `.plugin()`. It is also worth noting `getVideoComments` runs `aggregatePaginate` *and* a separate `countDocuments` for the same count, which the plugin already computed.

I would drop it. That removes `mongoose-aggregate-paginate-v2` and `@types` from `package.json` entirely, since `Video` declares the plugin but never calls `aggregatePaginate`.

## Migration

The two shapes can coexist. Convert one endpoint plus its client hook at a time.

Order by client pain: `getUserPlaylists` and `getUserTweets` (both feed infinite-scroll components), then comments, then the rest.

```bash
cd server
grep -rn "havePrevPage\|hasPreviousPage\|hasPrevPage" src/ | wc -l   # progress metric → 0
```
