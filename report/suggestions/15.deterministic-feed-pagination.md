# 15. Make the feed deterministic (it currently randomises its sort per request)

- **Rank: 6 / 10**
- **Side: Server**
- **Effort: Small-medium**

## Current picture

```ts
// server/src/controllers/feed.controller.ts
const [videos, tweets] = await Promise.all([
  Video.aggregate([
    { $match: { isPublished: true } },
    { $sort: { createdAt: Math.floor((Math.random() * 10) % 2) == 0 ? 1 : -1 } },
    { $skip: skip },
    { $limit: contentLimit },
    ...
  ]),
  Tweet.aggregate([
    { $sort: { createdAt: Math.floor((Math.random() * 10) % 2) == 0 ? 1 : -1 } },
    { $skip: skip },
    { $limit: contentLimit },
    ...
  ]),
]);

const feed = shuffle([...shuffle(videos), ...shuffle(tweets)]);
```

The intent is reasonable: a feed that does not always show the same items in the same order. The implementation makes pagination incoherent.

**The sort direction is re-rolled per request, and independently per collection.** Page 1 might sort videos ascending and tweets descending; page 2 flips both. So `$skip: 20` on page 2 skips into a *differently ordered* result set than page 1 was drawn from.

The concrete effect for a user scrolling an infinite feed:

- **Duplicates.** An item at position 5 in descending order sits near the end in ascending order. Flip direction between pages and you serve it twice.
- **Gaps.** Items in the middle of the collection are skipped past in both orderings and never appear.
- **Non-reproducible bugs.** "I saw the same video three times" cannot be reproduced, because the next request rolls differently.

Roughly half of all page transitions flip direction per collection, so this is not an edge case.

Three smaller problems in the same handler:

**`hasNextPage` is wrong.**

```ts
const hasNextPage = videos.length === contentLimit || tweets.length === contentLimit;
```

Post-`$lookup` filtering (`{ $match: { owner: { $exists: true, $ne: null } } }` drops content whose owner is deactivated or suspended) means a full page can come back short even when more content exists. The client then stops scrolling early. Conversely a page that happens to be exactly `contentLimit` after filtering reports a next page that may be empty.

**`Math.floor((Math.random() * 10) % 2) == 0`** is an elaborate way to write `Math.random() < 0.5`. Worth noting only because the complexity obscures what the line does.

**`limit` is unbounded**. `?limit=1000000` is honoured (`vulnerabilities/13`).

**`shuffle` mutates its argument** (`utils/algorithms.ts`, Fisher-Yates in place, returning the same array). It happens to be safe here because the arrays are freshly created, but a shuffle that mutates its input is a trap.

## Proposed picture

The underlying tension: you want variety, and you want stable pagination. `$skip`-based offset pagination cannot give you both, because the ordering must be identical across every request in a session.

### Option A. Cursor pagination with a stable sort (recommended)

Give up per-request randomness in exchange for correctness. Variety comes from content changing over time, which for a growing platform is enough.

```ts
export const getFeed = asyncHandler(async (req, res) => {
  const limit = Math.min(50, Math.max(1, Number(req.query.limit) || 30));
  const cursor = typeof req.query.cursor === "string" ? req.query.cursor : null;

  // Composite cursor: createdAt is not unique, so ties need _id to break them.
  const cursorFilter = cursor
    ? (() => {
        const [ts, id] = Buffer.from(cursor, "base64url").toString().split("|");
        return {
          $or: [
            { createdAt: { $lt: new Date(ts) } },
            { createdAt: new Date(ts), _id: { $lt: toObjectId(id) } },
          ],
        };
      })()
    : {};

  const perCollection = Math.ceil(limit / 2);

  const [videos, tweets] = await Promise.all([
    Video.aggregate([
      { $match: { isPublished: true, ...cursorFilter } },
      { $sort: { createdAt: -1, _id: -1 } },
      { $limit: perCollection + 1 },        // +1 to detect a next page
      ...ownerLookup,
    ]),
    Tweet.aggregate([
      { $match: cursorFilter },
      { $sort: { createdAt: -1, _id: -1 } },
      { $limit: perCollection + 1 },
      ...ownerLookup,
    ]),
  ]);

  const merged = [...videos, ...tweets]
    .sort((a, b) =>
      b.createdAt - a.createdAt || String(b._id).localeCompare(String(a._id))
    )
    .slice(0, limit);

  const last = merged.at(-1);
  const nextCursor = last
    ? Buffer.from(`${last.createdAt.toISOString()}|${last._id}`).toString("base64url")
    : null;

  return res.status(200).json(
    new ApiResponse(200, { items: merged, nextCursor, hasNextPage: nextCursor !== null },
      "FEED FETCHED SUCCESSFULLY")
  );
});
```

Three properties this gets you:

- **No duplicates or gaps**, even when new content is published mid-scroll. Offset pagination shifts every item when a new one is inserted at the top; a cursor does not.
- **`hasNextPage` is accurate**, because it is derived from fetching one extra row rather than inferred from the page being full.
- **The `_id` tiebreaker matters.** `createdAt` is not unique, and several videos published in the same second are common on a seeded database. Without the tiebreaker their relative order is undefined, and items near the boundary get duplicated or skipped.

Requires the indexes from `07.database-indexes-and-unique-constraints.md`: `{isPublished: 1, createdAt: -1}` on videos and `{createdAt: -1}` on tweets. Without them each page is a collection scan plus an in-memory sort.

### Option B. Seeded randomness

If per-session variety is genuinely wanted, make the randomness *stable within a session* by seeding it from a value the client passes back:

```ts
const seed = typeof req.query.seed === "string" ? req.query.seed : randomUUID();

const [videos] = await Promise.all([
  Video.aggregate([
    { $match: { isPublished: true } },
    // deterministic per-document score from the seed
    { $addFields: { _rank: { $function: {
        body: "function(id, seed) { let h = 0; const s = id + seed; for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) | 0; return h; }",
        args: ["$_id", seed],
        lang: "js",
    } } } },
    { $sort: { _rank: 1, _id: 1 } },
    { $skip: skip },
    { $limit: perCollection },
  ]),
]);
// return `seed` in the response; the client sends it back on every page
```

Honest assessment: `$function` requires server-side JavaScript enabled, is **not available on Atlas free/shared tiers**, cannot use an index (so every page is a full scan plus sort), and is slow. It works, but the cost is high for the benefit.

A cheaper approximation of the same idea: precompute a random float on each document at creation (`randomKey: { type: Number, default: Math.random, index: true }`) and sort by `randomKey` with a cursor. That is index-backed. The order is then fixed per document rather than per session, different from "shuffled per user", but it does decouple feed order from recency, which is probably the actual goal.

The three side by side:

| | A. Cursor + stable sort | B. Seeded `$function` | Stored `randomKey` |
| --- | --- | --- | --- |
| Pagination is coherent | yes | yes | yes |
| Index-backed | yes | no, full scan and sort per page | yes |
| Runs on Atlas free/shared | yes | **no**, server-side JS is unavailable | yes |
| Order varies per viewer | no | yes | no, fixed per document |
| Decouples order from recency | no | yes | yes |
| Work to build | low | high | low |

### Recommendation

**Option A.** Deterministic recency ordering with a cursor. It is correct, index-backed, and standard. Introduce genuine ranking later, whether engagement, recency decay or subscriptions, when there is enough content for ordering to matter. `Math.random()` in a `$sort` is not a ranking strategy, and replacing it with one is a separate, later project.

### While you are in this file

`shuffle` in `utils/algorithms.ts` should not mutate:

```ts
export function shuffle<T>(array: readonly T[]): T[] {
  const out = [...array];
  for (let i = out.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [out[i], out[j]] = [out[j], out[i]];
  }
  return out;
}
```

If you adopt Option A, `shuffle` has no remaining caller in the feed. Check whether anything else uses it (`ShuffleSearchResult.tsx` on the client has its own) before deleting.

## Client changes

`useFetchFeed` moves from `useInfiniteQuery` with numeric page params to cursor params:

```ts
useInfiniteQuery({
  queryKey: feedKeys.page(limit),
  initialPageParam: null as string | null,
  queryFn: ({ pageParam }) =>
    unwrap<FeedPage>(apiClient.get("/feeds", { params: { limit, cursor: pageParam } })),
  getNextPageParam: (last) => last.nextCursor,
});
```

Note the feed is now the one endpoint **not** using the standard `Paginated<T>` shape from `09.shared-pagination-contract.md`, because cursor pagination has no page numbers or total count. That is a deliberate, documented exception rather than an inconsistency. Define a `Cursored<T>` type alongside `Paginated<T>`.
