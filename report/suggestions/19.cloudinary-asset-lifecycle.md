# 19. Cloudinary assets are never deleted and their public IDs are never stored

- **Rank: 6 / 10**
- **Side: Server**
- **Effort: Small**

## Current picture

The user schema declares fields for tracking Cloudinary assets:

```ts
// server/src/models/user.model.ts:45-46
avatarPublicId:     { type: String },
CoverImagePublicId: { type: String },
```

**Nothing ever writes them.**

```ts
// server/src/controllers/userControllers/updateUserAvatar.ts:24
updatedUser.avatar = avatar.url;          // the URL is saved
const userWithNewAvatar = await updatedUser.save();
// avatar.public_id is available on the response object and is discarded
```

```ts
// server/src/controllers/userControllers/updateUserCoverImage.ts:25-33
const updatedUser = await User.findByIdAndUpdate(req.user._id,
  { $set: { coverImage: coverImage.url } },   // public_id discarded here too
  { new: true }
);
```

```ts
// server/src/controllers/userControllers/registerUser.ts:51-58
const userEntry = await User.create({
  avatar: checkAvatarCloudinaryUpload?.url,
  coverImage: checkCoverImageCloudinaryUpload?.url,
  // no avatarPublicId, no CoverImagePublicId
  ...
});
```

Three write paths, zero populate the fields. There is even a controller written to backfill them — `updateUsersWithPublicId.ts` — but it is commented out of the router (`user.routes.ts:18,61`).

### Consequences

**Old avatars are never deleted.** Each avatar change uploads a new asset and abandons the previous one. A user who changes their picture ten times leaves ten orphaned images in your Cloudinary account, billed against your storage and transformation quota, forever.

Compare with `updateVideo.ts:39`, which *does* delete the previous thumbnail:

```ts
const foo = await deleteFromCloudinary(video.thumbPublicId);
```

So the video path handles this correctly (because `Video` stores `thumbPublicId`) and the user path does not. The inconsistency is purely a consequence of the missing fields.

**Account deletion cannot clean up.** `vulnerabilities/06` proposes collecting `user.avatarPublicId` and `user.CoverImagePublicId` before deleting. Those are `undefined` for every existing user, so the cleanup silently does nothing for avatars and cover images. **This document must be applied before that cleanup is meaningful.**

**Deleted users' images stay publicly accessible.** Cloudinary URLs are unauthenticated. An avatar uploaded by a user who later deletes their account remains fetchable by anyone with the URL, indefinitely.

**No orphan recovery path.** Without stored public IDs there is no way to reconcile "assets in Cloudinary" against "assets referenced in the database" — you cannot even measure the problem.

### A related bug

`updateUserCoverImage.ts` uploads to Cloudinary **before** checking authentication:

```ts
export const updateUserCoverImage = asyncHandler(async (req, res) => {
  if (!req.file) throw new ApiError(400, "COVER FILE IS REQUIRED");
  const coverImage = await uploadOnCloudinary(coverImageLocalPath, "cover-image");   // upload
  if (!coverImage || !coverImage.url) throw new ApiError(400, "UPLOAD FAILED...");
  if (!req?.user || !req.user?._id) throw new ApiError(401, "USER NOT AUTHENTICATED");   // check
```

The route has `verifyJWT`, so `req.user` is always present in practice and this cannot be exploited. But the ordering means that if the guard ever becomes load-bearing, an unauthenticated request would still push an asset to Cloudinary before being rejected. `updateUserAvatar.ts` checks first, correctly — another inconsistency between two files doing the same job.

## Proposed picture

### Store the public IDs

```ts
// server/src/controllers/userControllers/updateUserAvatar.ts
export const updateUserAvatar = asyncHandler(async (req, res) => {
  if (!req.file) throw new ApiError(400, "AVATAR FILE IS REQUIRED");

  const user = await User.findById(req.user!._id).select(`${PRIVATE_USER_FIELDS} avatarPublicId`);
  if (!user) throw new ApiError(404, "USER NOT FOUND");

  const previousPublicId = user.avatarPublicId;

  const uploaded = await uploadOnCloudinary(req.file.path, "profile-image");
  if (!uploaded?.url) throw new ApiError(502, "AVATAR UPLOAD FAILED");

  user.avatar = uploaded.secure_url;
  user.avatarPublicId = uploaded.public_id;
  await user.save({ validateModifiedOnly: true });

  // Delete the old asset only after the new one is committed, and never
  // let a cleanup failure fail the request the user actually made.
  if (previousPublicId && previousPublicId !== uploaded.public_id) {
    deleteFromCloudinary(previousPublicId).catch((error) =>
      logService.warn("orphaned cloudinary asset", { publicId: previousPublicId, error })
    );
  }

  return ok(res, { user }, "AVATAR UPDATED SUCCESSFULLY");
});
```

Two ordering points:

- **Delete after the database commit.** Deleting first means a failed save leaves the user with a URL pointing at a deleted asset — a broken image.
- **Cleanup failure is logged, not thrown.** The user's avatar change succeeded; an orphaned asset is an accounting problem, not a reason to report failure.

Apply the same shape to `updateUserCoverImage` (with the auth check moved to the top) and add both IDs in `registerUser`:

```ts
const userEntry = await User.create({
  fullname, email, password, username,
  avatar: avatarUpload.secure_url,
  avatarPublicId: avatarUpload.public_id,
  coverImage: coverUpload?.secure_url,
  CoverImagePublicId: coverUpload?.public_id,
});
```

### Use `secure_url`, not `url`

Every upload path currently saves `response.url`, which is the `http://` variant. That is why `getSecureUrl.ts` exists on the client:

```ts
export const getSecureUrl = (url: string | undefined | null) => {
  if (!url) return "";
  return url.replace("http://", "https://");
};
```

and why `makingURLsecure.ts` exists on the server as a one-off migration (unrouted, and note it sends no response so it would hang if ever wired up).

Saving `secure_url` at write time removes the need for both. Cloudinary's config already sets `secure: true` (`utils/cloudinary.ts:15`), which makes `url` https in newer SDK versions — but `secure_url` is explicit and correct regardless.

Keep `getSecureUrl` on the client until existing rows are migrated:

```js
// mongosh — one-off
db.videos.updateMany({ videoFile: /^http:/ }, [{ $set: {
  videoFile: { $replaceOne: { input: "$videoFile", find: "http://", replacement: "https://" } },
  thumbnail: { $replaceOne: { input: "$thumbnail", find: "http://", replacement: "https://" } },
}}]);
db.users.updateMany({ avatar: /^http:/ }, [{ $set: {
  avatar: { $replaceOne: { input: "$avatar", find: "http://", replacement: "https://" } },
}}]);
```

### Backfill the missing public IDs

Cloudinary URLs contain the public ID, so existing rows can be recovered:

```
https://res.cloudinary.com/<cloud>/image/upload/v1234567890/profile-image/abc123.jpg
                                                            └────── public_id ──────┘
```

```ts
// server/scripts/backfillPublicIds.ts — run once
const extractPublicId = (url: string): string | null => {
  const match = url.match(/\/upload\/(?:v\d+\/)?(.+?)\.[a-z0-9]+$/i);
  return match?.[1] ?? null;
};

const users = await User.find({
  $or: [
    { avatar: { $exists: true, $ne: null }, avatarPublicId: { $in: [null, ""] } },
    { coverImage: { $exists: true, $ne: null }, CoverImagePublicId: { $in: [null, ""] } },
  ],
}).select("avatar coverImage avatarPublicId CoverImagePublicId");

for (const user of users) {
  const updates: Record<string, string> = {};
  if (user.avatar && !user.avatarPublicId) {
    const id = extractPublicId(user.avatar);
    if (id) updates.avatarPublicId = id;
  }
  if (user.coverImage && !user.CoverImagePublicId) {
    const id = extractPublicId(user.coverImage);
    if (id) updates.CoverImagePublicId = id;
  }
  if (Object.keys(updates).length) await User.updateOne({ _id: user._id }, { $set: updates });
}
```

This is roughly what the commented-out `updateUsersWithPublicId.ts` was for. Run it as a script rather than exposing it as a route — an unauthenticated bulk-mutation endpoint is not something to leave in a router even commented out. Delete that file afterwards.

### Rename the field

`CoverImagePublicId` is PascalCase while every other field is camelCase. Rename to `coverImagePublicId` during the backfill, since you are touching those documents anyway:

```js
db.users.updateMany(
  { CoverImagePublicId: { $exists: true } },
  { $rename: { CoverImagePublicId: "coverImagePublicId" } }
);
```

### Orphan sweep

Once IDs are stored, reconciliation becomes possible:

```ts
// server/scripts/findOrphanedAssets.ts
const { resources } = await cloudinary.api.resources({
  type: "upload", prefix: "profile-image/", max_results: 500,
});

const referenced = new Set(
  (await User.find({ avatarPublicId: { $ne: null } }).select("avatarPublicId"))
    .map((u) => u.avatarPublicId)
);

const orphans = resources
  .filter((r: any) => !referenced.has(r.public_id))
  .filter((r: any) => Date.now() - new Date(r.created_at).getTime() > 24 * 60 * 60 * 1000);

console.log(`${orphans.length} orphaned assets, ${orphans.reduce((s: number, r: any) => s + r.bytes, 0) / 1e6} MB`);
```

Run it in report mode first. Only delete once the numbers look right — a bug here deletes live avatars. The 24-hour age filter avoids racing with an in-flight upload.
