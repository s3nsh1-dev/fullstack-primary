# 05. Replace the `?userId=` pattern with an optionalAuth middleware

- **Rank: 8 / 10**
- **Side: Both**
- **Effort: Small-medium.** One middleware, nine controllers, nine client hooks

## Current picture

Nine endpoints ask the client to declare who is making the request, via a query parameter:

| Endpoint | File:line | Parameter | Used for |
| --- | --- | --- | --- |
| `POST /users/history/:videoId` | `addToWatchHistory.ts:9` | `userId` | **writes to that user** |
| `GET /videos/:videoId` | `getVideoById.ts:11` | `userId` | like status |
| `GET /comments/v/:video_ID` | `comment.controller.ts:207` | `userId` | like status |
| `GET /comments/t/:tweet_ID` | `comment.controller.ts:321` | `userId` | like status |
| `GET /comments/c/:comment_ID` | `comment.controller.ts:430` | `userId` | like status |
| `GET /tweets/:tweetId` | `fetchTweet.ts:13` | `userId` | like status |
| `GET /tweets/user/:userId` | `getUserTweets.ts:57` | path param | like status |
| `GET /homepage/:username` | `homepage.controller.ts:12` | `userId` | subscribe status |
| `GET /users/channel/:username` | `getUserChannelProfile.ts:10` | `adminId` | subscribe status |
| `GET /search/q/:text` | `searchUserText.controller.ts:13` | `userId` | like status |

The server is trusting the client's claim about its own identity. For the reads that means anyone can ask "has user X liked video Y?", a small leak. For the one **write** it means anyone can modify any user's watch history, documented as `vulnerabilities/07`.

There is also a broken attempt at optional auth already in the codebase:

```ts
// server/src/routes/view.route.ts:10-16
viewRouter.post("/:videoId",
  (req, res, next) => {
    if (req.headers.authorization) {
      return verifyJWT(req, res, next);
    }
    next();
  },
  incrementView
);
```

This checks the `Authorization` **header**. The app authenticates with **cookies**. `useIncrementView` sends `credentials: "include"` and no header. So for every real logged-in browser user this branch is skipped, `req.user` is undefined, and `view.controller.ts:41` falls back to the IP+User-Agent fingerprint. Logged-in users are counted as anonymous.

And a third variant: `getUserTweets.ts:57` uses the *channel owner's* ID as the liker:

```ts
{ $eq: ["$likedBy", toObjectId(userId)] }   // userId is the profile being viewed
```

So `isLiked` on a channel's tweet list means "did the channel owner like their own tweet", not "did I like it". A logic bug that the pattern makes easy to write.

## Proposed picture

One middleware that populates `req.user` when a valid token is present and does nothing when it is not.

```ts
// server/src/middleware/auth.middleware.ts
import jwt from "jsonwebtoken";
import { User } from "../models/user.model";
import env from "../config/env";
import ApiError from "../utils/ApiError";
import { asyncHandler } from "../utils/asyncHandler";

const AUTH_USER_FIELDS =
  "_id username fullname email avatar coverImage isDeactivated isSuspended tokenVersion";

/** Extract and verify a token. Returns null for any failure. */
const resolveUser = async (req: Request) => {
  const token =
    req.cookies?.accessToken ||
    req.header("Authorization")?.replace("Bearer ", "");
  if (!token) return null;

  let decoded: jwt.JwtPayload;
  try {
    decoded = jwt.verify(token, env.ACCESS_TOKEN_SECRET) as jwt.JwtPayload;
  } catch {
    return null;
  }
  if (typeof decoded !== "object" || typeof decoded._id !== "string") return null;

  const user = await User.findById(decoded._id).select(AUTH_USER_FIELDS);
  if (!user) return null;
  if (user.isSuspended || user.isDeactivated) return null;
  if ((decoded.tokenVersion ?? 0) !== (user.tokenVersion ?? 0)) return null;

  return user;
};

/** Rejects unauthenticated requests. */
export const requireAuth = asyncHandler(async (req, _res, next) => {
  const user = await resolveUser(req);
  if (!user) throw new ApiError(401, "UNAUTHENTICATED REQUEST");
  req.user = user;
  next();
});

/** Populates req.user when possible; never rejects. */
export const optionalAuth = asyncHandler(async (req, _res, next) => {
  req.user = (await resolveUser(req)) ?? undefined;
  next();
});
```

One caveat on `resolveUser` returning `null` for suspended accounts: `requireAuth` then reports 401 rather than the 403 that `vulnerabilities/17` specifies. If you want the distinction, and you should, so the client can show "your account is suspended" instead of silently logging the user out, have `resolveUser` throw for status failures and return `null` only for missing/invalid tokens, then catch in `optionalAuth`:

```ts
export const optionalAuth = asyncHandler(async (req, _res, next) => {
  try {
    req.user = (await resolveUser(req)) ?? undefined;
  } catch {
    req.user = undefined;      // a suspended user browsing public pages is just anonymous
  }
  next();
});
```

### Controllers

The change is mechanical:

```ts
// before
const { userId } = req.query;
if (userId && isValidObjectId(userId)) { ... }

// after
const viewerId = req.user?._id;
if (viewerId) { ... }
```

`isValidObjectId` checks disappear. `req.user._id` is an ObjectId from a database document, not a string from the network. That removes roughly fifteen validation calls.

`getUserTweets.ts:57` gets a genuine fix, not just a refactor:

```ts
// before — "did the profile owner like their own tweet"
{ $eq: ["$likedBy", toObjectId(userId)] }
// after — "did I like it"
{ $eq: ["$likedBy", req.user?._id ?? null] }
```

`view.controller.ts` gets its fingerprint fixed for free, because `req.user` is now populated for cookie-authenticated users:

```ts
const fingerprint = userId?.toString() || `${ipAddress}-${userAgent}`;
```

Combined with `app.set("trust proxy", 1)` from `03.security-middleware-baseline.md`, `ipAddress` also becomes the real client IP rather than the proxy's.

### Client

Remove the parameter from every hook. Example:

```ts
// client/src/hooks/data-fetching/useFetchSingleVideo.ts
// before
`${URL}/videos/${videoId}?userId=${userId}`
// after
`${URL}/videos/${videoId}`
```

Delete `userId` from each hook's argument type. Every caller passing it becomes a TypeScript error, which is how you find all of them. Several currently pass `user?._id` with an optional chain that silently sends `?userId=undefined`.

## Why this is worth doing beyond the security fix

Three things improve at once:

- **Cache correctness.** Query keys currently embed `userId` (`["video", videoId, userId]`). With identity coming from the cookie, keys simplify, and the bug where a logged-out user's cache entry gets reused for a logged-in one disappears.
- **Fewer round trips of wrongness.** `getVideoById` currently returns `isLikedByUser: false` for a logged-in user whose client forgot to pass `userId`. Silent, and only visible as "the like button doesn't show my like".
- **One place to change.** Adding "and the viewer must not be blocked by the author" later is one middleware edit, not ten.
