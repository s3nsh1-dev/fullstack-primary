# 10. Upload directly to Cloudinary with signed parameters

- **Rank: 7 / 10**
- **Side: Both**
- **Effort: Medium** — new signing endpoint, rewritten upload components, changed upload controllers

## Current picture

Every upload is proxied through your server:

```
browser → multipart POST → Express → multer writes to ./public/temp
       → controller reads the file → Cloudinary SDK uploads it
       → fs.unlink → respond
```

This is the source of an entire vulnerability (`vulnerabilities/04`: no size limit, no type filter, unauthenticated write to a publicly-served directory, orphaned files on failure) plus several operational problems:

**Every byte crosses your server twice.** A 200 MB video upload consumes 200 MB of inbound bandwidth, 200 MB of disk, and 200 MB of outbound bandwidth to Cloudinary. On a small instance that is the whole disk and a large share of the monthly transfer budget.

**Uploads block a request slot.** `publishAVideo` awaits `uploadOnCloudinary` for the video *and then* the thumbnail — sequentially (`publishAVideo.ts:23-27`). A large video holds the connection for minutes.

**Platform request timeouts.** Render and similar hosts cap request duration (often 30-100 s). A slow upload is killed mid-flight, after multer has written the file. The file stays.

**Failures are silent.** `uploadOnCloudinary` swallows every error and returns `undefined`:

```ts
} catch (error) {
  await fs.unlink(localFilePath).catch((error) => {
    logService.info("FAILED: ISSUE IN FILE DELETION", error);
  });
}
```

No rethrow, no error log — the Cloudinary failure is logged at `info` level *as a file-deletion message*, and the caller sees `undefined` and reports a generic 400. Debugging an upload failure from these logs is not possible.

**No progress feedback.** `VideoUploadForm.tsx` cannot show a progress bar because the browser only sees "request in flight" until the whole server-side pipeline finishes.

## Proposed picture

```
browser → GET /api/v1/uploads/signature  (authenticated, cheap)
       ← { signature, timestamp, apiKey, cloudName, folder, ... }
browser → POST direct to Cloudinary with those params  (progress events available)
       ← { public_id, secure_url, duration, bytes, format }
browser → POST /api/v1/videos { title, description, videoPublicId, ... }
```

The file never touches your server.

### Signing endpoint

```ts
// server/src/controllers/uploadController/getUploadSignature.ts
import { v2 as cloudinary } from "cloudinary";
import env from "../../config/env";

const PRESETS = {
  avatar:    { folder: "profile-image",     max_bytes: 5 * 1024 * 1024,   allowed_formats: "jpg,jpeg,png,webp,avif" },
  cover:     { folder: "cover-image",       max_bytes: 8 * 1024 * 1024,   allowed_formats: "jpg,jpeg,png,webp,avif" },
  thumbnail: { folder: "videos-thumbnails", max_bytes: 5 * 1024 * 1024,   allowed_formats: "jpg,jpeg,png,webp,avif" },
  video:     { folder: "videos",            max_bytes: 500 * 1024 * 1024, allowed_formats: "mp4,mov,webm" },
} as const;

export const getUploadSignature = asyncHandler(async (req, res) => {
  const { kind } = req.validatedQuery as { kind: keyof typeof PRESETS };
  const preset = PRESETS[kind];
  if (!preset) throw new ApiError(400, "UNKNOWN UPLOAD KIND");

  const timestamp = Math.round(Date.now() / 1000);

  // Everything signed here is enforced by Cloudinary. A client that alters
  // any of these values produces an invalid signature and is rejected.
  const params = {
    timestamp,
    folder: preset.folder,
    allowed_formats: preset.allowed_formats,
    max_bytes: preset.max_bytes,
    // scope the asset to the uploader so it cannot collide or be guessed
    public_id: `${req.user!._id}/${crypto.randomUUID()}`,
  };

  const signature = cloudinary.utils.api_sign_request(params, env.CLOUDINARY_API_SECRET);

  return res.status(200).json(
    new ApiResponse(200, {
      ...params,
      signature,
      apiKey: env.CLOUDINARY_API_KEY,
      cloudName: env.CLOUDINARY_CLOUD_NAME,
    }, "UPLOAD SIGNATURE ISSUED")
  );
});
```

```ts
uploadRouter.route("/signature").get(requireAuth, expensiveLimiter, validate(signatureSchema), getUploadSignature);
```

The security property that makes this work: **`max_bytes` and `allowed_formats` are part of the signed payload.** Cloudinary validates them server-side. A client that tries to upload a 2 GB file or an `.html` with a signature issued for `max_bytes: 5MB` is rejected by Cloudinary, not by your code. The limits you could not enforce reliably in multer are now enforced by the storage provider.

`CLOUDINARY_API_SECRET` never leaves your server — only the derived signature does, and it is scoped to one upload with a timestamp (Cloudinary rejects signatures older than one hour).

### Client

```ts
// client/src/hooks/useDirectUpload.ts
export const useDirectUpload = () => {
  const [progress, setProgress] = useState(0);

  const upload = async (file: File, kind: UploadKind): Promise<CloudinaryAsset> => {
    const sig = await unwrap<SignaturePayload>(
      apiClient.get("/uploads/signature", { params: { kind } })
    );

    const form = new FormData();
    form.append("file", file);
    form.append("api_key", sig.apiKey);
    form.append("timestamp", String(sig.timestamp));
    form.append("signature", sig.signature);
    form.append("folder", sig.folder);
    form.append("public_id", sig.public_id);

    const resourceType = kind === "video" ? "video" : "image";

    // deliberately plain axios, not apiClient — this must not carry our
    // cookies, our CSRF header, or our baseURL to a third party
    const { data } = await axios.post(
      `https://api.cloudinary.com/v1_1/${sig.cloudName}/${resourceType}/upload`,
      form,
      {
        onUploadProgress: (e) =>
          e.total && setProgress(Math.round((e.loaded * 100) / e.total)),
      }
    );

    return {
      publicId: data.public_id,
      url: data.secure_url,
      duration: data.duration,
      bytes: data.bytes,
      format: data.format,
    };
  };

  return { upload, progress };
};
```

The comment on the axios call matters: using `apiClient` here would send your session cookie and CSRF token to Cloudinary. Use a bare client.

### Controllers accept references

```ts
// publishAVideo.ts
const { title, description, video, thumbnail } = req.body as PublishVideoBody;

// The client can lie about these. Verify against Cloudinary before trusting them.
const [videoAsset, thumbAsset] = await Promise.all([
  cloudinary.api.resource(video.publicId, { resource_type: "video" }),
  cloudinary.api.resource(thumbnail.publicId, { resource_type: "image" }),
]);

// confirm the assets belong to this uploader — public_id is prefixed with their id
if (!videoAsset.public_id.startsWith(`${req.user!._id}/`)) {
  throw new ApiError(403, "ASSET DOES NOT BELONG TO YOU");
}

const created = await Video.create({
  owner: req.user!._id,
  videoFile: videoAsset.secure_url,
  videoPublicId: videoAsset.public_id,
  thumbnail: thumbAsset.secure_url,
  thumbPublicId: thumbAsset.public_id,
  duration: videoAsset.duration,
  title,
  description,
});
```

**The verification step is not optional.** Without it a client can POST any `publicId` — including another user's asset, or a URL pointing anywhere — and your database records it. The `public_id` prefix check is what ties the asset to the uploader. This is the one genuinely new risk the direct-upload model introduces, and it is why the signing endpoint scopes `public_id` to the user ID.

### What gets deleted

- `server/src/middleware/multer.middleware.ts`
- `server/src/utils/cloudinary.ts` (the upload half; keep `deleteFromCloudinary`)
- `server/public/temp/` and `express.static("public")`
- the `cleanupUploads` middleware from `vulnerabilities/04`, which becomes unnecessary
- `multer` and `@types/multer` from `package.json`

### Orphan cleanup

Direct upload introduces one new failure mode: the file uploads successfully, then the user closes the tab before submitting the form. The asset exists in Cloudinary with no database row.

Handle it with a scheduled sweep — list assets in each folder older than 24 hours, check for a matching `videoPublicId`/`avatarPublicId` in Mongo, delete the unmatched ones. This is a background job, not a request-path concern, and it is strictly easier to reason about than the current orphaned-local-file problem.

## Trade-offs

**Against:** more moving parts (two round trips instead of one), the asset-verification step is new logic you must get right, and the orphan sweep is a job you now own.

**For:** the vulnerability class in `vulnerabilities/04` disappears rather than being bounded. Bandwidth and disk cost drop to zero for media. Uploads stop blocking request slots. Progress bars become possible. Platform request timeouts stop mattering.

For a video platform, this is the standard architecture and it is worth the added complexity. If you were only handling avatars, I would say keep the proxy and just add the multer limits.
