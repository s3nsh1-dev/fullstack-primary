# 17. 20 lazy-loaded route components with no Suspense boundary

- **Rank: 7 / 10**
- **Side: Client**
- **Effort: Tiny** — a handful of lines

There is no `<Suspense>` anywhere in the client:

```bash
$ grep -rn "Suspense" client/src/
# no matches
```

`React.lazy` requires a `Suspense` ancestor. That is not a style preference — it is the documented contract. A lazy component throws a promise on first render, and without a boundary to catch it React has nowhere to render a fallback.

The router is `<BrowserRouter>` + `<Routes>` (declarative mode), which does **not** wrap route elements in an implicit Suspense boundary. The data-router APIs (`createBrowserRouter`) do more here; this app does not use them.

Note: I read the code and confirmed the absence, but did not reproduce the runtime behaviour in a browser. Depending on chunk timing and React's internals, the symptom may be an error caught by the root `ErrorBoundary`, or a blank region, and it will show up most reliably on a slow or throttled connection where the chunk does not resolve immediately. Either way, adding the boundary is unambiguously correct and takes two lines — this is not a case where you need to reproduce the failure first.

Two related gaps:

**`ErrorBoundary` cannot recover.** `client/src/components/ui-components/ErrorBoundary.tsx` catches, renders a message, and offers `window.location.reload()`. There is no `resetErrorBoundary`, and it wraps the whole app — so an error inside one route destroys the entire UI including the navbar.

**A chunk load failure is unrecoverable.** If a lazy `import()` rejects — a network blip, or a stale `index.html` referencing a chunk hash that no longer exists after a deploy — the promise rejects and there is no retry. This is a real production failure mode: users with a tab open across a deploy get a hard error on their next navigation.

## Proposed picture

### Add the boundary

```tsx
// client/src/App.tsx
import { lazy, Suspense, useEffect } from "react";
import AppLoadingProgress from "./pages/AppLoadingProgress";

function App() {
  // ...
  return (
    <ThemeProvider theme={getTheme(mode)}>
      <CssBaseline />
      <Box sx={{ mt: (theme) => `${theme.mixins.toolbar.minHeight}px` }}>
        <Suspense fallback={<AppLoadingProgress />}>
          <Routes>
            {/* unchanged */}
          </Routes>
        </Suspense>
      </Box>
    </ThemeProvider>
  );
}
```

`AppLoadingProgress` already exists and is already used as the auth-loading fallback, so there is nothing new to build.

### Better: put the boundary inside the layout

Wrapping `<Routes>` means the navbar unmounts and remounts on every lazy navigation, so the whole shell flashes. Put the boundary around the `<Outlet />` instead, so the chrome stays mounted:

```tsx
// client/src/pages/Navbar.tsx
<Main open={open}>
  <Suspense fallback={<CircularProgressCenter />}>
    <Outlet />
  </Suspense>
</Main>
```

`CircularProgressCenter` also already exists (`components/ui-components/CircularProgressCenter.tsx`). Keep a second `<Suspense>` around `<Routes>` in `App.tsx` for the routes outside the navbar layout (`/test`, `*`).

Nested routes under `/:username` render `ShowVideos`/`ShowTweets`/`ShowPlaylists`/`ShowSubscribed` — themselves lazy — into `Homepage`'s own `<Outlet />`. Add a boundary there too so switching profile tabs shows a spinner in the tab area rather than replacing the profile header.

### Retry chunk loads

```ts
// client/src/utilities/lazyWithRetry.ts
import { lazy, type ComponentType } from "react";

const RELOAD_FLAG = "chunk-reload-attempted";

export const lazyWithRetry = <T extends ComponentType<any>>(
  factory: () => Promise<{ default: T }>
) =>
  lazy(async () => {
    try {
      const module = await factory();
      sessionStorage.removeItem(RELOAD_FLAG);
      return module;
    } catch (error) {
      // A failed dynamic import after a deploy usually means the chunk hash
      // changed. One reload picks up the new index.html. The flag prevents
      // an infinite reload loop when the failure is not deploy-related.
      if (!sessionStorage.getItem(RELOAD_FLAG)) {
        sessionStorage.setItem(RELOAD_FLAG, "1");
        window.location.reload();
        // never resolves; the reload takes over
        return new Promise<{ default: T }>(() => {});
      }
      throw error;
    }
  });
```

Swap `lazy(` for `lazyWithRetry(` in `App.tsx`. The `sessionStorage` guard is the important part — without it, a chunk that genuinely cannot load produces an infinite reload loop.

### Make the ErrorBoundary recoverable and scoped

```tsx
// client/src/components/ui-components/ErrorBoundary.tsx
interface Props { children: ReactNode; fallback?: (error: Error, reset: () => void) => ReactNode; }

class ErrorBoundary extends Component<Props, State> {
  reset = () => this.setState({ hasError: false, error: null });

  render() {
    if (this.state.hasError && this.state.error) {
      if (this.props.fallback) return this.props.fallback(this.state.error, this.reset);
      return (
        <Box sx={sx}>
          <ErrorOutlineIcon sx={{ fontSize: 80, color: "error.main" }} />
          <Typography variant="h4" fontWeight={600}>Oops! Something went wrong</Typography>
          <Typography variant="body1" color="text.secondary">
            {this.state.error.message || "An unexpected error occurred"}
          </Typography>
          <Box sx={{ display: "flex", gap: 1 }}>
            <Button variant="contained" onClick={this.reset}>Try again</Button>
            <Button variant="outlined" onClick={() => window.location.reload()}>Reload</Button>
          </Box>
        </Box>
      );
    }
    return this.props.children;
  }
}
```

Then use a second instance inside the layout, so a failing route does not take down the navbar:

```tsx
<Main open={open}>
  <ErrorBoundary>
    <Suspense fallback={<CircularProgressCenter />}>
      <Outlet />
    </Suspense>
  </ErrorBoundary>
</Main>
```

One caution: `this.state.error.message` is rendered to the user. Once `06.single-http-client-with-interceptors.md` is in place, `ApiError.message` is the server's message — which is fine, since the server controls it. Today some messages are stringified axios errors (`` `PASSWORD CHANGING REQUEST FAILED: AxiosError...` ``), which is not something to show a user.

### Preload on hover

Optional, cheap, and noticeably improves perceived speed:

```tsx
const preloadPlaylist = () => import("./pages/Playlist");
<Link to="/playlists" onMouseEnter={preloadPlaylist}>Playlists</Link>
```

The chunk downloads while the pointer travels to the link, so the navigation is usually instant. Worth adding to the sidebar links in `DrawerContents.tsx`.
