# 20. Remove dead code and add the lint rules that would have caught it

- **Rank: 5 / 10**
- **Side: Both**
- **Effort: Small**

## Current picture

### Code that cannot execute

**`deleteUser.ts:35-67`.** 33 lines of cascade-delete logic wrapped in `if (0)`. The handler reports success and deletes nothing. Filed separately as `vulnerabilities/06`; listed here because it is the clearest example of what these lint rules exist to catch.

**`makingURLsecure.ts`.** An unrouted one-off migration that runs `Video.updateMany` and **never sends a response**. If it were ever wired up, the request would hang until the client timed out. It should be a script, not a controller.

**`updateUsersWithPublicId.ts`.** Imported and commented out in `user.routes.ts:18` and `:61`. Same category: a bulk-mutation backfill sitting in a router. See `19.cloudinary-asset-lifecycle.md` for the script version.

**`mail.service.ts`.** The SMTP implementation, superseded by `mailHttp.service.ts`. Not imported anywhere. It also has TLS verification disabled and debug logging enabled (`vulnerabilities/15`), so leaving it in place is an active liability.

**Guards that can never fire.** Dozens of `if (!result) throw new ApiError(...)` on values that are never falsy: `find()` returns `[]`, `create()` and `save()` reject rather than resolving falsy. Detailed in `vulnerabilities/20`.

**Revoke the Gmail App Password** when `mail.service.ts` goes. An unused credential that still works is still a credential. And remove the five `GMAIL_*` variables from `.env` and the config module.

### Add ESLint to the server

The server has **no ESLint configuration at all**. Only `client/eslint.config.js` exists. This is the gap that let `if (0)` ship.

```bash
cd server
npm i -D eslint @eslint/js typescript-eslint
```

```js
// server/eslint.config.js
import js from "@eslint/js";
import tseslint from "typescript-eslint";

export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  {
    languageOptions: {
      parserOptions: { project: "./tsconfig.json", tsconfigRootDir: import.meta.dirname },
    },
    rules: {
      "no-constant-condition": ["error", { checkLoops: false }],   // catches `if (0)`
      "no-unreachable": "error",
      "no-dupe-else-if": "error",
      "@typescript-eslint/no-unused-vars": ["error", {
        argsIgnorePattern: "^_", varsIgnorePattern: "^_",
      }],
      "@typescript-eslint/no-floating-promises": "error",
      "@typescript-eslint/no-misused-promises": "error",
      "@typescript-eslint/no-explicit-any": "warn",
    },
  },
  { ignores: ["dist/**", "node_modules/**"] }
);
```

```json
"scripts": {
  "lint": "eslint src",
  "lint:fix": "eslint src --fix",
  "typecheck": "tsc --noEmit"
}
```

Three rules earn their place immediately:

- **`no-constant-condition`** flags `if (0)`, which is `vulnerabilities/06`, the highest-impact finding that pure static analysis would have caught.
- **`no-floating-promises`** flags un-awaited async calls. `cloudinary.ts:28` does `fs.unlink(localFilePath).catch(...)` without awaiting, so the function may return before the file is removed.
- **`no-unused-vars`** flags `const foo = await ...` and the unused interface blocks.

`recommendedTypeChecked` requires type information and is slower, but it is what enables the promise rules. Worth it.

### Tighten TypeScript

`strict: true` is already set, which is good. Add:

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "exactOptionalPropertyTypes": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true
  }
}
```

`noUncheckedIndexedAccess` is the valuable one here. It makes `videoList[0].data` a type error unless you handle `undefined`, and that exact pattern appears in `getAllVideos.ts:72`, `getUserTweets.ts:88`, and `getUserPlaylists.ts:52`, each of which would throw on an empty aggregation result.

Expect a batch of errors on first enable. Turn them on one at a time.

### Clean up the `any` escape hatches

`strict: true` is undermined by explicit casts:

```ts
let server: any;                                    // index.ts:8
} catch (error: any) {                              // ~20 occurrences
const pipeline: any[] = [ ... ];                    // comment.controller.ts:209
} as any);                                          // mail.service.ts:28 — hid a real type error
const files = req.files as { [fieldname: string]: Express.Multer.File[] };
```

The `as any` in `mail.service.ts` is the instructive one: it suppressed the error that would have flagged `checkServerIdentity`'s wrong signature (`vulnerabilities/15`). A cast to `any` at a security-relevant boundary is worth treating as a defect in itself.

Replacements:

```ts
let server: import("http").Server | undefined;
} catch (error: unknown) { ... }                    // then narrow with instanceof
const pipeline: PipelineStage[] = [ ... ];          // from mongoose
```

## Why this is ranked 5, not lower

Dead code is not a vulnerability. But two of the most serious findings in this report, the no-op account deletion and the disabled TLS verification, exist *because* there was no automated check that would have flagged them, and both hid in plain sight for months. The lint configuration is a ten-minute change that closes that gap permanently.
