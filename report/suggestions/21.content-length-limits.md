# 21. Bound the length of every user-supplied text field

- **Rank: 6 / 10**
- **Side: Both**
- **Effort: Small**

## Current picture

No user-generated text field has a maximum length — not in the Mongoose schemas, not in the controllers, not in the client forms.

```ts
// tweet.model.ts
content: { type: String, required: true },                    // no maxlength

// comment.model.ts
content: { type: String, required: true },                    // no maxlength

// playlist.model.ts
name:        { type: String, required: true },                // no maxlength
description: { type: String },                                // no maxlength

// video.model.ts
title:       { type: String, required: true, trim: true },    // no maxlength
description: { type: String, required: true, trim: true },    // no maxlength

// user.model.ts
username: { type: String, required: true, unique: true, trim: true },   // no maxlength
fullname: { type: String, required: true, trim: true },                 // no maxlength
```

The controllers only check presence:

```ts
// createTweet.ts — no length check at all
const { content } = req.body;
const tweet = await Tweet.create({ owner: toObjectId(req.user._id as string), content });

// comment.controller.ts:19 — minimum only
if (!content || content.length < 1) throw new ApiError(404, "CONTENT NOT FOUND");

// createPlaylist.ts:12 — minimum only
if (!name || name.length < 1) throw new ApiError(404, "INPUT FIELD MISSING");
```

The only bound in the entire system is `express.json({ limit: "16kb" })` in `app.ts:49`.

The client does not compensate — `CreateTweetForm.tsx`, `AddTweetCommentForm.tsx`, `VideoCommentInput.tsx`, and `CreatePlaylistModal.tsx` all render unbounded `TextField`s with no `maxLength` and no character counter.

## Why 16 kb is not a sufficient limit

It bounds the request, not the damage. A 16 kb tweet is roughly 16,000 characters — about 100× a tweet-length post. What that does:

**Layout destruction.** A single 16 kb comment with no whitespace renders as one unbroken token. Unless every container has `overflow-wrap: anywhere` — and MUI's `Typography` does not by default — it blows out the flex container and breaks the page for everyone viewing that video, not just the author.

**Feed and search bloat.** `getFeed` returns up to `limit` items with full `content`. Thirty 16 kb tweets is a 480 kb JSON response for one feed page. `searchUserText.controller.ts` has no result limit at all (`vulnerabilities/13`), so a search matching many long tweets returns an arbitrarily large payload.

**Database growth.** MongoDB's 16 MB document cap is not the issue; index and working-set size is. A collection of maximum-length comments is ~16 KB/document instead of ~200 bytes — an 80× multiplier on storage and on what has to fit in RAM.

**Unicode amplification.** JavaScript's `.length` counts UTF-16 code units. A string of 8,000 emoji is 16,000 units and passes a naive 16,000-character check, while occupying ~32 kb as UTF-8 — so a byte-based limit and a `.length`-based limit disagree by up to 4×. Combining characters (Zalgo text) stack unboundedly on a single grapheme and break line height in ways CSS cannot contain.

**Username is the sharpest case.** `newUsernameUpdate.ts` writes `req.body.username` with no validation whatsoever (`vulnerabilities/12`). A 16 kb username propagates into every response that populates an owner, and usernames are URL path segments — most servers cap a URL at 8 kb, so a long enough username makes the user's own channel page unreachable.

## Proposed picture

### Schema level — the backstop

```ts
// tweet.model.ts
content: { type: String, required: true, trim: true, maxlength: [1000, "TWEET IS TOO LONG"] },

// comment.model.ts
content: { type: String, required: true, trim: true, maxlength: [2000, "COMMENT IS TOO LONG"] },

// playlist.model.ts
name:        { type: String, required: true, trim: true, maxlength: [100, "NAME IS TOO LONG"] },
description: { type: String, trim: true, maxlength: [500, "DESCRIPTION IS TOO LONG"] },

// video.model.ts
title:       { type: String, required: true, trim: true, maxlength: [150, "TITLE IS TOO LONG"] },
description: { type: String, required: true, trim: true, maxlength: [5000, "DESCRIPTION IS TOO LONG"] },

// user.model.ts
username: { type: String, required: true, unique: true, trim: true, lowercase: true,
            minlength: 3, maxlength: 20, match: /^[a-z0-9_]+$/ },
fullname: { type: String, required: true, trim: true, minlength: 1, maxlength: 80 },
```

Schema validators are the backstop, not the primary control, because they only run on `save()` and on `findOneAndUpdate` when `runValidators: true` is passed — which most update calls in this codebase do not. Several controllers use `findByIdAndUpdate` without it:

```ts
// newUsernameUpdate.ts — validators do NOT run
await User.findByIdAndUpdate(req.user._id, { $set: { username } }, { new: true });
// needs: { new: true, runValidators: true }
```

Audit every `findOneAndUpdate`/`findByIdAndUpdate` and add `runValidators: true`.

### Request level — the real control

```ts
// server/src/schemas/content.schema.ts
import { z } from "zod";

/** Reject unbounded combining marks (Zalgo) that break line rendering. */
const noExcessiveMarks = (s: string) => (s.match(/\p{M}/gu)?.length ?? 0) <= s.length * 0.3;

const text = (min: number, max: number) =>
  z.string()
    .trim()
    .min(min, `must be at least ${min} characters`)
    .max(max, `must be at most ${max} characters`)
    .refine(noExcessiveMarks, { message: "contains excessive combining characters" });

export const createTweetSchema  = { body: z.object({ content: text(1, 1000) }) };
export const createCommentSchema = { body: z.object({ content: text(1, 2000) }) };
export const createPlaylistSchema = {
  body: z.object({ name: text(1, 100), description: text(0, 500).optional().default("") }),
};
export const publishVideoSchema = {
  body: z.object({ title: text(1, 150), description: text(1, 5000) }),
};
```

Request-level validation is where the limit belongs: it runs before any database work, returns a clear message, and cannot be bypassed by an update path that forgot `runValidators`.

### Client level — usability

```tsx
// client/src/components/Tweets/CreateTweetForm.tsx
const MAX = 1000;

<TextField
  multiline
  value={content}
  onChange={(e) => setContent(e.target.value.slice(0, MAX))}
  slotProps={{ htmlInput: { maxLength: MAX } }}
  helperText={`${content.length} / ${MAX}`}
  error={content.length > MAX * 0.95}
/>
<Button disabled={content.trim().length === 0 || content.length > MAX}>Post</Button>
```

The server is what enforces the limit; the client is what stops a user typing 2,000 characters and only then being told no.

### CSS containment regardless

Length limits do not solve rendering of a single unbroken 1,000-character token. Add containment to every user-content surface:

```ts
// client/src/components/ui-components/TextStyledComponents.ts
export const UserContent = styled(Typography)({
  overflowWrap: "anywhere",
  wordBreak: "break-word",
  whiteSpace: "pre-wrap",     // preserve author line breaks; do not collapse
});
```

Use it in `TweetCard`, `CommenterCard`, `RepliesCard`, `VideoCommentItem`, `VideoChannelAndDescription`, and the playlist name/description renderers. `overflowWrap: "anywhere"` is what breaks an unbroken token; `wordBreak: "break-word"` alone does not in all browsers.

## Choosing the numbers

| Field | Limit | Rationale |
| --- | --- | --- |
| Tweet | 1,000 | 3.5× Twitter's 280. Generous, still bounded. |
| Comment | 2,000 | Comments are discussion; longer than a post is reasonable. |
| Video title | 150 | YouTube uses 100. Extra room for non-Latin scripts. |
| Video description | 5,000 | YouTube uses 5,000. |
| Playlist name | 100 | Rendered in constrained list rows. |
| Playlist description | 500 | Secondary text. |
| Username | 20 | URL segment; must stay short and typeable. |
| Full name | 80 | Long enough for full legal names in any script. |

These are starting points. The important property is that they exist and are enforced in one place; the exact values can be tuned.

## Existing data

```js
// mongosh — check whether anything already exceeds the new limits
db.tweets.countDocuments({ $expr: { $gt: [{ $strLenCP: "$content" }, 1000] } });
db.comments.countDocuments({ $expr: { $gt: [{ $strLenCP: "$content" }, 2000] } });
db.users.countDocuments({ $expr: { $gt: [{ $strLenCP: "$username" }, 20] } });
```

`$strLenCP` counts code points, which is the right measure. If there are violations, decide whether to truncate or leave them — schema validators only run on write, so existing documents are unaffected until edited. Leaving them is usually fine; just be aware that editing such a document will then fail validation, which is a confusing error for the author.
