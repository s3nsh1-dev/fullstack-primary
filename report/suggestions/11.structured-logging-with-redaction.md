# 11. Structured logging: redaction, request IDs, correct levels

- **Rank: 7 / 10**
- **Side: Server**
- **Effort: Small** — one middleware rewrite, one helper, logger config changes

## Current picture

The Winston setup in `server/src/services/logger.service.ts` is more thought-through than most — level-filtered file transports, JSON in production, a colourised console format in development, `maxsize`/`maxFiles` rotation. The problems are in what gets logged and when.

**Secrets are logged.** `requestLogger.middleware.ts:18-22` writes `req.body` for every POST/PUT/PATCH. A plaintext password is currently in `server/logs/http.log`. Full detail in `vulnerabilities/02`.

**File transports only exist in production.** Lines 42-93 are wrapped in `if (env.NODE_ENV === "production")`. So in development nothing is persisted — yet `server/logs/` contains populated files, which means this ran with `NODE_ENV=production` at some point, presumably locally. That is worth knowing: the "production-only" guard is not the safety net it looks like.

**No request correlation.** Two log lines per request ("Incoming request", "Request completed") with no shared identifier. With concurrent traffic you cannot tell which completion belongs to which start, and an error logged from a controller cannot be tied to either.

**Client IP is commented out everywhere.** `requestLogger.middleware.ts:14`, `error.middleware.ts:150`, `logger.service.ts:142` all have `// ip: req.ip` disabled. Presumably because `req.ip` returns the proxy address without `trust proxy` — so the field was useless and got commented out rather than fixed.

**Level misuse.** `cloudinary.ts:28-36` logs upload failures at `info`, with the message `"FAILED: ISSUE IN FILE DELETION"` — so a Cloudinary outage appears in `info.log` as a file-deletion notice. `mailHttp.service.ts:62` logs every successful email at `info` including the full provider response.

**Errors are logged twice.** `contact.controller.ts:32` logs the error, then throws `ApiError(500, ...)`, which `error.middleware.ts:148` logs again. Two entries, different shapes, same event.

## Proposed picture

### Redaction helper

```ts
// server/src/utils/redact.ts
const SENSITIVE = new Set([
  "password", "currentpassword", "newpassword", "confirmpassword",
  "token", "accesstoken", "refreshtoken", "authorization", "cookie",
  "apikey", "api_key", "secret", "signature", "csrftoken",
]);

const MAX_DEPTH = 6;
const MAX_STRING = 512;

export const redact = (value: unknown, depth = 0): unknown => {
  if (depth > MAX_DEPTH) return "[TRUNCATED]";
  if (typeof value === "string") {
    return value.length > MAX_STRING ? `${value.slice(0, MAX_STRING)}…[${value.length}]` : value;
  }
  if (value === null || typeof value !== "object") return value;
  if (Array.isArray(value)) return value.slice(0, 50).map((v) => redact(v, depth + 1));

  return Object.fromEntries(
    Object.entries(value as Record<string, unknown>).map(([k, v]) =>
      SENSITIVE.has(k.toLowerCase()) ? [k, "[REDACTED]"] : [k, redact(v, depth + 1)]
    )
  );
};
```

Depth and length caps matter as much as the key filter: a deeply nested or enormous object logged per request will fill a disk faster than any secret leak will hurt you.

### Request logger

```ts
// server/src/middleware/requestLogger.middleware.ts
import { randomUUID } from "crypto";

export function requestLogger(req: Request, res: Response, next: NextFunction): void {
  const startTime = process.hrtime.bigint();
  const requestId = req.get("x-request-id") ?? randomUUID();

  req.requestId = requestId;
  res.setHeader("x-request-id", requestId);

  res.on("finish", () => {
    const durationMs = Number(process.hrtime.bigint() - startTime) / 1e6;

    const entry = {
      requestId,
      method: req.method,
      route: req.route?.path ?? req.path,
      status: res.statusCode,
      durationMs: Math.round(durationMs),
      ip: req.ip,
      userId: req.user?._id ? String(req.user._id) : undefined,
      // deliberately absent: body, query values, headers
    };

    if (res.statusCode >= 500) logService.error("request failed", undefined, entry);
    else if (res.statusCode >= 400) logService.warn("request rejected", entry);
    else logService.http("request", entry);
  });

  next();
}
```

Five changes:

- **One line per request instead of two.** Halves volume and removes the correlation problem for the common case.
- **`res.on("finish")` instead of monkey-patching `res.end`.** The current code reassigns `res.end` with a cast (`as typeof res.end`), which is fragile and interacts badly with streaming responses. `finish` is the supported hook.
- **`req.route?.path`, not `req.originalUrl`.** Logs `/api/v1/users/profile/:userId` rather than `/api/v1/users/profile/68f2a…`. That makes the logs aggregatable by endpoint and stops IDs appearing in every line.
- **Level follows status.** A 500 belongs in `error.log`, not `http.log`.
- **`ip` re-enabled** — it works correctly once `app.set("trust proxy", 1)` is in place (`03.security-middleware-baseline.md`).

Note this also removes query *values* from logs. `?userId=...` and search terms are user data; the route pattern is enough for diagnostics.

### Error middleware

```ts
// server/src/middleware/error.middleware.ts
logService.error("unhandled error", error, {
  requestId: req.requestId,
  route: req.route?.path ?? req.path,
  method: req.method,
  userId: req.user?._id ? String(req.user._id) : undefined,
  body: redact(req.body),        // redacted, and only for 5xx
});
```

and return the ID to the client:

```ts
res.status(errorResponse.statusCode).json({
  success: false,
  message: errorResponse.message,
  errors: errorResponse.errors ?? null,
  requestId: req.requestId,
  ...(errorResponse.stack && { stack: errorResponse.stack }),
  data: null,
});
```

A user reporting "it broke" can now quote an ID that appears verbatim in your logs. That is the single highest-value diagnostic feature you can add, and it costs two lines.

### Logger config

```ts
// server/src/services/logger.service.ts
const fileTransportsEnabled =
  env.NODE_ENV === "production" || process.env.LOG_TO_FILE === "true";
```

Decouple file logging from `NODE_ENV`, so you can enable it locally without pretending to be production — which is how a real password ended up in `logs/http.log`.

Also add exception handlers, which the current config lacks:

```ts
const winstonInstance = winston.createLogger({
  level: logLevel,
  format: logFormat,
  transports: [ /* ... */ ],
  exceptionHandlers: [new winston.transports.Console({ format: logFormat })],
  rejectionHandlers: [new winston.transports.Console({ format: logFormat })],
  exitOnError: false,
});
```

### Fix the level misuse

```ts
// server/src/utils/cloudinary.ts
} catch (error) {
  logService.error("cloudinary upload failed", error, { localFilePath, folderName });
  await fs.unlink(localFilePath).catch(() => {});
  throw new ApiError(502, "MEDIA UPLOAD FAILED");   // was: silently return undefined
}
```

Rethrowing rather than returning `undefined` is the important part. Every caller currently does `if (!uploaded) throw new ApiError(400, "...")`, converting an upstream provider failure into a 400 that blames the client. It should be a 502.

(Moot if you adopt `10.direct-to-cloudinary-uploads.md`, which removes this function.)

## Retention and shipping

`maxsize: 5MB, maxFiles: 5` gives 25 MB per level — reasonable, but it is size-based, so you cannot answer "what happened last Tuesday". If that matters, switch to `winston-daily-rotate-file` with `maxFiles: "14d"`.

On Render, Railway, and Fly, the filesystem is ephemeral — logs vanish on every deploy and restart. **Files are the wrong destination there.** Log JSON to stdout and let the platform collect it; add a hosted sink (Better Stack, Axiom, Logtail) when you need retention. The `logFormat` (JSON) is already correct for this; you would simply not register the file transports in that environment.

Before shipping logs anywhere external, the redaction above must be in place. A third-party log service is a much wider audience than a local file.
