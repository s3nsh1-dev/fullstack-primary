# 07. Add indexes and let unique constraints enforce integrity

- **Rank: 8 / 10**
- **Side: Server**
- **Effort: Small.** Schema additions plus a one-time dedup migration

## Current picture

Across seven models there are **four** index declarations, and three of them are on the `View` collection.

| Model | Indexes declared |
| --- | --- |
| `user.model.ts` | `username` (via `index: true` + `unique`), `email` (`unique`), `fullname` (`index: true`) |
| `video.model.ts` | none |
| `comment.model.ts` | none |
| `like.model.ts` | none |
| `playlist.model.ts` | none |
| `subscription.model.ts` | none |
| `view.model.ts` | `videoId`, `fingerprint`, compound `{videoId, fingerprint, createdAt}`, TTL on `createdAt` |

Every foreign-key lookup in the application is therefore a collection scan. The queries that run on the busiest paths:

```ts
Video.find({ owner: userId })                        // dashboard, channel page
Video.aggregate([{ $match: { isPublished: true } }, { $sort: { createdAt } }])   // feed
Comment.find({ video: video._id })                   // every video page
Comment.countDocuments({ video: toObjectId(video_ID) })
Like.countDocuments({ video: videoId })              // every video page
Like.findOne({ video: videoId, likedBy: req.user._id })
Subscription.countDocuments({ channel: user._id })   // every profile page
Subscription.find({ subscriber: subscriberId })
Tweet.find({ owner: user_ID })
Playlist.aggregate([{ $match: { owner: toObjectId(userId) } }])
```

None of these can use an index. At demo scale that is invisible. It stops being invisible somewhere in the low tens of thousands of documents, and the failure is not gradual. `$sort` on an unindexed field aborts once the in-memory sort exceeds 100 MB, so queries start erroring rather than slowing down.

### Missing uniqueness is a correctness problem, not just performance

Two collections rely on application-level check-then-write, which is not atomic:

```ts
// toggleVideoLike.ts:19-28
const searchVideoLike = await Like.findOne({ video: videoId, likedBy: req.user._id });
if (!searchVideoLike) {
  await Like.create({ video: videoId, likedBy: req.user._id.toString() });
}
```

```ts
// toggleSubscription.ts:21-29
const findChannelByID = await Subscription.findOne({ channel: channelId, subscriber: subscriberId });
if (!findChannelByID) {
  await Subscription.create({ channel: channelId, subscriber: subscriberId });
}
```

Two concurrent requests, a double-click or a retried request, both read "no existing document" and both insert. Nothing prevents it. Results:

- Duplicate `Like` documents inflate `Like.countDocuments({ video })`, which is the like counter shown on every video.
- Duplicate `Subscription` documents inflate subscriber counts on the profile page and in `getChannelStats`.
- The toggle then breaks: `deleteOne` removes one duplicate, so the user clicks unlike and stays liked.

There is no way to fix this in application code. It requires a database constraint.

## Proposed picture

### Uniqueness first

```ts
// server/src/models/like.model.ts
// One like per user per target. Partial filters are required because each
// document sets exactly one of video/comment/tweet — without them, every
// document with `video: null` would collide on a plain compound unique index.
likeSchema.index(
  { video: 1, likedBy: 1 },
  { unique: true, partialFilterExpression: { video: { $exists: true, $type: "objectId" } } }
);
likeSchema.index(
  { comment: 1, likedBy: 1 },
  { unique: true, partialFilterExpression: { comment: { $exists: true, $type: "objectId" } } }
);
likeSchema.index(
  { tweet: 1, likedBy: 1 },
  { unique: true, partialFilterExpression: { tweet: { $exists: true, $type: "objectId" } } }
);

// lookups by target, for counts
likeSchema.index({ video: 1 });
likeSchema.index({ likedBy: 1, updatedAt: -1 });   // getEveryLikedContent's sort
```

The `partialFilterExpression` is the subtle part. `like.model.ts` has a polymorphic shape: `video`, `comment`, and `tweet` are all optional, and each document uses one. A plain `unique` index on `{video, likedBy}` treats missing fields as `null`, so a user's second comment-like would collide with their first on `{video: null, likedBy: X}`. The partial filter restricts the index to documents where `video` is actually an ObjectId.

```ts
// server/src/models/subscription.model.ts
subscriptionSchema.index({ subscriber: 1, channel: 1 }, { unique: true });
subscriptionSchema.index({ channel: 1 });     // subscriber counts and lists
```

Then simplify the toggles to rely on the constraint:

```ts
// toggleVideoLike.ts
try {
  await Like.create({ video: videoId, likedBy: req.user._id });
  return res.status(200).json(new ApiResponse(200, { liked: true }, "LIKE ADDED"));
} catch (error: any) {
  if (error?.code === 11000) {
    await Like.deleteOne({ video: videoId, likedBy: req.user._id });
    return res.status(200).json(new ApiResponse(200, { liked: false }, "LIKE REMOVED"));
  }
  throw error;
}
```

One round trip instead of two, and correct under concurrency because the uniqueness decision is made by the database, not by a read that can go stale.

### Query indexes

```ts
// video.model.ts
videoSchema.index({ owner: 1, createdAt: -1 });          // channel page, dashboard
videoSchema.index({ isPublished: 1, createdAt: -1 });    // feed
videoSchema.index({ owner: 1, isPublished: 1 });         // public channel listing

// comment.model.ts
commentSchema.index({ video: 1, createdAt: -1 });
commentSchema.index({ tweet: 1, createdAt: -1 });
commentSchema.index({ comment: 1, createdAt: -1 });      // nested replies
commentSchema.index({ owner: 1 });                        // cascade delete

// tweet.model.ts
tweetSchema.index({ owner: 1, createdAt: -1 });
tweetSchema.index({ createdAt: -1 });                     // feed

// playlist.model.ts
playlistSchema.index({ owner: 1, updatedAt: -1 });
```

**Compound field order follows the ESR rule**: Equality fields first, then Sort, then Range. `{ owner: 1, createdAt: -1 }` serves `find({owner}).sort({createdAt: -1})` entirely from the index, with no in-memory sort and no document fetch for the sort phase. Reversing to `{createdAt: -1, owner: 1}` would not.

A compound index also serves queries on its prefix, so `{ owner: 1, createdAt: -1 }` covers plain `find({ owner })` too. That is why the list is shorter than the query list.

### Text indexes for search

`searchUserText.controller.ts` uses unanchored `$regex`, which cannot use a standard index under any circumstances, so every search is a full scan of four collections.

```ts
userSchema.index({ username: "text", fullname: "text" });
videoSchema.index({ title: "text", description: "text" });
tweetSchema.index({ content: "text" });
```

The trade-off is real and you should decide deliberately: text indexes match **whole words with stemming**, so searching `prog` stops matching `programming`. Regex substring matching is what the current UI implies. Options:

- **Accept word matching.** Simplest, index-backed, gives relevance scores via `$meta: "textScore"`. Most search UIs work this way.
- **Keep regex, add anchoring.** `new RegExp("^" + escaped, "i")` on `username` *can* use the existing index, but only for prefix matches, and only on that field.
- **Hybrid.** Text index for queries of 3+ characters, anchored regex for shorter prefixes.

| | Index-backed | Matches mid-word | Matches prefixes | Relevance scoring | Cost per search |
| --- | --- | --- | --- | --- | --- |
| Unanchored `$regex` (today) | **no** | yes | yes | no | full scan of 4 collections |
| Anchored `^prefix` regex | yes, that one field only | no | yes | no | cheap |
| Text index | yes | no, whole words with stemming | no | yes, via `$meta` | cheap |

I would take the first. Note MongoDB permits only **one** text index per collection, so `{username: "text", fullname: "text"}` must be a single compound declaration, as written.

## Migration

Indexes are built in the background by default on modern MongoDB, but **unique** index creation fails if duplicates already exist. Clean first:

```js
// mongosh — find duplicate likes
db.likes.aggregate([
  { $match: { video: { $exists: true, $ne: null } } },
  { $group: { _id: { video: "$video", likedBy: "$likedBy" }, ids: { $push: "$_id" }, n: { $sum: 1 } } },
  { $match: { n: { $gt: 1 } } },
]);

// remove all but the first of each group
db.likes.aggregate([
  { $match: { video: { $exists: true, $ne: null } } },
  { $group: { _id: { video: "$video", likedBy: "$likedBy" }, ids: { $push: "$_id" }, n: { $sum: 1 } } },
  { $match: { n: { $gt: 1 } } },
]).forEach(g => db.likes.deleteMany({ _id: { $in: g.ids.slice(1) } }));
```

Repeat for `comment`/`tweet` likes and for subscriptions.

**Turn off `autoIndex` in production.** Mongoose builds declared indexes on startup by default, which is convenient in development and a hazard in production, because a large index build blocks startup and consumes I/O.

```ts
// server/src/db/mongodb.connect.ts
await mongoose.connect(`${env.MONGODB_URI}/${env.DB_NAME}`, {
  autoIndex: env.NODE_ENV !== "production",
});
```

In production, create indexes deliberately via a migration script or the Atlas UI. Also worth adding to that call: `serverSelectionTimeoutMS: 10_000` and `maxPoolSize: 10`. The current connect has no options at all, so a Mongo outage hangs startup for the driver's 30-second default.
