# 02. Validate every request at the route boundary with schemas

- **Rank: 9 / 10**
- **Side: Server** (with knock-on type safety for the client)
- **Effort: Medium** — one middleware, ~25 schema definitions, incremental rollout

## Current picture

There is no validation layer. Each controller does its own ad-hoc checking, and the approaches are all different:

```ts
// registerUser.ts — calls .trim() before checking the value exists
if ([fullname, email, username, password].some((field) => field.trim() === ""))

// loginUser.ts — checks presence but not type; no password check at all
if (!username && !email) throw new ApiError(400, "USERNAME OR EMAIL IS REQUIRED");

// newUsernameUpdate.ts — no check whatsoever
const { username } = req.body;
await User.findByIdAndUpdate(req.user._id, { $set: { username } });

// createTweet.ts — no check; relies on the Mongoose `required` validator
const { content } = req.body;

// usernameAvailability.ts — a cast that asserts a type it has not verified
const { inp } = req.query as { inp: string };

// updatePlaylist.ts — actually does it correctly
const name = typeof req.body.name === "string" ? req.body.name.trim() : undefined;

// contact.route.ts — the only route using express-validator
body("email").trim().isEmail().normalizeEmail()
```

Seven files, six different strategies. `express-validator` is already a dependency and is used on exactly one route out of roughly sixty.

The consequences are documented separately as vulnerabilities:

- `vulnerabilities/12.nosql-operator-injection.md` — untyped values reaching query filters as operators.
- `vulnerabilities/14.weak-registration-validation.md` — no password policy, `TypeError` 500s from `.trim()` on `undefined`.
- `vulnerabilities/13.unbounded-pagination-and-unpaginated-search.md` — `page`/`limit` unclamped.

Fixing those one controller at a time produces twenty more hand-written checks in twenty different styles. The alternative is one layer.

## Proposed picture

Schemas at the route, typed data in the controller.

### Choose zod over express-validator

You have express-validator installed, so this is a real decision. My recommendation is **zod**, for one reason that matters more than the others: it produces TypeScript types from the schema, so the controller's `req.body` is typed without a cast.

```ts
// express-validator: validation and types are separate, and can drift
body("limit").isInt({ min: 1, max: 100 })
const limit = Number(req.query.limit);         // still `any`, still needs Number()

// zod: one declaration, type inferred
const schema = z.object({ limit: z.coerce.number().int().min(1).max(100).default(20) });
type Query = z.infer<typeof schema>;           // { limit: number }
```

The second advantage is that zod **transforms** as well as validates — `z.coerce.number()`, `.trim()`, `.toLowerCase()` — so the controller receives clean data rather than raw strings it must convert. That removes a whole category of `Number(req.query.page) || 1` boilerplate.

```bash
cd server && npm install zod && npm uninstall express-validator
```

### The middleware

```ts
// server/src/middleware/validate.middleware.ts
import type { Request, Response, NextFunction } from "express";
import { ZodError, type ZodTypeAny } from "zod";
import ApiError from "../utils/ApiError";

type Schemas = {
  body?: ZodTypeAny;
  query?: ZodTypeAny;
  params?: ZodTypeAny;
};

export const validate =
  (schemas: Schemas) =>
  (req: Request, _res: Response, next: NextFunction) => {
    try {
      if (schemas.body)   req.body = schemas.body.parse(req.body);
      if (schemas.params) req.params = schemas.params.parse(req.params);
      if (schemas.query) {
        // Express 5: req.query is a getter — assign to a separate property
        (req as any).validatedQuery = schemas.query.parse(req.query);
      }
      next();
    } catch (error) {
      if (error instanceof ZodError) {
        throw new ApiError(
          400,
          "VALIDATION ERROR",
          error.issues.map((i) => `${i.path.join(".") || "(root)"}: ${i.message}`).join("; ")
        );
      }
      throw error;
    }
  };
```

**The Express 5 note is important.** In Express 5 `req.query` is a lazily-computed getter with no setter — assigning to it throws `TypeError: Cannot set property query`. Your `package.json` has `express: ^5.1.0`. Write the parsed result to `req.validatedQuery` and read that in controllers. (`req.body` and `req.params` are still writable.)

Declare it once:

```ts
// server/src/types/express.d.ts
declare global {
  namespace Express {
    interface Request {
      user?: UserThisType;
      validatedQuery?: unknown;
    }
  }
}
```

### Shared building blocks

```ts
// server/src/schemas/common.schema.ts
import { z } from "zod";
import { isValidObjectId } from "mongoose";

export const objectId = z
  .string()
  .refine(isValidObjectId, { message: "must be a valid ObjectId" });

export const pagination = z.object({
  page:  z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
});

export const username = z
  .string()
  .trim()
  .toLowerCase()
  .regex(/^[a-z0-9_]{3,20}$/, "3-20 characters: a-z, 0-9, underscore")
  .refine((v) => !RESERVED_USERNAMES.has(v), { message: "that username is reserved" });

export const email = z.string().trim().toLowerCase().email().max(255);

export const password = z
  .string()
  .min(10, "must be at least 10 characters")
  .max(128, "must be at most 128 characters")
  .refine((v) => !COMMON_PASSWORDS.has(v.toLowerCase()), { message: "too common" });

export const RESERVED_USERNAMES = new Set([
  "admin", "api", "settings", "setting", "history", "tweets", "videos",
  "playlists", "search", "support", "messages", "liked-content",
  "my-videos", "subscribers", "test",
]);
```

This is where the cross-document consistency lives. `vulnerabilities/12` and `vulnerabilities/14` both specify a username rule and a password rule. **They must be one definition, here**, not three copies.

### Feature schemas

```ts
// server/src/schemas/user.schema.ts
import { z } from "zod";
import { username, email, password, objectId, pagination } from "./common.schema";

export const registerSchema = {
  body: z.object({
    fullname: z.string().trim().min(1).max(80).regex(/^[\p{L}\p{M}'\-. ]+$/u, "invalid characters"),
    email,
    username,
    password,
  }),
};

export const loginSchema = {
  body: z
    .object({
      username: z.string().trim().toLowerCase().optional(),
      email: z.string().trim().toLowerCase().optional(),
      password: z.string().min(1, "password is required"),
    })
    .refine((d) => Boolean(d.username || d.email), {
      message: "username or email is required",
    }),
};

export const changePasswordSchema = {
  body: z.object({
    currentPassword: z.string().min(1),
    newPassword: password,
  }),
};

export const usernameAvailabilitySchema = { query: z.object({ inp: username }) };
export const userIdParamSchema = { params: z.object({ userId: objectId }) };
```

Note `loginSchema` does **not** apply the strong-password rule to the `password` field — existing users may have weak passwords, and rejecting them at login would lock them out. Only `registerSchema` and `changePasswordSchema` enforce the policy. This distinction is easy to get wrong and is exactly the kind of thing a shared schema module makes visible.

### Wired into routes

```ts
// server/src/routes/user.routes.ts
userRouter.route("/register").post(
  registerLimiter,
  imageUpload.fields([{ name: "avatar", maxCount: 1 }, { name: "coverImage", maxCount: 1 }]),
  validate(registerSchema),
  registerUser
);

userRouter.route("/login").post(authLimiter, validate(loginSchema), loginUser);
userRouter.route("/profile/:userId").get(optionalAuth, validate(userIdParamSchema), fetchUserById);
userRouter.route("/change-password").post(requireAuth, validate(changePasswordSchema), changeCurrentPassword);
```

**Middleware order matters:** multer must run before `validate` on multipart routes, because `req.body` does not exist until multer has parsed the form. The rate limiter must run before multer, so a rejected request does not write a file first (see `vulnerabilities/04`).

### The controller shrinks

```ts
// before — registerUser.ts
export const registerUser = asyncHandler(async (req, res) => {
  const { fullname, email, username, password } = req.body;
  if ([fullname, email, username, password].some((field) => field.trim() === "")) {
    throw new ApiError(400, "INCOMPLETE INPUT FIELDS BY USER");
  }
  const exitedUser = await User.findOne({ $or: [{ username, email }] });
  if (exitedUser) throw new ApiError(409, "DUPLICATE DATA: USERNAME OR EMAIL");
  ...

// after
export const registerUser = asyncHandler(async (req, res) => {
  const { fullname, email, username, password } = req.body as RegisterBody;
  // fields are guaranteed present, correctly typed, trimmed, lowercased,
  // and the password already satisfies the policy

  const existing = await User.findOne({ $or: [{ username }, { email }] });
  if (existing) throw new ApiError(409, "USERNAME OR EMAIL IS ALREADY REGISTERED");
  ...
```

## Rollout order

Do not attempt this in one pass. Ranked by risk closed per unit of work:

1. `login`, `register`, `change-password`, `update/username` — closes `vulnerabilities/12` and `14`.
2. Every route with an `:id` parameter — replaces ~30 scattered `isValidObjectId` checks.
3. Every paginated list route — closes `vulnerabilities/13` (see `09.shared-pagination-contract.md`, whose helper is subsumed by the `pagination` schema above).
4. Content-creation routes — tweets, comments, playlists (see `21.content-length-limits.md`).

The layer is additive: routes without a `validate()` call behave exactly as they do today, so you can migrate one route at a time and ship in between.
