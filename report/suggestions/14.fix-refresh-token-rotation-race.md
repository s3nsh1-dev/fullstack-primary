# 14. Fix the refresh-token rotation race

- **Rank: 7 / 10**
- **Side: Both**
- **Effort: Small-medium**

## Current picture

Refresh tokens rotate on every use. `generateAccessAndRefreshTokens` mints a new pair and overwrites the stored bcrypt hash:

```ts
// generateAccessAndRefreshTokens.ts
const newAccessToken = await user.generateAccessToken();
const newRefreshToken = await user.generateRefreshToken();
const hashedRefreshToken = await hashRefreshToken(newRefreshToken);
user.refreshToken = hashedRefreshToken;
await user.save({ validateBeforeSave: false });
```

Rotation is correct and good practice — it makes a stolen refresh token detectable, because reuse of a rotated token fails.

The problem is that **the client calls the rotating endpoint for something that is not a refresh**:

```ts
// client/src/hooks/data-fetching/useRefreshUser.ts
export const useRefreshUser = () =>
  useQuery({
    queryKey: ["currentUser"],
    queryFn: async () => {
      const response = await fetch(`${URL}/users/refresh-token`, {
        credentials: "include",
        method: "POST",
      });
      if (!response.ok) throw new Error("Failed to refresh user");
      return (await response.json()).data;
    },
    staleTime: 1000 * 60 * 5,
    refetchOnWindowFocus: false,
    retry: false,
  });
```

This runs in `AuthContextProvider` on **every mount of the app**, to answer "am I logged in?". So a rotation happens on every page load.

### The race

`user.refreshToken` is a single column. Two concurrent refreshes:

```
t0  Tab A sends refresh with token R1
t1  Tab B sends refresh with token R1
t2  Server (A): compareRefreshToken(R1, hash(R1)) → true → stores hash(R2), returns R2
t3  Server (B): compareRefreshToken(R1, hash(R2)) → false
t4  Server (B): $unset refreshToken, throws 401 "REFRESH TOKEN IS EXPIRED OR USED"
```

Tab B is logged out. And because `refreshAccessToken.ts:56` **unsets the stored token** on mismatch, tab A's brand-new R2 is destroyed as well. Both tabs are logged out, and so is every other device.

That `$unset` is deliberate — it is the standard reuse-detection response, on the theory that a replayed token means theft. It is the right behaviour for actual theft. Here it fires on ordinary concurrency.

Triggers, all routine:

- Two tabs open, both reloaded (⌘R on a browser restoring a session).
- One tab plus a mobile app or a second browser.
- Any concurrent request storm after the access token expires — every 401 triggers a refresh, and there is nothing to deduplicate them.
- Double-clicking reload.

Two more contributing factors:

**`staleTime: 5 min` does not help.** React Query's `staleTime` prevents *refetches* within a session, but a page reload is a fresh cache. Every hard navigation rotates.

**`retry: false` means a transient failure is a logout.** A dropped connection during refresh is indistinguishable from an invalid token to this client.

## Proposed picture

Three changes. The first is by far the most important.

### 1. Stop using `/refresh-token` for session bootstrap

Add `GET /users/me`, which reads the access token and has no side effects. The client bootstraps from that.

```
GET  /users/me            → who am I?             no side effects
POST /users/refresh-token → my access token died  rotates
```

With this, refresh happens only when an access token actually expires — roughly once every 15 minutes of active use, rather than on every page load. The race window shrinks from "every navigation" to "the rare moment two requests both 401 simultaneously".

Full design in `04.unify-auth-session-model.md`. **This is the change that matters**; the two below are refinements.

### 2. Deduplicate refresh on the client

Even with (1), a page load fires several queries at once. If the access token has just expired they all 401 together. Collapse them into one refresh:

```ts
// client/src/lib/apiClient.ts
let refreshPromise: Promise<void> | null = null;

const refreshSession = (): Promise<void> => {
  refreshPromise ??= apiClient
    .post("/users/refresh-token")
    .then(() => undefined)
    .finally(() => { refreshPromise = null; });
  return refreshPromise;
};
```

Detailed in `06.single-http-client-with-interceptors.md`. This handles concurrency *within one tab*. It cannot help across tabs — for that you need (3), or a `BroadcastChannel` lock, which is more machinery than this problem warrants.

### 3. Server-side grace window

Accept the immediately-previous token for a short period, so a genuinely concurrent second request succeeds instead of triggering reuse detection.

```ts
// server/src/models/user.model.ts
refreshToken:         { type: String, default: "" },
previousRefreshToken: { type: String, default: "" },
previousTokenExpiry:  { type: Date, default: null },
```

```ts
// server/src/utils/refreshTokenSecurity.ts
const GRACE_MS = 30_000;

export const verifyRefreshToken = async (
  incoming: string,
  user: { refreshToken?: string; previousRefreshToken?: string; previousTokenExpiry?: Date | null }
): Promise<"current" | "grace" | "invalid"> => {
  if (user.refreshToken && (await bcrypt.compare(incoming, user.refreshToken))) {
    return "current";
  }
  const graceValid =
    user.previousRefreshToken &&
    user.previousTokenExpiry &&
    user.previousTokenExpiry.getTime() > Date.now() &&
    (await bcrypt.compare(incoming, user.previousRefreshToken));

  return graceValid ? "grace" : "invalid";
};
```

```ts
// generateAccessAndRefreshTokens.ts
user.previousRefreshToken = user.refreshToken;
user.previousTokenExpiry = new Date(Date.now() + GRACE_MS);
user.refreshToken = await hashRefreshToken(newRefreshToken);
await user.save({ validateBeforeSave: false });
```

```ts
// refreshAccessToken.ts
const state = await verifyRefreshToken(incomingRefreshToken, user);

if (state === "invalid") {
  // genuine reuse of a long-dead token → treat as theft
  await User.updateOne({ _id: user._id }, {
    $unset: { refreshToken: 1, previousRefreshToken: 1, previousTokenExpiry: 1 },
    $inc: { tokenVersion: 1 },
  });
  throw new ApiError(401, "REFRESH TOKEN IS EXPIRED OR USED");
}

if (state === "grace") {
  // A concurrent request already rotated. Do not rotate again — issue a fresh
  // access token against the token that is already current.
  const accessToken = await user.generateAccessToken();
  return res
    .status(200)
    .cookie("accessToken", accessToken, accessTokenCookieOptions)
    .json(new ApiResponse(200, { user: safe(user) }, "ACCESS TOKEN REFRESHED"));
}

// state === "current" → normal rotation
```

The `grace` branch deliberately **does not rotate again**. Rotating on a grace hit would restart the race. Issuing only a new access token is enough — the client's refresh cookie is already the current one from the concurrent request.

`GRACE_MS` of 30 seconds is long enough for realistic concurrency and short enough that a stolen token cannot be meaningfully replayed. It only accepts one generation back.

## Also worth fixing here

**`compareRefreshToken` has a plaintext fallback:**

```ts
const isBcryptHash = (value: string) => value.startsWith("$2");

export const compareRefreshToken = async (incoming: string, stored: string | undefined) => {
  if (!stored) return false;
  if (!isBcryptHash(stored)) {
    return incoming === stored;      // legacy plaintext comparison
  }
  return bcrypt.compare(incoming, stored);
};
```

This is a migration shim from when tokens were stored in plaintext. It also uses `===`, which is not constant-time. Once no plaintext tokens remain — check with `db.users.countDocuments({ refreshToken: { $not: /^\$2/, $ne: "" } })` — delete the branch.

**`retry: false` on the bootstrap query.** Distinguish a 401 (not logged in — do not retry) from a network error (do retry):

```ts
retry: (failureCount, error) =>
  isAxiosError(error) && error.response?.status === 401 ? false : failureCount < 2,
```
