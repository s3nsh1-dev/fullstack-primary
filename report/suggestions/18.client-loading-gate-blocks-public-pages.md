# 18. The session check blanks the entire app, including public pages

- **Rank: 6 / 10**
- **Side: Client**
- **Effort: Small**

## Current picture

```tsx
// client/src/App.tsx:44-61
function App() {
  const { mode } = useMode();
  const { loading } = useAuth();
  const searchRef = useGlobalSearch();
  // ...
  if (loading) return <AppLoadingProgress />;
  return ( /* the entire application */ );
}
```

`loading` is `isLoading` from the `useRefreshUser` query in `AuthContextProvider`. So until `POST /api/v1/users/refresh-token` resolves, the app renders nothing but a loading screen.

This gates **everything** on an authentication call, including content that requires no authentication:

- `/` — the feed, public
- `/:username` — channel pages, public
- `/videos/:videoId` — video pages, public
- `/tweets/:tweetId` — tweet pages, public
- `/search` — public
- `/support` — public

The consequences:

**Every visitor waits for an auth round trip they do not need.** A first-time visitor with no cookies still waits for the request to complete and return 401 before seeing anything. On a cold serverless start or a slow connection that is seconds of blank screen.

**A slow API means a blank site.** If the API is slow but the CDN-served frontend is fast, users see nothing at all rather than a shell.

**Bad interaction with `retry: false`.** `useRefreshUser` sets `retry: false`, so a transient network failure resolves `loading` immediately but leaves the user logged out — which is at least fast. But combined with the rotation race (`14.fix-refresh-token-rotation-race.md`), a user in a second tab is silently logged out with no explanation.

**Crawlers and link previews see nothing.** Any bot that does not execute JavaScript and wait gets an empty page. For a video platform where links get shared, that means no previews.

Two smaller issues in the same function:

- `AppLoadingProgress` is imported eagerly while eighteen route components are lazy — correct, since it is needed immediately, but worth noting the loading screen is in the main bundle.
- The `Ctrl/Cmd+K` keyboard handler in `useEffect` is registered after the early return, so it does not attach until loading completes. Minor, but it means the shortcut is dead during load.

## Proposed picture

Public routes should render immediately. Only routes that genuinely need a user should wait.

### Render the shell immediately

```tsx
// client/src/App.tsx
function App() {
  const { mode } = useMode();
  const searchRef = useGlobalSearch();

  useEffect(() => {
    const handleCTRL_k = (e: KeyboardEvent) => { /* unchanged */ };
    window.addEventListener("keydown", handleCTRL_k);
    return () => window.removeEventListener("keydown", handleCTRL_k);
  }, [searchRef]);

  // no `loading` gate — the shell renders straight away
  return (
    <ThemeProvider theme={getTheme(mode)}>
      <CssBaseline />
      <Box sx={{ mt: (theme) => `${theme.mixins.toolbar.minHeight}px` }}>
        <Suspense fallback={<AppLoadingProgress />}>
          <Routes>
            <Route element={<Navbar />}>
              {/* public */}
              <Route path="/" element={<Dashboard />} />
              <Route path="/search" element={<SearchPage />} />
              <Route path="/support" element={<Support />} />
              <Route path="/:username" element={<Homepage />}>{/* ... */}</Route>
              <Route path="/videos/:videoId" element={<OpenSingleVideoPage />} />
              <Route path="/tweets/:tweetId" element={<OpenSingleTweetPage />} />

              {/* authenticated */}
              <Route element={<RequireAuth />}>
                <Route path="/liked-content" element={<LikedContent />} />
                <Route path="/setting" element={<Settings />} />
                <Route path="/subscribers" element={<Subscribers />} />
                <Route path="/history" element={<WatchHistory />} />
                <Route path="/messages" element={<Messages />} />
                <Route path="/playlists">{/* ... */}</Route>
                <Route path="/my-videos">{/* ... */}</Route>
                <Route path="/tweets" index element={<Tweets />} />
              </Route>
            </Route>
            <Route path="*" element={<NotFound />} />
          </Routes>
        </Suspense>
      </Box>
    </ThemeProvider>
  );
}
```

### A route guard that waits only where it matters

```tsx
// client/src/components/routing/RequireAuth.tsx
import { Navigate, Outlet, useLocation } from "react-router-dom";
import useAuth from "../../hooks/useAuth";
import CircularProgressCenter from "../ui-components/CircularProgressCenter";
import NotLoggedIn from "../../pages/NotLoggedIn";

const RequireAuth = () => {
  const { user, loading } = useAuth();
  const location = useLocation();

  if (loading) return <CircularProgressCenter />;
  if (!user) return <NotLoggedIn returnTo={location.pathname} />;
  return <Outlet />;
};

export default RequireAuth;
```

The spinner is now scoped to the content area — the navbar, drawer, search, and theme toggle stay interactive while the session resolves.

`NotLoggedIn.tsx` already exists but is currently unused except in a commented-out line in `Navbar.tsx:91`. This gives it a purpose. Passing `returnTo` lets you send the user back where they were after logging in, which the app cannot do today.

### Components that adapt rather than gate

Components rendering on public pages should treat `user` as optional rather than waiting:

```tsx
// e.g. a like button
const { user } = useAuth();
// no `loading` check — render the button, and prompt on click if not logged in
<IconButton onClick={user ? handleLike : promptLogin}>
```

Prefetching the video before knowing who the viewer is works fine, because the server derives the viewer from the cookie (`05.optional-auth-middleware.md`), not from a client-supplied parameter.

## Optional: sub-100ms session resolution

If you want the shell *and* an accurate logged-in navbar with no flash, cache the last known user in `localStorage` and use it as `initialData`:

```ts
const cached = localStorage.getItem("lastSession");

useQuery({
  queryKey: authKeys.session,
  queryFn: fetchSession,
  initialData: cached ? JSON.parse(cached) : undefined,
  staleTime: 0,          // always revalidate in the background
});
```

**Store only display fields — username, avatar URL, display name. Never a token, never an email.** This is a rendering hint, not a credential: the server still authenticates every request from the cookie, and a tampered `localStorage` value grants nothing beyond a briefly wrong navbar.

Given that the app already uses `localStorage` for the theme preference, this is consistent with existing practice. It is optional — the route guard above is the change that matters.

## Interaction with other documents

- `17.missing-suspense-boundaries.md` touches the same `App.tsx` render tree. **Apply together** — the `<Suspense>` in the snippet above is that document's fix.
- `04.unify-auth-session-model.md` — moving bootstrap from `/refresh-token` to `GET /users/me` makes the session check cheaper and removes the rotation side effect. That is the deeper fix; this one makes the wait invisible either way.
- `05.optional-auth-middleware.md` is what makes public pages work correctly for logged-in users without the client passing `?userId=`. Without it, a page rendered before the session resolves would show `isLiked: false` and never correct itself.
- `14.fix-refresh-token-rotation-race.md` — with the gate removed, a failed session check degrades to "logged out navbar" rather than "blank site", which makes that race much less user-visible.
