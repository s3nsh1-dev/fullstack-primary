# PlayTube: security and architecture audit

Audit date: 2026-08-07 · Branch `fix/2026` @ `460480e` · Stack: Vite/React 19 client + Express 5/Mongoose server

**20 vulnerabilities** in [`vulnerabilities/`](vulnerabilities/) · **22 suggestions** in [`suggestions/`](suggestions/)

Every document is standalone: what is wrong, where, why it matters, and the fix. Every document also ends with an **Interaction** section naming the other documents it touches and which one wins where they overlap. That is the part that makes them combinable rather than 42 contradictory patches.

Context used for ranking: deployed, demo data only, no real users yet. So data-exposure findings are ranked on *exploitability* and marked "must fix before real users" rather than "incident in progress".

## How to read this

1. **This file.** The two pictures, the conflict register, and the decisions only you can make.

Do not implement in file order. Implementation order is in [Sequencing](#sequencing) and it is deliberately different from severity order, because several high-severity fixes are trivial once a foundation exists and painful before it.

### What actually changes, in one sentence each

| | Old | New |
|---|---|---|
| **Identity** | client asserts it via `?userId=` | server derives it from the cookie |
| **Tokens** | cookie **and** JSON body | cookie only |
| **Session bootstrap** | `POST /refresh-token` on every page load (rotates!) | `GET /users/me`, no side effects |
| **Config** | `\|\|` fallbacks, boots misconfigured | validated at boot, refuses to start |
| **Validation** | 6 styles across 7 files, or none | one zod schema per route |
| **Authorization** | re-derived per controller, inconsistently | one service function per rule |
| **Integrity** | check-then-write in app code | unique indexes in the database |
| **Deletes** | N sequential ops, half-complete on crash | one transaction |
| **Pagination** | 6 response shapes, unbounded `limit` | one shape, clamped at 100 |
| **Uploads** | proxied through your disk, unlimited, publicly served | signed direct-to-Cloudinary |
| **Logs** | request bodies incl. passwords | redacted, one line, request ID |
| **HTTP client** | 60 hand-rolled call sites | one instance with interceptors |

## Decisions I could not make for you

Each changes what the code should be, and each is referenced from the document that needs it.

1. **Deactivation semantics.** Three components currently disagree: `loginUser` silently reactivates, `refreshAccessToken` rejects, and `reactivateUser` requires a token a deactivated user cannot obtain. Pick "reversible by logging in" (simplest, then delete `reactivateUser`) or "requires explicit reactivation". → [V17](vulnerabilities/17.auth-middleware-ignores-account-status.md)

2. **Account deletion model.** Hard delete, or anonymise-and-purge with a tombstone? I recommend the second (keeps referential integrity), but it is a product decision about what "delete my account" promises. → [V06](vulnerabilities/06.account-deletion-is-a-noop.md)

3. **Search semantics.** MongoDB text indexes are index-backed but match whole words, so `prog` stops matching `programming`. Unanchored regex matches substrings but can never use an index. → [S07](suggestions/07.database-indexes-and-unique-constraints.md), [V13](vulnerabilities/13.unbounded-pagination-and-unpaginated-search.md)

4. **Registration → logged in?** Currently the client *thinks* it logs you in and the server sets no cookies. Either make registration issue cookies, or require an explicit login. Not a third option. → [S04](suggestions/04.unify-auth-session-model.md)

5. **Channel URL namespace.** `/:username` at the router root means any username can shadow an app route (`/settings`, `/history`, `/search`). A reserved-word list works but must stay in sync with `App.tsx` by hand. Moving to `/c/:username` removes the coupling permanently. Cheap now, expensive after launch. → [V12](vulnerabilities/12.nosql-operator-injection.md)

6. **MongoDB replica set.** Transactions require one. Atlas provides it on every tier including free; a standalone local `mongod` does not. This gates [S12](suggestions/12.atomic-cascade-deletes.md) and therefore [V06](vulnerabilities/06.account-deletion-is-a-noop.md).

7. **Direct uploads: worth it?** [S10](suggestions/10.direct-to-cloudinary-uploads.md) removes a whole vulnerability class and your media bandwidth, at the cost of an asset-verification step and an orphan sweep job. For a video platform I would say yes. For an avatars-only app, no.

## What is already good

Worth stating, because an audit is a list of problems and that is a distorted view of the codebase.

- **Passwords are bcrypt-hashed** with a `pre("save")` hook and an `isModified` guard. That is correct, and the guard is the part people get wrong.
- **Refresh tokens are hashed at rest** and rotated on use. Rotation is beyond what most projects at this stage do.
- **Cookies are `httpOnly` + `secure` + `sameSite`**, and no token is written to `localStorage`. That is the single most common auth mistake in a React app, avoided.
- **The CORS allowlist is exact-match**, not a wildcard or a `startsWith` prefix check.
- **Body size limits** (`16kb`) are set on both parsers.
- **Ownership filters are pushed into the query** (`findOneAndUpdate({_id, owner})`) in the playlist controllers. That is the right pattern; the bug in [V20](vulnerabilities/20.silent-authorization-failures.md) is only that one of them does not check the result.
- **`asyncHandler`** wraps every controller, so no route can hang on an unhandled rejection.
- **Graceful shutdown** handles `SIGTERM`/`SIGINT` and closes Mongo, which is genuinely uncommon.
- **`strict: true`** in both tsconfigs.
- **Winston** is configured with level-filtered transports and rotation. The problem is *what* is logged, not the setup.
- **`.env` is correctly gitignored** and `git ls-files` confirms no secret has ever been committed.

The recurring theme across the findings is not carelessness. It is that correct patterns were written once and then copied, and the copies drifted. That is what the service layer, the shared projections, and the validation schemas are for.
